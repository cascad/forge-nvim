## 2026-05-30

### 1. Курсор упирается в конце файла (нет scroll-beyond-last-line)

**Проблема.** В конце файла, когда строк ниже нет, курсор смещается к низу
окна — неудобно. В VS Code можно скроллить за последнюю строку, даже если
ниже ничего нет. Мышью скроллится нормально, а vim — нет.

**Причина.** Neovim из коробки не умеет скроллить за последнюю строку
буфера: окно упирается в EOF.

**Решение.** Новый модуль `lua/forge/eob_scroll.lua` подкладывает под
последнюю строку файла виртуальные пустые строки (`extmark.virt_lines`,
~`высота окна − 2`). Их нет в файле и они не сохраняются, но Neovim
учитывает их при скролле — значит последнюю реальную строку можно поднять
почти к верху окна. Только для обычных file-буферов (спец-окна
neo-tree/dap-ui/terminal/telescope пропускаются). Toggle: `:ForgeEobScroll`
или `vim.g.forge_eob_scroll = false`.

**Файлы:** `lua/forge/eob_scroll.lua` (новый), `lua/config/options.lua`
(подключение через `require("forge.eob_scroll").setup()`).

### 2. Курсор строго по центру → резкий прыжок при выделении мышью

**Проблема.** Указатель строго по центру, при выделении мышью экран
мгновенно прыгает — невозможно нормально скопировать. Хотелось: курсор
двигается в центральной зоне свободно, а у краёв оставляет несколько строк
и начинает ехать.

**Причина.** `opt.scrolloff = 999` — строгое центрирование на каждое
движение.

**Решение.** `scrolloff = 8`. Курсор свободно двигается в центральной зоне,
скролл начинается только у краёв (~1/6 экрана сверху/снизу). Мышиное
выделение перестало дёргаться.

**Файлы:** `lua/config/options.lua`.

### 4. Как заполнить структуру дефолтами по всем полям (fill / autofill)

**Проблема.** Как вызвать саджест, который заполнит структуру дефолтными
значениями по всем полям?

**Это НЕ автокомплит, а Quick Fix / code action** (как лампочка в VS Code,
`Ctrl+.`). «Fill struct» отдаёт LSP-сервер (gopls) как code action.

**Как вызвать меню (3 одинаковые клавиши, выбирай любую):**

| Клавиша   | Что это физически       | Аналог в VS Code / IDE      |
|-----------|-------------------------|-----------------------------|
| `<A-CR>`  | **Alt + Enter** (Return)| IntelliJ / GoLand Alt+Enter |
| `<C-.>`   | **Ctrl + точка**        | VS Code Quick Fix `Ctrl+.`  |
| `<leader>la` | Space, затем `l`, `a`| —                           |

> `<A-CR>` в нотации Neovim = зажать **Alt** и нажать **Enter**. Никакой
> магии. `<C-.>` = **Ctrl + .** (точка), но учти: некоторые терминалы её
> не передают — тогда жми `<A-CR>` или `<leader>la`.

**Что происходит.** Откроется **плавающее меню у курсора** (как лампочка
Quick Fix в VS Code) со списком доступных действий: `Fill Foo`,
`Fill Foo with default values`, `Organize Imports`, `Add import ...`,
clippy-фиксы и т.п. Стрелками/`<C-j>`/`<C-k>` выбираешь, `<Enter>` —
применяешь, `<Esc>` — отмена.

**Пошагово для fill struct:**

1. Курсор на пустом литерале структуры `Foo{}` (или на имени `Foo`).
2. `<A-CR>` (Alt+Enter).
3. В меню выбрать `Fill Foo` → `<Enter>`.
4. gopls подставит все поля с дефолтными значениями.

**Почему раньше «меню не было».** `vim.ui.select` использовал дефолтный
бэкенд Neovim — нумерованный список одной строкой внизу экрана (легко
проглядеть, не похоже на VS Code). Добавили `telescope-ui-select` с темой
`cursor` → теперь это нормальное плавающее меню у курсора. Затрагивает все
select-меню: code action, layout picker (`<leader>pp`), выбор dap-конфига.

**Файлы:** `lua/config/keymaps.lua` (клавиши, см. п. 5),
`lua/plugins/telescope.lua` (`telescope-ui-select` + тема `cursor`).

### 5. Как принять предложение LSP/clippy (например «could lift into loop condition»)

**Проблема.** clippy/gopls предлагают улучшение («default: could lift into
loop condition», «fill struct» и т.п.) — как принять его одной клавишей, как
в VS Code?

**Причина.** Был только `<leader>la` (code action), без привычных VS Code /
IntelliJ биндингов.

**Решение.** Добавили глобальные code-action клавиши:

- `<C-.>` — VS Code Quick Fix (в normal/insert/visual). NB: не все терминалы
  передают `<C-.>`.
- `<A-CR>` (Alt+Enter) — IntelliJ-style, надёжнее в терминале.

Работают и до attach LSP (без LSP — no-op). Через них принимаются: fill
struct, clippy-фиксы, organize imports, add missing import (с выбором
пакета при коллизии) и пр.

**Файлы:** `lua/config/keymaps.lua`.

### 6. Дебаг: остановка на `fatalpanic` — layout не висит, `<leader>pd` не открывает, после F5 call stack пустой

**Проблема.** При остановке на панике (Rust `fatalpanic`) тред
подсвечивается, но debug-layout (левый sidebar со scopes/watch/call
stack/breakpoints) не открыт, и `<leader>pd` его не открывает. После
нажатия F5 (continue → программа завершилась) левая панель появляется, но
call stack пустой.

**Причина.** Layout открывался только на `event_initialized` (РОВНО один раз
при старте сессии) и по нажатию F5. Если программа паниковала/стопалась
позже, а sidebar к тому моменту был скрыт — ничего его не переоткрывало.
Поэтому панель «появлялась» только при следующем действии (continue →
exit), уже с пустым стеком.

**Решение.** Добавили `dap.listeners.after.event_stopped` — на **каждой**
остановке исполнения (breakpoint, паника, исключение, step) гарантированно
показываем левый sidebar с актуальными scopes/call stack. Через
`vim.schedule` (чтобы не словить таймаут «Debug adapter didn't respond»
внутри rpc-callback). Только sidebar; bottom (terminal/repl) и REPL-вывод
не трогаем, чтобы не мигало и не чистилось. Пустой call stack ПОСЛЕ
завершения программы — это норма (сессии больше нет), как в VS Code.

**Файлы:** `lua/plugins/dap.lua`.

### 10. Длинные строки Go не переносятся автоформаттером

**Проблема.** Длинная строка вроде
`fmt.Printf("buggy: %v\n", s2Lst(mergeTwoLists(lst2S(...), lst2S(...))))`
не переносится по правилам Go в автоформате.

**Причина.** `gofmt` и `gofumpt` **принципиально не переносят** длинные
строки — в стиле Go нет лимита длины строки, это намеренное решение
Go-команды. Поэтому официальные тулзы выравнивают отступы/скобки/импорты,
но длинный вызов оставляют одной строкой.

**Решение.** Добавили в цепочку Go-форматтеров `golines`
(`github.com/segmentio/golines`) ПЕРЕД gofumpt: он ломает длинные строки по
аргументам/цепочкам вызовов. Лимит `-m 100` (совпадает с colorcolumn),
`--no-reformat-tags`. golines внутри гоняет gofmt, потом gofumpt
накладывает строгий стиль. Если golines не установлен — conform тихо его
пропускает (переносов не будет, остальное форматируется как раньше).

**Требует установки (системно, не через mason):**
`go install github.com/segmentio/golines@latest`

**Что golines НЕ ломает (важно):**

- **строковые литералы** — содержимое строки не трогает (разрыв изменил бы
  значение). Длинная строка-литерал остаётся одной строкой даже >100.
- **struct-теги** — защищены флагом `--no-reformat-tags`.
- **комментарии** — не сокращает (`--shorten-comments` выключен по умолчанию).

Переносит только в безопасных местах: аргументы вызова (по запятым), поля
composite literal/struct, цепочки `.a().b()`.

**Файлы:** `lua/plugins/format.lua`.

### 9. `Failed to run config for nvim-lspconfig` — Invalid buffer id

**Проблема.** На старте падало:
`vim/diagnostic.lua:1356: Invalid buffer id: 2`, в стеке —
`vim.diagnostic.config` (lsp.lua:131) → `show` → `once_buf_loaded`.
Из-за этого обрывался ВЕСЬ `config()` lspconfig: LSP-серверы,
capabilities и LspAttach ниже строки 131 не настраивались → LSP не
поднимался.

**Причина.** В новых Neovim `vim.diagnostic.config()` при применении
делает re-show диагностики по уже открытым буферам. На старте среди них
бывает временный невалидный/wiped буфер (scratch/alpha, id=2) — внутренний
`once_buf_loaded` падает с «Invalid buffer id». Опции конфига при этом уже
записаны (show идёт ПОСЛЕ записи), падал только перерисов.

**Решение.** Обернули `vim.diagnostic.config(...)` в `pcall` (вынесли в
`apply_diagnostic_config()`); при ошибке — повторная попытка на `VimEnter`
(`once`, через `vim.schedule`), когда буферы стабильны. Вызовы в
`DiagToggle` тоже обёрнуты в `pcall`. Теперь ошибка перерисовки не рушит
весь config, LSP поднимается, а диагностика дорисуется на следующем
publish / WinEnter (`setup_refresh`).

**Файлы:** `lua/plugins/lsp.lua`.

### WezTerm: шелл/диск, дополнение путей, шрифт, Ctrl+C/V

Терминал WezTerm (конфиг в корне репо — `wezterm.lua`, подключается через
переменную окружения `WEZTERM_CONFIG_FILE`). Это НЕ часть nvim-конфига:
WezTerm только рисует и передаёт клавиши, а `cd`/дополнение путей — функции
шелла (PowerShell).

**Проблема 1 — `cd` не менял диск.** WezTerm запускал `cmd.exe` (наш конфиг
ещё не подхватывался), а в `cmd` `cd D:\` без `/d` диск не меняет.
**Решение.** `default_prog` явно ставит PowerShell: pwsh 7 если есть в PATH,
иначе встроенный `powershell.exe` (в нём `cd D:\` работает). Конфиг
подключён через `WEZTERM_CONFIG_FILE` (User-level env).

**Проблема 2 — Tab подставлял несуществующие папки / не дополнял
существующие.** Это поведение PSReadLine, а не терминала.
**Решение.** В `$PROFILE` (`Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1`):
`Tab → MenuComplete` (меню реальных путей), `Up/Down → HistorySearch`,
`SaveIncrementally` + `HistoryNoDuplicates`, опционально `PredictionSource
History` (через try/catch — PSReadLine 2.0 его не умеет, нужен 2.1+).

**Проблема 3 — `Unable to load font CaskaydiaCove Nerd Font`.** Шрифт не был
установлен.
**Решение.** Поставлен per-user (без админа) из официального релиза Nerd
Fonts: скачан `CascadiaCode.zip`, `CaskaydiaCoveNerdFont-*.ttf` скопированы в
`%LOCALAPPDATA%\Microsoft\Windows\Fonts` и зарегистрированы в
`HKCU\...\Fonts`. ВАЖНО: в Nerd Fonts 3.x семейство называется
`CaskaydiaCove NF` (не `CaskaydiaCove Nerd Font`) — оно стоит первым в
`font_with_fallback`, дальше старое имя и моноширинные фолбэки. Добавлен
`warn_about_missing_glyphs = false`.

**Проблема 4 — нужен рабочий Ctrl+C/Ctrl+V.**
**Решение.** Ctrl+C — «умный»: копирует при наличии выделения, иначе шлёт
SIGINT в программу. Ctrl+V — вставка. Дубли на Ctrl+Shift+C/V.
ВАЖНО: Ctrl+V теперь перехватывается терминалом, поэтому visual-block в
nvim — через `Ctrl+Q` (штатный синоним Neovim для `Ctrl+V`).

**Файлы:** `wezterm.lua` (корень репо),
`Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1` (вне репо).

### Старт проекта через Alpha: пустой [No Name] вместо дерева

**Проблема.** При открытии нового проекта через Alpha → «Open folder path»
(первый раз для репо, сессии ещё нет) после `:restart` открывался пустой
`[No Name]` буфер, а дерево файлов было закрыто. Сама Alpha как заглушка
отсутствия файла — ок, не трогаем; нужно лишь показывать дерево слева на
старте без сессии.

**Причина.** `open_path_prompt` звал `open_project(path, { open_files = false })`
→ после рестарта шёл `open_code_only_layout()`, который делает `enew`
(вот и `[No Name]`) и дерево не открывает. А `open_files_layout` до этого
сам подменял Alpha через `close_start_buffer()`/`enew`.

**Решение.**
1. `open_path_prompt` теперь зовёт `open_project(path)` (open_files=true) —
   вход в проект идёт по «files»-ветке.
2. `open_files_layout` больше НЕ делает `close_start_buffer()`/`enew`: Alpha
   остаётся в главном окне как заглушка, а слева открывается дерево
   (`ide.show("explorer")`).

Примечание: старт через `nvim <папка>` уже открывал дерево отдельной
VimEnter-автокомандой в `neo-tree.lua`; при рестарте без аргумента-файла она
не срабатывает, поэтому дерево открывает именно `open_files_layout`.

**Файлы:** `lua/config/start.lua`.

### WezTerm: окно не перетаскивается

**Проблема.** Окно WezTerm не за что ухватиться — не двигается.

**Причина.** `window_decorations = "RESIZE"` убирает заголовок окна (остаются
только рамки ресайза), поэтому таскать не за что.

**Решение.** `window_decorations = "TITLE | RESIZE"` — нативный заголовок (с
перетаскиванием и кнопками свернуть/развернуть/закрыть) + рамки ресайза.

**Файлы:** `wezterm.lua` (корень репо).

### Автопары не подставляли скобки в файле с ошибкой парсинга

**Проблема.** Если файл «не проходит линтинг» (есть синтаксическая ошибка),
закрывающая скобка перестаёт подставляться автоматически.

**Причина.** У `nvim-autopairs` стоял `check_ts = true` — пара решается через
запрос ноды treesitter. Когда файл не парсится, дерево в состоянии ERROR,
запрос ноды у курсора срывается, и autopairs не вставляет закрывающий
символ.

**Решение.** `check_ts = false` — пары работают по текстовым правилам
всегда, независимо от состояния парсинга. Минус: `"` может добавиться и
внутри строки, но это предсказуемее, чем «скобки молча отвалились».

Примечание про «авто-саджест вариантов ломался»: когда файл не парсится,
LSP (rust-analyzer/gopls) сам отдаёт меньше completion-вариантов — это
ограничение языкового сервера на «сломанном» коде, в конфиге не лечится.

**Файлы:** `lua/plugins/editor.lua`.

### Не все ошибки подсвечиваются в "сломанном" коде (undeclared / no-field)

**Проблема.** При сломанном коде подсвечиваются не все проблемы; хотелось
видеть необъявленные переменные и обращения к несуществующим полям структур.

**Решение / разбор.**
- Rust: включены экспериментальные нативные диагностики rust-analyzer
  (`diagnostics.experimental.enable = true`) — они ловят больше type-ошибок
  «на лету» (необъявленные имена, несуществующие поля/методы) ДО cargo check.
  Полные rustc-ошибки (E0425 undeclared, E0609 no field) приходят от
  `cargo clippy` на **save** (`checkOnSave = true` уже стоял).
- Go: gopls репортит «undeclared name» и «type has no field X» нативно как
  core type-ошибки — отдельный флаг не нужен.
- Врождённое ограничение (не лечится конфигом): type-проверка требует, чтобы
  код вокруг **парсился**. Если есть синтаксическая ошибка (незакрытая скобка
  и т.п.), парсер не строит AST в этом месте, и ни ra, ни gopls не могут там
  проверить типы.
- `update_in_insert = false` (perf): новые ошибки появляются при выходе из
  insert / save, а не на каждый набранный символ.

**Файлы:** `lua/plugins/lsp.lua`.

### 11. Go: нет автоимпорта недостающего пакета при наборе `strings.`

**Проблема.** Набираешь `strings.` или `strings.Filter` — completion НЕ
ищет символ по неимпортированным пакетам и не предлагает добавить import.
Хочется VS Code-поведение: поставил точку после имени пакета — найди его и
подставь импорт.

не было вообще.

неимпортированным пакетам и accept сам добавляет import. На коллизиях gopls
показывает ВСЕ кандидаты отдельными пунктами с полным путём пакета в
`[LSP]`-detail — выбираешь руками, ничего не угадывается молча. Старый путь
«добавить импорт к уже написанному имени» (`<leader>la` / `<leader>lO`)
остаётся. Добавлен `importShortcut = "Both"`.

### 12. Фриз при форматировании / генерации текста ошибки

**Проблема.** Редактор подвисал (именно фриз) при форматировании файла и
при появлении подсветки ошибки — особенно по ходу набора, когда линтер
видит проблему и «сдвигает строки», чтобы показать пояснение. Требование:
редактор НЕ блокируется ни в каком случае, текст пояснения подъезжает по
готовности, при необходимости — кэшируется.

**Причина (две независимые).**
1. **Формат.** `format_on_save` — синхронный хук на `BufWritePre`, а
   gofumpt/golines/rustfmt/prettier — внешние процессы. `auto-save.nvim`
   пишет каждые 500мс по ходу набора, и на КАЖДУЮ такую запись редактор
   синхронно ждал форматтер. Раньше autosave-байпас был только для Rust —
   остальные языки фризили каждые полсекунды.
2. **Текст диагностики.** `M.format` (перенос сообщения) звался на каждую
   диагностику при каждом показе virtual_lines, а `setup_refresh` ещё и
   передёргивал show на каждый `WinEnter` (смена фокуса окна) — лишний
   пересчёт без изменения ширины.

**Решение.**
1. Форматируем ТОЛЬКО на явном `:w` / `Ctrl+S` (когда
   `vim.g.user_auto_save_active = false`). Фоновые autosave-записи больше
   не форматируются вообще — блокировка стала одноразовой и ожидаемой
   вместо «каждые 500мс». LSP-диагностики и rust-analyzer
   checkOnSave/clippy на autosave продолжают работать (autocmd'ы записи не
   трогаем).
2. Кэш переноса текста по `(сообщение → результат)` для текущей ширины окна
   (сбрасывается при смене ширины) — «генерация текста» считается один раз.
   Из `setup_refresh` убран `WinEnter` (оставлены только реальные ресайзы),
   плюс дебаунс 60мс на серию ресайз-событий.

**Файлы:** `lua/plugins/format.lua`, `lua/config/diagnostics.lua`.

### 13. Ошибки не подсвечены, пока курсор не на строке

**Проблема.** Проблемная строка визуально не отмечена, пока не наведёшь на
неё курсор. Хотелось: не рисовать всю простыню текста сразу, а просто
внятно подчеркнуть/подсветить место ошибки везде.

**Причина.** Метка проблемы была только прямой `underline` (catppuccin
native_lsp), который в терминале почти не виден; единственным заметным
индикатором оставался inline-текст virtual_lines текущей строки — а он
по определению только под курсором.

**Решение.** `DiagnosticUnderlineError/Warn/Info/Hint` переопределены на
жирную волнистую (`undercurl`) с цветом по severity (`sp`): красный/жёлтый/
голубой/бирюзовый. Теперь каждое проблемное место подчёркнуто сразу и на
всех строках, не дожидаясь курсора. Inline-пояснение остаётся ленивым
(virtual_lines текущей строки) — «простыню» не рисуем. `update_in_insert`
остаётся `false` (ошибки обновляются на выходе из insert/save, не на каждый
символ).

### 17. WezTerm: Ctrl+C/V не работают на русской раскладке

**Проблема.** Хоткеи не должны зависеть от раскладки. На ЙЦУКЕН Ctrl+C не
копировал и (важнее) не слал SIGINT.

**Причина.** Биндинги ловились по СИМВОЛУ (`key = "c"`). На русской
раскладке физическая «C» печатает «с» (кириллица) → wezterm не узнаёт
биндинг → ни копирования, ни прерывания.

**Решение.** Привязки переведены на ФИЗИЧЕСКУЮ позицию клавиши:
`key = "phys:C"` / `"phys:V"` — ловятся на любой раскладке. В ветке «нет
выделения» smart_copy шлёт в pane чистый `Ctrl+C`, который conpty
превращает в `0x03` → SIGINT. Прочие Ctrl+<буква> уходят в nvim, где
раскладку разруливает `config/ru_keys.lua` (langmap + алиасы).

**Файлы:** `wezterm.lua` (корень репо).

### 18. WezTerm: русский файл выводится кракозябрами

**Проблема.** `cat файл.md` с русским показывал «РёРЅР±РѕРєСЃ».

**Причина.** Это UTF-8-байты, прочитанные как cp1251. Windows PowerShell
5.1 (его поднимает wezterm, т.к. pwsh 7 в PATH нет) по умолчанию и ЧИТАЕТ
файлы в ANSI/cp1251, и держит консоль не в UTF-8. WezTerm рисует UTF-8 —
рассинхрон даёт кракозябры.

**Решение.** В `$PROFILE` (вне репо) выставили UTF-8 на всех стыках:
`[Console]::OutputEncoding/InputEncoding` и `$OutputEncoding` = UTF-8
(без BOM), и `$PSDefaultParameterValues['Get-Content:Encoding']='utf8'`
(главное для симптома — `cat` теперь читает UTF-8). Set-Content/Out-File
тоже на utf8 (в 5.1 это, увы, UTF-8 С BOM). Радикально и без BOM — переход
на pwsh 7 (`winget install Microsoft.PowerShell`), где UTF-8 родной.
Проверено: `Get-Content -Encoding Default` → кракозябры,
`-Encoding utf8` → корректный русский.

**Файлы:** `Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1`
(вне репо).

### 19. (вопрос) Как wezterm-конфиг из репо синхронизируется с системой

**Вопрос.** Конфиг wezterm лежит в репозитории — как он попадает в систему,
как синхронизировать?

**Ответ.** Синхронизировать НЕ НАДО: система уже читает файл из репо
напрямую. Это сделано переменной окружения `WEZTERM_CONFIG_FILE`
(User-level), сейчас = `F:\repo\forge-nvim\wezterm.lua` (проверено). WezTerm
на старте читает именно её. Значит:
- правишь `wezterm.lua` в репо → это и есть системный конфиг;
- применить без перезапуска: в WezTerm `Ctrl+Shift+R` (Reload) или меню;
- проверить путь: `$env:WEZTERM_CONFIG_FILE` в PowerShell.

Альтернатива (если не хочется env-переменной) — симлинк
`%USERPROFILE%\.wezterm.lua` → файл в репо:
`New-Item -ItemType SymbolicLink -Path $HOME\.wezterm.lua -Target F:\repo\forge-nvim\wezterm.lua`.
Но env-вариант уже работает и предпочтителен (см. шапку `wezterm.lua`).

**Файлы:** — (конфигурация окружения, не код).

### 20. Подсветка всех совпадений ПРЯМО во время набора поиска

**Проблема.** Хотелось, чтобы при наборе `/foo` все вхождения
подсвечивались сразу по ходу печати (как find-box в VS Code), а не только
после Enter.

**Разбор.** Это нативно: при `incsearch=true` + `hlsearch=true` Neovim
подсвечивает ВСЕ совпадения по всему файлу уже во время набора паттерна
(`:h 'incsearch'` — «When 'hlsearch' is on, all matched strings are
highlighted too while typing»). Оба флага стояли, но эффекта не было,
потому что на `/` и `?` висел `cmp.setup.cmdline` — popup автодополнения
nvim-cmp перехватывал строку поиска и ломал живую перерисовку incsearch
(плюс закрывал совпадения собой). Цвет Search до этого тоже был блёклый
(поправлено в §14).

**Решение.** Сняли cmp с поиска (`/`, `?`) — на `:` он остаётся. Теперь
incsearch рисует чисто: по ходу набора текущее совпадение — персиковое
(IncSearch), остальные по всему файлу — жёлтые (Search). Плагин не нужен,
это нативное поведение. Счётчик `[3/12]` Neovim и так показывает в
cmdline (флаг `S` в shortmess не выставлен).

**Файлы:** `lua/plugins/completion.lua` (+ цвета Search в
`lua/config/options.lua`, см. §14).

### 21. Счётчик совпадений поиска (nvim-hlslens)

**Проблема.** К живой подсветке всех совпадений (§20) захотелось ещё
«лупу» — счётчик `[3/12]` прямо у совпадений, чтобы видеть номер текущего
и общее число, не считая глазами.

**Причина.** Нативный incsearch+hlsearch красит совпадения, но цифр у них
не рисует (счётчик есть только в командной строке `[3/12]`, и то мелкий).

**Решение.** Добавили `kevinhwang91/nvim-hlslens`. Он рендерит виртуальный
текст `[n/total]` у каждого совпадения и отдельно у текущего под курсором,
ПОВЕРХ нативной подсветки (её не ломает — дополняет цифрами). Ключевое:
`enable_incsearch = true` — счётчик появляется уже ВО ВРЕМЯ набора `/foo`,
до Enter. Грузим на `BufReadPost`/`BufNewFile`, чтобы CmdlineChanged-хук
incsearch был зарегистрирован до первого поиска. `nearest_float_when =
"never"` — только инлайновый virt-text без плавающего окна (оно перекрывало
бы текст при наборе). `calm_down = false` — подсветка и счётчик держатся до
`:noh`. Перевесили `n`/`N`/`*`/`#`/`g*`/`g#` на запуск `hlslens.start()`,
чтобы счётчик обновлялся при навигации (под русской раскладкой работает
через langmap, как j/k). Цвета лупы — в `set_matchparen_hl()`
(`HlSearchLensNear` персиковый в тон CurSearch, `HlSearchLens` приглушённый
на surface), переживают смену темы через ColorScheme-autocmd.

**Файлы:** `lua/plugins/search.lua` (spec + setup + маппинги),
`lua/config/options.lua` (`HlSearchLens*` в `set_matchparen_hl`),
`lazy-lock.json`.

### 22. Обычный файл открывается в нижней/боковой панели и «прилипает» к ней

**Проблема.** В нижней панели вместо того, что там должно быть (debug-
консоль, терминал, вывод задач), открылся обычный файл. И с тех пор КАЖДУЮ
сессию там файл вместо панели. Нижняя и боковые панели должны быть строго
для своих инструментов — давать туда класть файл нельзя.

**Причина.** Панели у нас — это edgy edgebar'ы; edgy ловит свои окна по
`filetype`. Когда фокус в нижней панели (DAP terminal/REPL, Overseer,
Trouble, quickfix) и делаешь `gd`/`gf`/`<C-]>`/`:e`/клик по пути — Neovim
заменяет буфер ПРЯМО в этом окне. Как только в окне оказался файл
(ft=lua/go/…), edgy перестаёт считать окно частью edgebar'а и «забывает»
его — окно осиротевает в позиции панели с файлом внутри. Хуже:
persistence.nvim сохраняет этот сломанный layout в сессию (`localoptions`
в `sessionoptions` тащит и `winfixheight`), и файл восстанавливается в
панели на каждый старт. `prepare_session_save` чистил панели по filetype —
а у просочившегося файла ft обычный, под фильтр не попадал.

**Решение (v1, неполное).** Завели страж `forge/panel_guard.lua`: на
`BufWinEnter` переносить файл из panel-окна в main, детектя панель по
`edgy.get_win()` ИЛИ `winfix`. Не помогло — см. диагностику ниже.

**Что показала диагностика** (`:luafile _paneldiag.lua` на живой сломанной
сессии). Layout после restore: `row[ neo-tree(edgy), col[ W1000, W1001 ] ]`,
где W1000 — настоящий main с `main.go`, W1001 — залипший horizontal-strip
снизу с ТЕМ ЖЕ `main.go`. КЛЮЧЕВОЕ: `winfix=true` стоял НЕ только на залипшем
окне, а и на НАСТОЯЩЕМ main (оба `wfh=true wfw=true`, оба `edgy=false`).
winfix «протёк» с панели на соседние editor-окна и сохранился в сессию через
`localoptions`. Из-за этого `find_main_window` считал ОБА окна панелью →
main не находился → relocate отменялся (v1 молча ничего не делал).

**Решение (v2, рабочее).** Сменили сигнал. НОРМАЛЬНОЕ editor-окно (не edgy,
не float, обычный буфер) winfix НЕ имеет — этот конфиг его на редактор не
ставит, только edgy на свои окна. Значит **editor-окно с winfix = след
протёкшей панели**. `sweep()` теперь: (1) проходами схлопывает winfix-порченые
editor-окна к одному main (приоритет — оставить чистое окно без winfix; если
все порченые — оставляем крупнейшее), относя файл в main и закрывая лишние
окна (буферы остаются в списке, не теряются); (2) финально СНИМАЕТ winfix со
всех editor-окон, чтобы порча больше не попала в сессию. Идемпотентно: на
здоровом layout и на легитимном сплите двух разных файлов (без winfix) —
no-op (проверено: такой сплit остаётся нетронут). `sweep()` зовётся на
`PersistenceLoadPost`, `VimEnter` и в начале `prepare_session_save`; живой
`BufWinEnter`-страж остаётся для gd-из-панели. Добавлена ручная команда
`:ForgePanelHeal`. Проверено: layout «два winfix-окна с файлом» → `sweep()`
сводит к одному чистому editor-окну.

**Файлы:** `lua/forge/panel_guard.lua` (новый), `init.lua` (вызов
`setup()`), `lua/config/panels.lua` (`sweep()` в `prepare_session_save`).

### 23. Единый контроллер панелей: маркировка + триггеры + toggle

**Проблема/запрос.** Нужно: (а) «маркировать» панели; (б) свободный toggle
панелей on/off; (в) авто-toggle-on по триггерам (старт дебага и т.п.);
статичный набор механизмов как в VS Code. И вопрос: строгая ли у нас

**Разбор.** Панелями рулили ДВА параллельных контроллера: чистый фреймворк

контроллеру `ide/` и на чистой базе доделать фичи.

### 24. Подсветка ошибок терялась — ни подчёркивания, ни цвета (ревизия §13)

**Проблема.** Ошибки в коде не видны: ни подчёркивания, ни цвета. §13 (undercurl
+ `sp`) на практике не сработал.

**Причина (по диагностике).** Три вещи сложились: (1) `TERM=xterm-256color` —
этот terminfo НЕ умеет undercurl и цветное подчёркивание (нет `Smulx`/`Setulc`),
поэтому `undercurl`+`sp` в коде не рисовали НИЧЕГО; (2) `vim.g.have_nerd_font =
false` — значки диагностик в gutter были nerd-глифами, рендерились пустотой/тофу;
(3) `virtual_text=false` — инлайн-цвета сообщения тоже нет. Итог: на строках без
курсора ошибка невидима (а сообщение и так только под курсором, virtual_lines
current).

**Решение (надёжно, без зависимости от undercurl).**
- `DiagnosticUnderlineError/Warn` теперь `underline=true` + `sp` + **`bg`**
  (приглушённая заливка токена). `bg` рисуется ВСЕГДА при `termguicolors` — это
  гарантированный «красный маркер ошибки» в коде, как в VS Code; прямое
  подчёркивание тоже рисуется в любом терминале. Info/Hint — только подчёркивание
  (без шума). Цветная линия — бонусом там, где терминал умеет (WezTerm c
  `TERM=wezterm`).
- Значки в gutter: ASCII-фоллбэк `E/W/I/H` когда нет nerd-шрифта — красятся в цвет
  severity (`DiagnosticSign*`) и видны в любом шрифте.
- Сообщение под курсором (`virtual_lines` current) — без изменений.

Проверено headless: `DiagnosticUnderlineError` = `{underline=true, bg=#4a2f3a,
sp=#f38ba8}`, значок `ERROR='E'`, `DiagnosticSignError.fg=#f38ba8`.

Для «как в норме» (волнистая цветная + иконки): поставить nerd-шрифт и
`vim.g.have_nerd_font=true`, терминалу выставить `TERM=wezterm` (WezTerm умеет
undercurl) — тогда можно вернуть `undercurl`. Хочешь ещё инлайн-сообщение на
каждой строке (truncated, цветное) — включается одним блоком `virtual_text`.

**Файлы:** `lua/config/options.lua` (`set_matchparen_hl` → `DiagnosticUnderline*`),
`lua/plugins/lsp.lua` (`apply_diagnostic_config` → ASCII signs).

### 25. Как закрывать info/popup-окна (ConformInfo и подобные)

**Вопрос.** Непонятно, как закрывать окна вроде `:ConformInfo`. Закрытие буфера
(`<leader>bd`) работает, но иногда что-то ломается в layout'е.

**Разбор.** `:ConformInfo` — это ПЛАВАЮЩЕЕ окно (scratch, `bufhidden=wipe`), и в
нём conform сам мапит `q` → `:close` (`conform/health.lua`). Большинство
info/popup-окон (help, Lazy, Mason, Trouble, hover) тоже закрываются по `q`.
`<leader>bd` тут не подходит: он УДАЛЯЕТ редактируемый буфер — для tool/панельных
буферов это дёргает edgy/panel_guard и layout «плывёт». Закрывать надо ОКНО, а
не буфер.

**Решение.**
- `q` — закрыть info-окно (теперь единообразно: добавлен buffer-local `q`=`:close`
  для ft без него — `checkhealth`, `lspinfo`, `conform-info`, `qf`, `fugitiveblame`
  и т.п.; edgy-панели не трогаем — у них свои toggle'ы).
- `<F4>` (а также `Alt+q` / `Alt+w`) — универсальное «закрыть текущий контекст»:
  теперь ПЕРВЫМ делом закрывает любое плавающее окно, затем Diffview/Neotree/
  tool-окно, и только для файла — умное закрытие буфера. Floats не влияют на
  layout, так что это всегда безопасно.

Проверено headless: float `conform-info` → `q` замаплен; `ForgeCloseContext`
(`<F4>`) закрывает float (2 окна → 1).

**Файлы:** `lua/config/keymaps.lua` (`smart_close_current_context` + FileType
autocmd `ForgeQuitInfoWindows`).

### 26. Форматтер «падал» на нормальных файлах (lua/json/yaml/md)

**Проблема.** На обычном файле форматтер не работал; `:ConformInfo` показывал
`prettier`/`prettierd` `unavailable: Command not found`.

**Причина (диагностика по факту на диске).** Два конкурирующих механизма
установки тулз — «на костылях»:
- `mason-tool-installer` ЗАЯВЛЯЛ `stylua`/`gofumpt`/`goimports`, но реально их
  НЕ ставил: в `mason/packages` лежали только 5 LSP-серверов (их ставит
  `mason-lspconfig`). То есть tool-installer фактически не отрабатывал.
- `stylua` нигде в системе тоже не было → conform по `lua` молча сваливался в
  один `trim_whitespace` (Lua-файлы — основной язык этого конфига — реально не
  форматировались).
- `gofumpt`/`golines` работали лишь «по случайности» — они оказались в
  системном PATH (`go install`), а не из Mason.
- `prettier`/`prettierd` не были объявлены в Mason вообще → json/yaml/md без
  реального форматирования (только trim).
- Шапка `format.lua` при этом врала: «тулзы ставятся СИСТЕМНО, не через
  mason-tool-installer» — хотя `stylua`/`gofumpt` лежали именно в mason-списке.

**Решение (единый механизм — системная установка, по выбору юзера).**

- Шапка `format.lua` переписана: один источник правды (системная установка),
  без противоречия.

Проверено headless: `conform.get_formatter_info` → `stylua`/`prettier`/`gofumpt`/
`golines` = available; `list_formatters_to_run` для lua = `stylua,…`, для
json/yaml/md = `prettier`. Boot чист (0 ошибок).

Примечание (отдельный латентный баг, НЕ форматтеры): `mason-tool-installer`
не ставит и свои оставшиеся пакеты (`delve`/`debugpy`/`golangci-lint`) — их в

**Файлы:** `lua/plugins/format.lua` (шапка), `lua/plugins/lsp.lua`

### 27. Фризы при наборе кода / навигации (опять) → формат асинхронный

**Проблема.** Редактор СНОВА подвисал по ходу написания кода (например, когда
правишь ошибку и жмёшь `Ctrl+S`). Жёсткое требование: фризов не должно быть
НИ В КАКОМ виде. Форматтер пусть «тормозит» в фоне, но не набор. Autosave нужен,
но он не должен тормозить движение по файлу и печать; линтер — в фоне.

**Причина.** §12 пропускал формат на autosave, но `format_on_save` так и
остался СИНХРОННЫМ хуком на `BufWritePre` с `timeout_ms = 1000`. То есть на
КАЖДОМ явном `:w`/`Ctrl+S` (а его жмут рефлекторно по ходу правки) главный
цикл редактора блокировался до 1 секунды, пока отрабатывал внешний форматтер.
Любая дырка в autosave-гейте — и тот же синхронный формат прилетал прямо во
время набора.

**Решение (формат уведён с пути ввода полностью).**
- `format_on_save` → `format_after_save` (АСИНХРОННЫЙ): conform запускает
  форматтер уже ПОСЛЕ записи (на `BufWritePost`) и применяет дифф отдельной
  записью. Главный цикл не ждёт форматтер ни на `:w`, ни тем более на autosave.
  Гейт `vim.g.user_auto_save_active` сохранён (autosave не форматит вообще).
- Autosave оставлен как есть (персист + фоновые диагностики). На autosave-пути
  больше НЕТ ни одной синхронной внешней операции.
- Линтер уже в фоне: `rust-analyzer checkOnSave=clippy` крутится в ОТДЕЛЬНОМ
  процессе `cargo` и шлёт диагностики асинхронно — nvim его не ждёт. Живые
  type-ошибки идут от `didChange`, тоже асинхронно.

Проверено headless: после загрузки conform на `BufWritePre` — 0 хуков conform
(нет синхронного формата), на `BufWritePost` — 1 хук (асинхронный формат);
`opts.format_on_save = nil`, `opts.format_after_save = function`. Boot чист.

**Файлы:** `lua/plugins/format.lua` (`format_after_save`), `lua/plugins/editor.lua`
(шапка auto-save), `lua/plugins/lsp.lua` (комментарий `checkOnSave`).

### 28. Слишком широкая колонка номеров строк

**Проблема.** Под нумерацию строк уходил «жирный кусок» пустого места —
заметно шире, чем нужно файлу, в котором строк немного.

**Причина.** `statuscolumn` был `"%s%C %4{v:lnum} %=%3{v:relnum} "`:
фиксированные ширины `%4` (абсолютный номер) и `%3` (относительный) +
разделитель `%=`, который РАСТЯГИВАЕТ колонку, расталкивая два номера к
краям. В итоге даже на 50-строчном файле резервировалось ~7 знаков под
цифры плюс растяжка — отсюда «толщина».

**Решение.** Колонка собирается функцией `_G.forge_statuscolumn()`, ширина
считается от РЕАЛЬНОГО числа строк буфера (`line("$")`, минимум 2 цифры).
Обе колонки (абсолютная + относительная) стоят впритык через один пробел,
без растягивающего `%=`. На коротком файле колонка ужимается до 2+2 цифр,
на большом — растёт ровно настолько, насколько нужно. Знаки/фолды (`%s%C`)
и подсветка `CursorLineNr` сохранены; на wrap-строках номер не дублируется
(`v:virtnum ~= 0 → ""`). Проверено headless: функция определена, зовётся,
`opt.statuscolumn` выставлен, boot чист.

**Файлы:** `lua/config/options.lua` (`forge_statuscolumn` + `statuscolumn`).

fg). Boot чист.

### 31. Ctrl+[ — outdent (сдвиг строки влево)

**Проблема.** Ctrl+[ для сдвига влево не работал (вправо Ctrl+] — ок).

**Причина.** Физически Ctrl+[ == Esc (0x1b); nvim их не различает, поэтому
`<C-[>` намеренно не маппился — иначе сломал бы выход из режимов.

самой клавише Esc и `<Esc><Esc>`. Visual-маппинг через `xm` (только visual, НЕ
select) — чтобы `<F13>` не перехватывался на плейсхолдере сниппета и не мешал
§30. В терминалах без wezterm-правила Ctrl+[ так и работает как Esc.

### 33. Go: ошибка `++`/`--` видна «только при запуске»

**Проблема.** Неверное использование `++`/`--` (в Go это операторы-СТЕЙТМЕНТЫ,

**Файлы:** см. §36 (`lua/plugins/lsp.lua`).

### 34. Форматирование «молча не форматирует»

**Проблема.** Формат не применялся к файлу с кривой раскладкой (`continue`/
скобка), и молча — непонятно почему.

**Причина.** В примере была СИНТАКСИЧЕСКАЯ ошибка (`left, right == left++,
right--` — невалидный Go). gofmt/gofumpt/golines (и rustfmt) отказываются
форматировать непарсящийся код и выходят с ошибкой, а conform делал это тихо.
Плюс `:Format` числился в `cmd` lazy, но самой команды не существовало.

**Решение.** Создали `:Format` — СИНХРОННЫЙ, показывает stderr форматтера
(ровно «проверить на месте»: запусти на битом go-файле — увидишь, где сломано).
Ручной формат `<S-A-f>`/`<leader>lf` теперь тоже показывает ошибку (callback +
`quiet=true`, чтобы не было ДВОЙНОГО popup'а — это поймал ревью). Подсказку
«почини синтаксис» добавляем только для runtime-ошибок форматтера, не для
«нет форматтера»/timeout (иначе вводит в заблуждение). На авто-формат при
сохранении оставлен `notify_on_error`.

**Файлы:** `lua/plugins/format.lua`.

### 35. Go: какая версия активна + переключение (как в VS Code)

**Проблема.** Снизу видно только filetype «go», а версия Go/toolchain —
непонятно; нужно переключать (был конфликт go1.24 vs требуемой 1.25).

**Решение.** В статуслайне (lualine_x, только на go-буферах) — `Go x.y.z`
(звёздочка = принудительный GOTOOLCHAIN-оверрайд). `:GoVersion` — показать
версию + GOTOOLCHAIN. `:GoToolchain [go1.25.0|auto|local]` (или picker без
аргумента) — ставит `vim.env.GOTOOLCHAIN` и перезапускает gopls; нужная
toolchain скачается сама (Go 1.21+). Версия определяется асинхронно
(`vim.system`, timeout 15с — ввод не блокирует).

Проверено headless: `label()` → «Go 1.23.3»; `:GoVersion/:GoToolchain` есть.

**Файлы:** `lua/forge/go.lua` (новый), `lua/plugins/lsp.lua` (команды),
`lua/plugins/ui.lua` (статуслайн).

### 36. Линтер/диагностика «тихо ломается» + рестарт

**Проблема.** gopls-диагностика переставала работать молча — помогал только
перезапуск nvim. Хочется ЗНАТЬ о поломке и уметь перезапустить точечно.

**Решение.** `on_exit` на всех LSP-конфигах: если сервер УПАЛ (ненулевой код/
сигнал, и это не наш рестарт и не выход из nvim) → WARN с подсказкой
«перезапусти <leader>lR». `<leader>lR` — рестарт LSP на текущем буфере:
форс-стоп (`c:stop(true)` — сервер мог зависнуть) + ре-attach через
`FileType`-autocmd на ВСЕХ задетых буферах. Тем же надёжным путём перезапускают
`:LspRestart` и `:GoToolchain`.

Ревью поймал: прежний `:edit` падал E37 на ИЗМЕНЁННОМ буфере (и оставлял буфер
вообще без LSP) и ре-attach'ил лишь текущий буфер — заменено на FileType.

Проверено headless: lua_ls после `stop(true)`+`FileType` ре-attach'ится;
ложной crash-нотификации при нашем рестарте нет.

**Файлы:** `lua/plugins/lsp.lua`, `lua/forge/go.lua`.

### 37. DAP: нижняя панель не открывалась на F5 (Go), молча

**Проблема.** Иногда при F5 (current go file) нижняя дебаг-панель просто не
открывалась, без объяснений.

**Причина.** Фильтр «безобидных» warning'ов глушил ЛЮБОЙ ненулевой выход delve —
включая ПАДЕНИЕ НА СТАРТЕ (ошибка сборки/пути). Сессия не инициализировалась →
панель не поднималась → и причины не видно. (delve у юзера есть в `~/go/bin`,
так что дело было не в нём.)

**Решение.** Выход delve глушим ТОЛЬКО при штатном завершении (после
`event_initialized`); падение ДО инициализации показываем («Delve не смог
запустить… см. :DapShowLog»), без дубля с «Error on launch». Плюс watchdog: если
через 800мс нижняя секция не появилась, а сессия жива — открываем ещё раз
(страховка от edgy-гонки), с привязкой к КОНКРЕТНОЙ сессии.

Ревью поймал критичный тайминг: сброс флага «инициализирована» надо вешать на
`before.initialize`, а НЕ `before.launch` — nvim-dap зовёт `before.<cmd>` на
ОТВЕТ запроса, а delve шлёт событие `initialized` ДО ответа на `launch`. С
`before.launch` флаг занулялся бы уже ПОСЛЕ инициализации, и каждое штатное
завершение (delve выходит ненулевым кодом) орало бы ложной ошибкой.

**Файлы:** `lua/plugins/dap.lua`.
