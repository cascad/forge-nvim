# Proposal

## Why

Режим WINDOWS задуман как модальный слой «как режимы в vim» (`wezterm.lua:405-413`, FIXLOG 2026-08-01). Сверка базовой линии показала, что модальный он только наполовину, а правило «всё, что открывает запрос или экран, сперва выходит из режима» нарушено. Решения владельца: №1 — клавиши без команды в режиме проглатываются; №2 — `o` переводит фокус на следующую панель; всё, что в режиме открывает запрос или экран, сначала выключает режим (WT-WIN-19). 2026-09-27 владелец ответил на два вопроса, от которых зависели delta: RESIZE подчиняется тем же правилам, что WINDOWS, а сочетания терминала работают в режимах одинаково на Windows и macOS через копии в таблицах режимов (подробности и отклонённые варианты — design.md, Decisions).

- **WT-WIN-4, решение №1 (divergence 48).** Клавиши без команды уходят в программу. Воспроизведение: в панели с pwsh нажать Ctrl+Shift+Space, затем `i`, `g`, `y`, `t` — буквы печатаются в шелле, бейдж WINDOWS горит; в nvim та же `i` включает вставку. Где: `wezterm.lua:700-702`, `ActivateKeyTable{ name = "windows" }` без `prevent_fallback`.
- **WT-WIN-6, решение №2 (divergence 49).** `o` переставляет панели (`RotatePanes("Clockwise")`, `wezterm.lua:637`), а не переводит фокус. Воспроизведение: две панели A|B, фокус в A, Ctrl+Shift+Space, `o` — панели меняются местами, фокус остаётся на левой позиции.
- **WT-WIN-7, баг (divergence 50).** `q` открывает выбор панели, не выключая режим (`wezterm.lua:638`). Метки a, s, d, f, h, j, k, l — это команды режима, поэтому, например, `s` делит панель, а не выбирает вторую. Esc на Windows закрывает экран выбора, а на macOS выключает режим, и экран остаётся. Воспроизведение: две панели, Ctrl+Shift+Space, `q`, `s`. Выведено из исходника 20240203 (`keyevent.rs`: привязки таблицы окна сопоставляются в raw-проходе раньше, чем экран выбора получает клавишу).
- **WT-WIN-10, баг (divergence 51).** `x` открывает запрос «Really kill this pane?», не выключая режим (`wezterm.lua:643`). Режим перехватывает `n` (следующая вкладка) и Esc/Enter (выход из режима при открытом запросе). При решении №1 режим проглотил бы и `y`, и запрос нельзя было бы подтвердить с клавиатуры. Выведено из исходника 20240203.
- **WT-WIN-19, баг (divergence 52).** Правило из `wezterm.lua:565-568` и FIXLOG не выполнено для `q` и `x`: оба экрана открываются при включённом режиме.
- **WT-WIN-11, решение владельца 2026-09-27 (вопрос 1).** Подрежим RESIZE, как и WINDOWS, пропускает клавиши без команды в программу: `wezterm.lua:648-651`, `ActivateKeyTable{ name = "resize_pane" }` без `prevent_fallback`. Воспроизведение: Ctrl+Shift+Space, `r`, затем `i` — буква печатается в шелле, бейдж RESIZE горит.
- **WT-WIN-11, дрейф комментария (divergence 60).** `wezterm.lua:646-647` обещает «один Esc = выход из любого модального слоя». Это неверно: Esc снимает только верхний слой (RESIZE → обычный ввод, но WINDOWS поверх RESIZE → снова RESIZE).
- **Нюанс WezTerm 20240203** (`wezterm-gui/src/termwindow/keyevent.rs`, `KeyTableState::lookup_key`, `raw_key_event_impl`, `key_event_impl`). `prevent_fallback` подставляет Nop только во втором, «приготовленном» проходе. Привязки `config.keys` на `phys:` сопоставляются ещё в первом, raw-проходе и продолжат работать в режиме. Привязки на именованных клавишах (Ctrl+Tab, Ctrl+Shift+Enter, Ctrl+Shift+стрелки, Ctrl+Shift+PageUp/PageDown, Shift+PageUp/PageDown, Ctrl/Shift+Insert) на Windows будут проглатываться, а на macOS часть из них сработает в raw-проходе. Одна строка `prevent_fallback = true` даёт разное поведение на двух ОС. Кроме того, экраны, которые открывают глобальные сочетания при включённом режиме (Ctrl+Shift+W, Ctrl+Shift+U, Ctrl+Shift+X, Cmd+Q), делят клавиши с таблицей режима (WT-WIN-21), а при решении №1 не получали бы клавиш вовсе.

## What Changes

- Режимы WINDOWS и RESIZE проглатывают клавиши и сочетания без команды: до программы они не доходят, режим остаётся включённым, таймаут от них заново не отсчитывается (WT-WIN-4, WT-WIN-11; следствия в WT-WIN-2, WT-WIN-3, WT-WIN-20).
- Сочетания терминала вне режимов (WT-KEYS-3) работают в обоих режимах так же, как без них, одинаково на Windows и macOS. Их копии попадают в таблицы режимов из того же списка, что `config.keys`, поэтому каждое такое сочетание продлевает режим на 5 секунд, как команда режима (WT-WIN-3). Команда режима важнее сочетания с той же клавишей: Ctrl+Shift+Space в WINDOWS по-прежнему выключает режим.
- Сочетания, которые открывают экран поверх панели, при включённом режиме сперва выключают его: Ctrl+Shift+W, Ctrl+Shift+U, Ctrl+Shift+X, на macOS Cmd+Q.
- `o` переводит фокус на следующую панель по кругу и не переставляет панели; зум снимается, как у h/j/k/l (WT-WIN-6, требование переименовывается).
- `q` и `x` сначала выключают режим, затем открывают экран выбора панели или запрос подтверждения (WT-WIN-7, WT-WIN-10). В WT-WIN-19 они переходят в группу «выходят»; правило проверяется в `tests/`.
- «Выключить режим до действия» значит выключить все слои режима в окне: если WINDOWS включён поверх RESIZE, команда из группы «выходят» и сочетание, открывающее экран, выключают оба (WT-WIN-19). Иначе RESIZE, который теперь проглатывает клавиши, остался бы под запросом и съедал бы ввод. Esc, Enter и Ctrl+Shift+Space по-прежнему снимают только верхний слой (WT-WIN-11); комментарий «один Esc = выход из любого модального слоя» (`wezterm.lua:646-647`) исправляется.
- WT-WIN-21 переписывается: режим больше не остаётся включённым поверх экрана, который открыт из режима. Для случая, когда режим включают по Ctrl+Shift+Space поверх уже открытого экрана, задан порядок: клавиши copy mode и search mode важнее команд режима, команды режима и сочетания терминала выполняются, остальное проглатывается. Исключение, которое конфиг обойти не может, — экраны выбора панели, выбора символа и палитра команд: WezTerm отдаёт им клавиши раньше таблиц режима.
- Соседние требования, в которых описано взаимодействие с режимом: WT-PANE-4 (запрос закрытия при включённом режиме) и WT-UI-12 (сценарий «Copy mode поверх режима WINDOWS»).
- Не меняется: вкладочные команды `c`, `n`, `p`, `1…9` оставляют режим включённым (WT-WIN-13, WT-WIN-19); WINDOWS по Ctrl+Shift+Space из RESIZE ложится поверх RESIZE (WT-WIN-11); выключение режимов при смене шрифта и перечитывании конфига (WT-WIN-2, вопрос OQ7 в `review-baseline`); бейдж COPY/SEARCH поверх WINDOWS (WT-UI-12); ограничение русской раскладки на экранах WezTerm, которые сравнивают символ (метки выбора панели, y/n в запросе).
- В `tests/` появляются проверки таблиц режимов по `wezterm show-keys`. Документация режима WINDOWS в `docs/WEZTERM.md` правится под новое поведение, в `nvim_forge/FIXLOG.md` дописывается запись со строками `Спека:`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `wezterm-windows-mode`: WT-WIN-4 (клавиши без команды проглатываются, сочетания терминала работают и продлевают режим), WT-WIN-6 (`o` — следующая панель; RENAMED), WT-WIN-7 и WT-WIN-10 (`q`, `x` сперва выходят), WT-WIN-19 (состав групп, сочетания, открывающие экран, выход из обоих слоёв), WT-WIN-21 (режим и экраны), WT-WIN-2 и WT-WIN-3 (модифицированный Enter, продление таймаута сочетаниями терминала), WT-WIN-20 (клавиши без команды не доходят до программы при любом протоколе), WT-WIN-11 (RESIZE по тем же правилам).
- `wezterm-panes-tabs`: WT-PANE-4, сценарий о запросе при включённом режиме WINDOWS и новый сценарий «Ctrl+Shift+W в режиме».
- `wezterm-ui`: WT-UI-12, сценарий «Copy mode поверх режима WINDOWS» (после Ctrl+Shift+X режим выключен, возврата к бейджу WINDOWS нет) и новый сценарий о режиме, включённом из copy mode.

`wezterm-key-ownership` не меняется: набор перехватов вне режимов (WT-KEYS-3), привязка букв, цифр и знаков по физической позиции при именованных Enter, Tab, Esc и стрелках (WT-KEYS-2) и одна запись на пару в каждой таблице (WT-KEYS-8) остаются в силе. Вариант с переводом именованных клавиш на `phys:` владелец отклонил (design.md, Decisions).

## Impact

- `wezterm.lua`:
  - `prevent_fallback` у входа в WINDOWS (Ctrl+Shift+Space) и в RESIZE (`r`);
  - помощник `map()` получает четвёртый аргумент `opts` с пометкой «открывает экран» у Ctrl+Shift+W, Ctrl+Shift+U, Ctrl+Shift+X и Cmd+Q;
  - после последней записи в `config.keys` — копирование сочетаний терминала в таблицы `windows` и `resize_pane`;
  - в таблице `windows`: `o` → следующая панель, `q` и `x` выходят из режима, вся группа «выходят» выключает все слои режима;
  - комментарии `wezterm.lua:405-413`, `562-569`, `646-647`.
- `tests/`: сценарии в `tests/wezterm-keys.scenarios.sh` по настоящему разбору конфига (`show-keys --lua`) для Windows и для вида macOS. Проверяются `prevent_fallback` у обоих входов, состав групп «остаются / выходят», `o` → `ActivatePaneDirection("Next")`, покрытие сочетаний терминала таблицами режимов и выход из режима у каждого сочетания, открывающего экран. Если к моменту применения есть проверки из `add-wezterm-spec-checks`, их проверки WT-WIN и эталоны правятся в том же коммите.
- Документы: раздел режима WINDOWS в `docs/WEZTERM.md` (его же переписывает `sync-docs-with-baseline`), `nvim_forge/FIXLOG.md`.
- Соседние changes:
  - `resolve-key-ownership-conflicts` может изменить состав WT-KEYS-3; копии в таблицах режимов подхватят это сами;
  - `change-search-enter-accept` не пересекается по поведению (WT-SCROLL-10), но делит файл `tests/wezterm-keys.scenarios.sh`: кто применяется вторым, тот дополняет файл;
  - `sync-docs-with-baseline` оставил этому change исправление комментария WT-WIN-11 (divergence 60);
  - `restructure-wezterm-config` идёт после; задуманная там сигнатура `map(key, mods, action, opts)` совпадает с этой;
  - `add-wezterm-spec-checks`: эталоны `show-keys` меняются осознанно (`--update-golden`).
- Ручная проверка в GUI на Windows и macOS: всё выведенное из исходника (экраны выбора и запросы после выхода из режима, режим поверх уже открытых экранов, сочетания на именованных клавишах). Отпускание проглоченной клавиши, которое WezTerm всё равно передаёт программе в win32-input-mode, проверяется на ConPTY-стенде без GUI.
