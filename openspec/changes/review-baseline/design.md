# Design

## Context

Мотивация — в proposal.md (Why).

**Состояние.** В `openspec/specs/` 10 capability и 128 требований. Их сняли с рабочего дерева 2026-09-27, затем пять верификаторов сверили их с кодом, документами и исходником WezTerm 20240203. Итог сверки сохранён в `baseline_divergences.json` рядом с этим файлом:

- 71 divergence: 23 code-bug, 18 doc-drift, 18 comment-drift, 9 untestable-claim, 3 owner-decision;
- 59 открытых вопросов.

Баги, решения владельца и дрейф текстов разобраны по своим changes. Этому change остаются:

- untestable-claim (divergences 28–34, 46, 47);
- непроверенные пункты из открытых вопросов;
- семь вопросов владельцу, которые ни один change не разбирает;
- противоречие WT-WIN-16 ↔ WT-SCROLL-9.

**Ограничения.**

- Mac удалённый: проверять на нём может только владелец. Версия WezTerm на Mac неизвестна (divergence 47).

- OpenSpec 1.13.2 при архивации MODIFIED-delta заменяет требование целиком тем текстом, который записан в delta.

## Goals / Non-Goals

**Goals:**

- Каждое утверждение базовой линии из чек-листов проверено на своей платформе. Если результат расходится со спекой, спека исправлена под код до перехода.
- Ручную проверку можно повторить. У пункта есть шаги, ожидаемое по спеке и отметка. Результаты дописываются, прежние не стираются.
- У каждой divergence и каждого вопроса сверки по capability есть дом до её подтверждения: открытый change, задача этого change или пункт `PROBLEMS.md`.
- Переход в фазу 2 — одна точка в истории: один коммит, который откатывается одним `git revert`.

**Non-Goals:**

- Менять поведение. Всё, что владелец решит изменить, уходит в отдельные changes.
- Править docs, README и комментарии в коде — это `sync-docs-with-baseline`.
- Проверять установщик на Mac (заглушка git без CLT, cask шрифта, разбор plist) — это `fix-macos-installer`.
- Проверять исправления других changes. Здесь фиксируется только текущее поведение; новое поведение проверяют задачи самих changes.
- Проверять Linux. Машины с GUI нет, а linux-утверждения по `config.yaml` остаются «по возможности».
- Автоматизировать проверки: CI, pre-commit, поддельный модуль `wezterm`, перенос пробы ConPTY в `tests/`. Это отдельные changes: `add-wezterm-spec-checks` (раннер и trace; чек-листы этого change он только читает, формат пунктов — решение 3) и `resolve-key-ownership-conflicts` (тест пересечения клавиш).
- Писать спеки nvim_forge.

## Decisions

**1. Проверка — в фазе 1, переход — последним шагом.** Всё, что может исправить базовую линию, делается, пока действует правило «спека не совпала с кодом — чинится спека». Строка фазы меняется только после этого. После перехода любое расхождение уже считается багом кода.
- Альтернатива: перейти сразу, а ошибки спеки чинить потом как «баги спеки». Отклонено. В фазе 2 агент по правилу чинит код под спеку, и непроверенный вывод из исходника начнёт ломать работающий код.

**2. Переход ждёт прогона на Mac.** `config.yaml` ставит переход «после проверки владельцем», а macOS-утверждения — самые слабые места базовой линии: все они выведены из исходника, и версия WezTerm на Mac неизвестна.
- Альтернатива: перейти после прогона на Windows и оставить macOS-пункты помеченными. Отклонено: именно на Mac ошибочный вывод дороже всего, потому что на месте его не проверить.
- Цена: фаза 2 откладывается до доступа к Mac. Changes в это время живут как обычно: их delta одинаково работают в обеих фазах.

**3. Чек-листы — в `tests/manual/wezterm-windows.md` и `tests/manual/wezterm-macos.md`, по платформам.** Владелец проходит их, сидя за одной машиной, поэтому группировка по платформе. Внутри файла пункты сгруппированы по capability.
- Пункт содержит: код (W1…, M1…), ID требований, источник (divergence или вопрос), шаги, ожидаемое словами спеки и название сценария, для какого change результат служит воспроизведением.
- Результат дописывается строкой: `Проверено: <дата>, <ОС и версия>, WezTerm <версия>, раскладка <…> — совпало | расходится: <что видно>`. Прежние строки не правятся, последняя строка — текущий статус.
- Так выполняется правило 5 `CLAUDE.md`: доказательство лежит в `tests/`. В фазе 2 пункты остаются регрессионными чек-листами для любых changes.
- Альтернатива: результаты в FIXLOG. Отклонено: FIXLOG — журнал инцидентов, и три десятка отметок его засорят.
- Альтернатива: результаты в папке change. Отклонено: после архивации их никто не найдёт.
- Альтернатива: файл на capability. Отклонено: за одной машиной пришлось бы открывать 10 файлов.

**4. Состав чек-листов. Платформо-независимое проверяется на Windows, на Mac — только платформенные пути.** Таблицы клавиш, PaneSelect, запросы и оверлеи — общий код WezTerm, его достаточно проверить на доступной машине. На Mac остаются IME, kitty, Cmd, окружение launchd, симлинк, шрифты и то, что по исходнику ведёт себя иначе, чем на Windows.

Пункт сверяется с текстом требования в `openspec/specs/` на момент прогона. Если требование уже поменял заархивированный change, сверка идёт с новым текстом.

**5. Разошлось — правится спека, и только она.** Результат «расходится» значит, что базовая линия описала код неверно. По правилу фазы 1 текст требования правится под наблюдаемое поведение, а пометки «выведено из исходника» и «не проверено» у проверенного убираются. Если владелец при этом хочет поведение иначе, это отдельный `/opsx:propose`: спека до его архивации описывает то, что есть.
- Противоречие WT-WIN-16 ↔ WT-SCROLL-9 решается так же, в пользу кода: `f` открывает search mode с шаблоном и типом, сохранёнными для вкладки, а в вкладке, где ещё не искали, — с пустым шаблоном без учёта регистра.

**6. В проверенных требованиях — строка `Проверка: вручную (tests/manual/wezterm-<ос>.md, <пункт>)`.** Этого требует формат из `config.yaml` («когда способ проверки известен»). В фазе 2 агент, читающий требование, сразу видит, как оно проверяется.
- Альтернатива: связь только в одну сторону, от чек-листа к ID, через grep. Отклонено: расходится с форматом требований.

**7. Правки базовой линии переносятся в открытые delta.** При архивации MODIFIED заменяет требование целиком, поэтому правка из решений 5 и 6 пропадёт, если тот же ID меняет открытый change.
- Для каждого исправленного ID запускается `grep -rln "Requirement: <ID> " openspec/changes/*/specs`.
- Найденная delta получает ту же правку через `/opsx:update <change>`.
- Это единственный случай, когда задача этого change трогает чужую папку. Делается штатной командой, не правкой руками. Проверяет ли это сам OpenSpec 1.13.2 при архивации — не уверен, поэтому считаем, что нет.

**8. Подтверждение capability — по критериям, а не «прочитал».** Владелец отмечает задачу capability в группе 5, когда выполнено всё:
- (а) спека прочитана целиком (`openspec show <capability> --type spec`);
- (б) у всех ручных пунктов этой capability из таблицы Context есть результат, а расхождения исправлены (решение 5);
- (в) у каждой divergence этой capability есть дом: `grep -rln "<ID>" openspec/changes/*/proposal.md` находит change; дрейф docs и комментариев — `sync-docs-with-baseline`;
- (г) вопросы OQ по этой capability решены;
- (д) всё, что владелец хочет иначе, заведено через `/opsx:propose`, а не правкой спеки.

Отметка в tasks.md и перечень в записи FIXLOG — это и есть запись о подтверждении. После архивации change она остаётся в `openspec/changes/archive/`.

**9. Решения по Open Questions записываются в этот design.md.** Запись идёт через `/opsx:update review-baseline`: у вопроса появляется строка «Решение владельца (<дата>): вариант …, change <id> | без изменений». Итог повторяется в записи FIXLOG. При «оставить» спека не меняется: её текст уже описывает это поведение, в фазе 2 он становится намерением. При «менять» заводится change, и до его архивации спека описывает то, что есть.

**10. Переход — одним коммитом из трёх правок.**
- `openspec/config.yaml`: абзац о фазе заменяется на «ТЕКУЩАЯ ФАЗА: 2 «источник правды» (с <дата>). Фаза 1 «базовая линия» — с 2026-09-27 по <дата>, проверка — change review-baseline.» Описание обеих фаз ниже остаётся: правило фазы 1 понадобится для будущих capability, например спек nvim_forge.
- `CLAUDE.md`: пункт «Сейчас — фаза 1» становится «Сейчас — фаза 2 (с <дата>)», фаза 1 описывается в прошедшем времени.
- `nvim_forge/FIXLOG.md`: новая нумерованная запись. В ней: подтверждённые capability, уточнённые ID, решения OQ, ссылки на чек-листы и пометки «не проверено», оставшиеся в спеках, с причиной. Строки `Спека:` нет, потому что поведение не меняется.
- Альтернатива: разнести правки по коммитам. Отклонено: промежуточное состояние (config в фазе 2, `CLAUDE.md` в фазе 1) даёт агентам противоречивые правила.

**11. Отчёт сверки хранится в папке change.** `baseline_divergences.json` скопирован из временного каталога без изменений (sha256 совпадает). На его номера ссылаются proposal всех changes. После архивации файл остаётся в `openspec/changes/archive/<дата>-review-baseline/`.
- Альтернатива: оставить во временном каталоге. Отклонено: `%TEMP%` может очистить Storage Sense или сам владелец, и тогда номера divergences во всех changes повиснут.

## Risks / Trade-offs

- [Доступ к Mac откладывается] → Фаза 2 ждёт (решение 2). Если ждать станет неприемлемо, владелец меняет решение 2 через `/opsx:update review-baseline`. Непроверенные M-пункты тогда перечисляются в записи FIXLOG, а их требования получают пометку «на Mac не проверено».
- [На Mac не WezTerm 20240203] → Версия фиксируется в M0 и в каждой строке результата. Расхождение, которое объясняется версией, не правится в спеке молча. Владельцу задаётся вопрос о целевой версии (`config.yaml`, «Целевые версии»): обновить Mac до целевой или сменить целевую версию.
- [Пункты по поведению, которое меняет открытый change (W1, W9, W10, W13, M6, M12)] → Пункт фиксирует текущее поведение и служит воспроизведением. Если change заархивирован до прогона, сверка идёт с новым текстом (решение 4). Проверку нового поведения делают задачи самого change, здесь она не дублируется.
- [Правка базовой линии пропадёт при архивации чужой MODIFIED-delta] → Решение 7 и задача 3.4.
- [Подтверждение 128 требований превращается в формальность] → Критерии решения 8 и карта сверки в Context показывают, где смотреть внимательно: требования с divergences и непроверенными пунктами.
- [Ручная проверка не повторяется у другого человека или позже] → Пункт содержит точные шаги и ожидаемое словами спеки, результат — версию и раскладку. Повтор дописывает строку, историю видно.
- [Строки `Проверка:` удлиняют требования] → Одна строка на требование, по формату `config.yaml`.

## Migration Plan

1. Группы 1–5 tasks выполняются в фазе 1. Порядок:
   - группа 3 — после прогонов (группы 1 и 2);
   - задачи группы 4 — после своих ручных пунктов (они указаны в задачах);
   - задача capability в группе 5 — после групп 3 и 4 по этой capability.
2. Переход (группа 6) — одним коммитом (решение 10). Перед ним `openspec validate --all --strict` должен проходить.
3. Архивация: `openspec archive review-baseline`. Из-за `skip_specs: true` спеки не сливаются, папка переезжает в `archive/` вместе с отчётом сверки.
4. Откат: `git revert` коммита перехода возвращает фазу 1. Код от фазы не зависит, уточнения базовой линии остаются верными в обеих фазах.

## Open Questions

Все семь вопросов можно решить позже: задачи этого change от ответов не зависят. Каждый ответ — это либо «оставить», и спека не меняется, либо новый change. Решение записывается по решению 9.

**OQ1. Готовый лэйаут `a` не идемпотентен** (WT-PANE-9, сценарий «Повторный вызов»; WT-WIN-12). Повторный вызов снова делит текущую панель, и в вкладке становится пять панелей.
- (а, рекомендуется) Оставить. Команда означает «разложить текущую панель». `a` выключает режим, поэтому случайный повтор требует снова войти в режим. Лишние панели закрываются `x`. Спека это уже описывает.
- (б) Если во вкладке больше одной панели, не делить и показать уведомление. Уходит и сценарий «Делится только текущая панель» — change `change-ready-layout-idempotent`.
- (в) Распознавать собранный лэйаут по геометрии. Не рекомендуется: эвристика ломается после ресайза и зума.

**OQ2. Невидимое окно при повторном запуске из другого воркспейса** (WT-PANE-10, сценарий «Повторный запуск WezTerm из другого воркспейса»; проверяется в W14).
- (а, рекомендуется при редком использовании воркспейсов) Оставить и описать в docs. Для проблемы нужны одновременно не-default воркспейс и повторный запуск; окно не теряется, оно в default.
- (б, если воркспейсы нужны каждый день) Открывать окно повторного запуска в активном воркспейсе — change `fix-relaunch-workspace-window`. Механизм неясен. В 20240203 `default_workspace` задаётся при вычислении конфига, а активный воркспейс известен только в обработчиках событий. Есть ли чистый путь — не уверен, нужно исследование.
- (в) Переключать весь GUI на default. Не рекомендуется: уводит все окна с активного воркспейса.

**OQ3. Cmd+Q всегда спрашивает подтверждение** (WT-PANE-8, сценарий «Cmd+Q всегда спрашивает»; проверяется в M8). Причина — `window_close_confirmation` по умолчанию.
- (а, рекомендуется) Оставить. Лишний `y` стоит дешевле потери всех панелей, а Cmd+Q стоит рядом с Cmd+W и Cmd+A.
- (б) Не спрашивать никогда (`window_close_confirmation = "NeverPrompt"`). Это меняет и закрытие окна кнопкой — change `change-quit-confirmation`.
- (в) Спрашивать, только если работает что-то кроме шелла, как у Ctrl+Shift+W (WT-PANE-4). Штатной настройки для выхода в 20240203 не видно, понадобится своя привязка Cmd+Q с обходом панелей. Это собственный код ради редкого случая.
- Отдельно: подтверждение на русской раскладке только кликом — это общий вопрос «экраны WezTerm сравнивают набранный символ», он сюда не входит.

**OQ4. Выгрузка `b`: пустые строки и файл на диске** (WT-SCROLL-13, сценарий «Пустые строки выпадают» и абзац о файле). Если оба ответа «оставить», change не нужен. Иначе — change `fix-scrollback-dump`. В него же уходит M7, если проверка подтвердит, что WezTerm.app из Dock не находит `nvim`.
- Пустые строки:
  - (а, рекомендуется) Сохранять. Выгрузка нужна, чтобы читать вывод и искать в нём. Слипшиеся абзацы теряют структуру: сливаются трассы стека и границы команд. Каким API читать строки панели без потери пустых, решает change; проверить по исходнику 20240203.
  - (б) Оставить.
- Файл `~/.wezterm_scrollback.txt`:
  - (а) Оставить: один файл, он перезаписывается.
  - (б, рекомендуется) Удалять при выходе из nvim (автокоманда в команде запуска). Файл переживает только аварийный выход, и он по-прежнему один.
  - (в) Уникальный временный файл на каждый вызов. Не рекомендуется: файлы копятся без предела.

**OQ5. QuickSelect ищет в 1000 строках истории** (WT-SCROLL-12). Он раздаёт невидимые метки фрагментам за краем экрана и может сам прокрутить вид.
- (а) Оставить: так ведёт себя WezTerm по умолчанию.
- (б, рекомендуется) Искать только на видимом экране: `scope_lines = 0` в аргументах QuickSelect (поле есть в 20240203). Метки только у того, что видно; уехавшее вверх ищется через copy mode и поиск. Change `change-quickselect-scope`. При реализации проверить, что без `patterns` остаются штатные шаблоны.
- (в) Узкое окно, например один экран над видимым.
- Метки на русской раскладке — общий вопрос «экраны WezTerm сравнивают набранный символ», он сюда не входит.

**OQ6. На Windows конфиг перечитывается при изменении любого файла в корне репо** (WT-LOAD-14, сценарий «Windows — наблюдается весь каталог файла»; проверяется в W17, на Mac связан с M11). Решать после W17.

Меняются сценарии автоперечитывания WT-LOAD-14 на всех ОС — change `change-config-autoreload`.
