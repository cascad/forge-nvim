# Design

## Context

Мотивация описана в proposal.md, раздел Why. Подход определяют такие ограничения.

- Сейчас горячие клавиши записаны в трёх местах: в коде `wezterm.lua`, в его комментариях и в `docs/WEZTERM.md`. Синхронизируются они вручную, и никакая проверка за этим не следит. Переход LEADER → режим WINDOWS (FIXLOG 2026-08-01) обновил только код: в «Файлах» той записи указан один `wezterm.lua`.
- Теперь есть спеки `openspec/specs/wezterm-*` и `macos-install` со стабильными ID. Идёт фаза 1: спеки описывают код как есть, а docs производны от кода. В фазе 2 docs станут производными от спек. Если описывать через спеки, текст не придётся переписывать при смене фазы.
- Параллельно готовятся changes, которые меняют поведение тех же мест:
  - `fix-windows-mode-modality`: режим WINDOWS (решения владельца 1 и 2, `x` и оверлеи выходят из режима);
  - `change-search-enter-accept`: Enter в search mode (решение 3);
  - `fix-window-state-new-windows`: размер новых окон (FIXLOG §32);
  - `resolve-key-ownership-conflicts`: Super-шрифт на Windows и клавиши WT-KBD-6;
  - `fix-copy-clobbers-clipboard`: `y` в copy mode;
  - `fix-ui-robustness`: WT-UI (шрифт, шелл, статус-бар; рядом комментарии, которые правит группа 3);
  - `fix-macos-installer` и `add-linux-installer-parity`: установщики.

  После применения каждый из них правит свои разделы docs. В их задачах разделы `docs/WEZTERM.md` названы по старым номерам (§5, §8, §9–§10).
- Проверить можно только Windows: `wezterm show-keys`, `ls-fonts`, GUI. На Mac проверять на месте нельзя. Как ведёт себя macOS, известно только из спек, а там это частью выведено из исходника 20240203.
- В `wezterm.lua` 318 строк комментариев из 786. В части из них перечислены факты, которые теперь принадлежат спеке (списки клавиш, поведение платформ), и некоторые из этих перечислений уже неверны.

## Goals / Non-Goals

**Goals:**
- `docs/WEZTERM.md` описывает то, что делает код на момент применения, и по ID в разделах видно, какое требование описывает каждый раздел.
- Комментарии `wezterm.lua` не противоречат коду и спекам. Перечисления, которые дублируют спеку, заменены ссылкой на ID.
- Документация nvim_forge не обещает на Windows сочетаний, которые там не доходят, и верно описывает установщики.
- Неточности в старых записях FIXLOG отмечены новой записью, сами записи не переписываются.

**Non-Goals:**
- Изменения поведения, даже если расхождение нашлось рядом. Каждое идёт своим change с delta: семантика режима WINDOWS (WT-WIN-4, WT-WIN-6, WT-WIN-10, WT-WIN-21), Enter и Esc в search mode (WT-SCROLL-10, WT-SCROLL-11), пустые строки при выгрузке (WT-SCROLL-13), область и раскладка меток QuickSelect (WT-SCROLL-12), Super-сочетания шрифта на Windows (WT-KEYS-3), доставка Ctrl+Shift+буквы, Ctrl+., Ctrl+Space и других клавиш на Windows (WT-KBD-6), `animation_fps` (WT-UI-9), бейдж у оверлеев (WT-UI-12), режим установки в `~/.config/nvim` (MAC-INST-10).
- Правка `openspec/specs/**`. Уточнения базовой линии относятся к change `review-baseline`.
- Комментарии установщиков (divergences 13–15) и комментарий RESIZE (divergence 60, WT-WIN-11). Они в своих changes.
- Прочая уборка комментариев, которой нет среди divergences этого change: история правок у `window_decorations`, строковое `"PopKeyTable"`, сломанные отступы в `resize_pane`. Это задача будущего рефакторинга `wezterm.lua`.
- Генератор или автоматическая проверка docs. Они относятся к change с тестами (см. решение 4).
- Слияние перекрывающихся `HOTKEYS.md` и `KEYBINDINGS.md`, статусы `docs/PANELS_PLAN*.md`, документация nvim_forge сверх оговорок WT-KBD-6.

## Decisions

### 1. `docs/WEZTERM.md` остаётся руководством по задачам и не копирует спеки

Документ отвечает на вопрос «как сделать X», а спека — на вопрос «что обязано происходить». Структура документа:

0. Где лежит конфиг и как понять, что он загружен (WT-LOAD-1, -3, -4, -13, -15).
1. Принципы: физические позиции клавиш и где раскладка всё же важна: метки QuickSelect, `q`, y/n в запросах WezTerm (WT-KEYS-1, WT-KEYS-2, WT-SCROLL-12, WT-WIN-7, WT-PANE-4).
2. Режим WINDOWS: вход, выход, таймаут, клавиши без команды, таблица команд с колонкой «режим остаётся / выключается», RESIZE, бейджи (WT-WIN-1…21, WT-UI-12…15).
3. Панели без режима (WT-PANE-1…4, -9, -12, -13).
4. Вкладки и окна (WT-PANE-5…8, -11, WT-KEYS-5).
5. Воркспейсы (WT-PANE-10, WT-UI-13).
6. История: прокрутка, очистка, copy mode, search mode (WT-SCROLL-1…11, -15).
7. QuickSelect (WT-SCROLL-12).
8. Выгрузка истории в nvim (WT-SCROLL-13).
9. Буфер обмена (WT-CLIP-*).
10. Окно и шрифт (WT-STATE-*).
11. Различия Windows и macOS (WT-KBD-1…5, WT-CLIP-2/3/5, WT-PANE-8, WT-UI-1/2).
12. Что отдано nvim и что nvim на самом деле получает (WT-KEYS-4, WT-KEYS-6, WT-KEYS-7, WT-KBD-6, WT-KBD-7).
13. Альтернативный экран и OSC 52 (WT-SCROLL-14, WT-CLIP-11).

ID стоят в заголовке каждого раздела. В каждой таблице клавиш есть колонка «Спека», как в таблице WT-KEYS-3. В начале документа одна строка: нормативное описание — `openspec/specs/wezterm-*`, запланированные изменения — `openspec/changes/`.

Отвергнутые варианты:
- (а) Собрать документ из текстов спек. Спеки нормативные и подробные, в них все корнер-кейсы, а шпаргалке нужна краткость.
- (б) Удалить документ и ссылаться на спеки. Спеки разложены по capability, а не по задачам человека за клавиатурой, а CLAUDE.md определяет docs как руководства для человека.
- (в) Точечно поправить старые строки. Модель LEADER пронизывает §1–§8, и после точечных правок в документе остались бы две модели сразу.

### 2. Источник текста — код на момент применения, прочитанный через спеку

Фаза 1: спека равна коду, поэтому текст пишется по спеке и сверяется с `wezterm show-keys` на Windows. Если на момент применения спека и код расходятся (базовая линия ещё не уточнена), документ следует коду, а расхождение передаётся в `review-baseline`. Известные баги описываются как есть, без обещаний «будет исправлено». Разделы обновит change, который их исправит. Если к моменту применения какой-то change поведения уже применён, описывается уже новое поведение.

Отвергнутый вариант: описать намерение владельца (решения 1–4) заранее. Документ тогда соврал бы до применения этих changes, а это нарушает правило фазы 1.

### 3. Уровень детализации

Документ содержит то, что нужно для работы, и ловушки, на которые пользователь наткнётся:
- на русской раскладке метки QuickSelect не набрать;
- Esc в поиске закрывает и copy mode;
- пустые строки при выгрузке выпадают;
- H/L держат отступ в 5 строк;
- закрытие панели без вопроса, если в ней только шелл.

Исчерпывающие корнер-кейсы остаются в спеке, документ ссылается на неё по ID. Утверждения, которые в спеке помечены как выведенные из исходника и не проверенные на Mac, в документе не подаются как проверенные.

### 4. Таблицы клавиш пока пишутся руками. Генерация из `show-keys` отвергнута, будущая проверка отложена

Генерировать таблицы из `wezterm show-keys --lua` сейчас нельзя по четырём причинам:
- вывод недетерминирован: регистр phys-букв меняется от запуска к запуску;
- все `action_callback` выглядят одинаково непрозрачно, как `EmitEvent 'user-defined-N'`;
- в выводе нет описаний для человека;
- вывод снимается только на своей ОС, а Mac недоступен.

Поэтому таблицы пишутся руками в едином виде: сочетание, платформы, действие, «Спека». Этот вид годится для будущей машинной сверки: набор сочетаний в docs сравнивается с нормализованным снимком `show-keys` или с набором из тестового прогона конфига с поддельным модулем `wezterm` для обеих ОС. Проверка — не генератор. Она относится к change с тестами. Генерация становится разумной, только если привязки станут данными с описаниями (keymap как таблица, этап рефакторинга из аудита `wezterm.lua`). Какой из двух источников выбрать, записано в Open Questions. На этот change выбор не влияет.

### 5. Ограничения WT-KBD-6 описываются в одном месте, в документации nvim_forge на них ссылки

Полный список того, что nvim на Windows получает вместо задуманного, и альтернативы nvim_forge находятся в разделе 12 `docs/WEZTERM.md`. Альтернативы: `<leader>sF`, `<C-e>`/`<C-A-e>`, `:Telescope commands`, `<leader>dD`, `<leader>dr`, Alt+Enter / `<leader>.` / `<leader>la`. Для `<C-Space>`, `<C-/>` и F-клавиш с модификаторами альтернатива определяется по `:map` в nvim_forge при выполнении задачи; если её нет, так и пишется «альтернативы нет». В справочниках `HOTKEYS.md` и `KEYBINDINGS.md`, которые читают построчно, у каждой строки с затронутым сочетанием стоит пометка «Windows+WezTerm: не доходит (WT-KBD-6)» с альтернативой. В руководствах `QUICKSTART.md`, `PANELS.md` и `COOKBOOK.md`, которые читают подряд, одна оговорка в начале со ссылкой на раздел 12.

Отвергнутые варианты:
- Пометить каждое упоминание во всех пяти файлах, около 50 строк: шум и пятикратное дублирование.
- Не трогать документацию nvim_forge: читатель KEYBINDINGS.md так и не узнает, почему `<C-Space>` молчит.

### 6. Комментарии объясняют «почему» и ссылаются на ID, фактов спеки не перечисляют

Неверное утверждение исправляется или удаляется. Перечисление, которое принадлежит спеке, например «какие Ctrl+Shift заняты Neovim», заменяется ссылкой вида `(WT-KEYS-4)`. Обоснование, которое нужно читателю кода, остаётся: зачем `phys:`, зачем маска IME, почему kitty выключен на Windows. Ссылки пишутся обычным текстом в скобках. Машинный тег для проверки трассировки отложен (Open Questions), grep находит оба варианта.

### 7. Строка `text:gsub("%s+$", "\n")` удаляется

В WezTerm 20240203 (и в main, см. `openspec/config.yaml`) `get_lines_as_text` сам срезает хвостовые пробелы у всего текста. Шаблон ничего не находит, и файл выгрузки получается одинаковым с этой строкой и без неё. Комментарий к ней утверждал обратное и этим ввёл в заблуждение. Удаление поведения не меняет, это проверяется сравнением файла выгрузки до и после. Нужно ли сохранять пустые строки, решается отдельным change по WT-SCROLL-13.

Отвергнутый вариант: оставить строку как страховку для других версий WezTerm. Версия зафиксирована в `config.yaml`, а страховка для гипотетической версии — мёртвый код, который уже однажды ввёл в заблуждение.

### 8. FIXLOG: одна новая запись, старые не трогаются

Запись в формате «Проблема → Причина → Решение → Файлы». Проблема: документ и комментарии разошлись с кодом. Причина: записи 2026-08-01 и более ранние не обновили docs, и ничто это не проверяет. Решение:
- docs переписаны по спекам;
- комментарии исправлены;
- перечислены неточные утверждения §16 (полоса прокрутки, `min_content_width`), §17 («чистый» Ctrl+C → 0x03), 2026-05-31 п. 3 (имя шрифта) и 2026-08-01 («нет бейджа = NORMAL», неполный список файлов), и для каждого указан ID, где теперь верное описание.

Строки `Спека:` в записи нет, потому что поведение не менялось.

### 9. `nvim_forge/README.md` описывает установщик как есть

curl | bash на macOS клонирует в `~/forge-nvim` и ставит в локальном режиме, `~/.config/nvim` не трогает (MAC-INST-3). Установка в каталог конфига Neovim идёт только с `FORGE_NVIM_DEPS_ONLY=0`. Сегодня она удаётся только вместе с `FORGE_NVIM_USE_LOCAL_SOURCE=1`: клон по умолчанию останавливается на `No init.lua` (MAC-INST-10). Этот абзац перепишет change установщика, если MAC-INST-10 изменится. Язык файла, английский, сохраняется.

## Risks / Trade-offs

- [Change поведения применён раньше этого, и документ описывает уже старый код] → Перед началом `openspec list` и `git log -- wezterm.lua` показывают, что применено. Итоговые таблицы сверяются со свежим `show-keys` (решение 2).
- [Соседние changes ссылаются на старые номера разделов `docs/WEZTERM.md` (§5 строка `y`, §8, §9–§10), а после этого change номера другие] → Разделы ищутся по ID из заголовков: WT-SCROLL-7, WT-STATE-*, WT-KEYS-3/4, WT-KBD-6, WT-LOAD-*. Содержание, на которое они ссылаются (строка `y`, таблица шрифта, различия платформ, раздел «отдано nvim»), в новом документе сохраняется.
- [Change поведения, применённый позже, забудет про docs] → Правило tasks в `config.yaml` уже требует задачи на docs. ID в заголовках разделов показывают, какой раздел править. Автоматическая сверка появится с change тестов.
- [Утверждения о macOS нельзя проверить на месте] → Для macOS текст берётся из спек (таблица WT-KEYS-3, WT-KBD-2/3, WT-PANE-8). Выведенное из исходника в документе не подаётся как проверенное.
- [Конфликты в `wezterm.lua` с параллельными changes кода] → Правки комментариев — короткие локальные ханки. Они идут отдельным коммитом, и `git diff` должен показывать только строки комментариев и одну удалённую строку.
- [Удаление `gsub` изменит выгрузку на другой версии WezTerm] → Версия зафиксирована. Файл выгрузки сравнивается до и после на Windows.
- Компромисс: документ переписывается сейчас и ещё раз по частям, когда применяются changes поведения. Это принято осознанно. Каждая следующая правка локальна благодаря ID, а если ждать, документ ещё долго описывал бы несуществующий LEADER.
- Компромисс: таблицы, которые пишутся руками, могут снова разойтись с кодом, пока не появится проверка. Колонка «Спека» делает будущую проверку механической.

## Migration Plan

1. Желательно применить до changes, которые меняют поведение WezTerm и установщиков (см. Context). Если какой-то из них уже применён, см. решение 2.
2. Порядок внутри change: `docs/WEZTERM.md` → документация nvim_forge → комментарии `wezterm.lua` и запись FIXLOG. Каждая группа — отдельный коммит.
3. Откат — `git revert` соответствующего коммита. В `wezterm.lua` меняются только комментарии и строка без эффекта. После отката конфиг перечитывается (Ctrl+Shift+R), а `ls-fonts` подтверждает загрузку.
4. Если `review-baseline` уточнит спеки, разделы docs с изменёнными ID правятся в том же change.

## Open Questions

- Источник для будущей сверки или генерации таблиц клавиш: нормализованный снимок `wezterm show-keys --lua` для каждой ОС или keymap как данные после рефакторинга `wezterm.lua`. Этот change не зависит от выбора: таблицы в любом случае пишутся руками с колонкой «Спека».
- Формат ссылки на требование в коде: обычный текст `(WT-KEYS-4)` или машинный тег вида `[spec WT-KEYS-4]` для проверки трассировки. Решается вместе с проверкой, а переход между форматами — механическая замена.
- Нужен ли `config.animation_fps = 1` (WT-UI-9). Курсор от него не зависит, дискретность дают Constant-ease. Если убирать, это отдельный change поведения, а здесь исправляется только комментарий.
