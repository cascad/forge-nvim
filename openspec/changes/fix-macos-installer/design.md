# Design

## Context

Мотивация — proposal.md, раздел Why. Ограничения, которые определяют подход:

- `install-macos.sh` — один bash-скрипт. Он MUST работать под `/bin/bash` 3.2.57 и без утилит, которых нет в чистой macOS (MAC-INST-12). В чистой macOS `python3` — такая же заглушка CLT, как git, поэтому на него опираться нельзя.
- Проверка — `tests/install-macos.scenarios.sh`: песочница с HOME, `env -i` и заглушками `launchctl`, `wezterm`, `pgrep`. Сейчас все сценарии идут с `FORGE_NVIM_SKIP_DEPS=1`, так что шаги Homebrew, шрифта и тулчейнов не покрыты. Режим `~/.config/nvim` покрыт одним S11, и тот проверяет только, что шаг начался: `nvim` в песочнице нет. Прогон — WSL, bash 5.2 и собранный bash 3.2.57.
- Mac удалённый. Заглушку git без CLT, настоящий cask шрифта, `plutil` с двоичным plist и `nvim` через симлинк `~/.config/nvim` здесь проверить нельзя.
- OpenSpec 1.13.2 требует, чтобы MODIFIED сохранял имена всех прежних сценариев: имя сценария — неизменный якорь. Поэтому часть старых имён («присваивание, добавленное после блока, не нейтрализуется», «проверка текстовая», «повтор с исключениями», «источник по умолчанию — клон монорепо») осталась, а их тело описывает новое поведение.
- Режим установки в `~/.config/nvim` владелец решил 2026-09-27 (Decision 9). Для этого режима в `lazy.nvim` важно вот что (сверено по исходнику в локальном каталоге данных `nvim_forge`):
  - `Lazy sync` — это clean + install + update, `update` без lockfile двигает плагины к свежим версиям и затем переписывает `lazy-lock.json` (`lua/lazy/manage/init.lua`, `lua/lazy/manage/lock.lua`);
  - `Lazy restore` — это `update` с `lockfile = true`;
  - недостающие плагины при старте ставятся с `lockfile = true` (`lua/lazy/core/loader.lua`).

  `nvim_forge/lazy-lock.json` отслеживается git: `.gitignore` прямо говорит «коммитим, чтобы версии плагинов воспроизводились».

## Goals / Non-Goals

**Goals:**

- Исправить divergences 1–9, 13 и 14 так, чтобы повторный запуск ничего не переустанавливал и не давал ложных «сломано» и «перезапусти».
- Сделать режим `~/.config/nvim` той же конструкцией, что подключение `wezterm.lua`: симлинк в чекаут. Никакого своего состояния, которое может разъехаться.
- Каждое исправление закрыть сценарием в `tests/install-macos.scenarios.sh`, прогоном под bash 5.2 и 3.2.57. То, что песочница не покрывает, — ручным шагом на macOS с записью результата.
- Не добавлять зависимостей ни установщику, ни тестам.

**Non-Goals:**

- Режим `~/.config/nvim` в `install-linux.sh` (клон всего монорепо или копия) и в `install-windows.ps1`. Симлинк на Linux — follow-up change после `add-linux-installer-parity`, здесь не делается.
- Подсказка `Start with: nvim` при нестандартном `FORGE_NVIM_INSTALL_DIR`: такой конфиг `nvim` без `NVIM_APPNAME` не прочтёт. Подсказка остаётся прежней.
- Удаление и ротация старых бэкапов (MAC-INST-8, «бэкапы копятся»). Прежняя копия уходит в бэкап один раз и остаётся там.
- Автоопределение режима (MAC-INST-2) не меняется. Скрипт, запущенный через симлинк `~/.config/nvim`, раскрывается в чекаут и без флага выбирает локальный режим — это уже так в коде и ничего не ломает.
- Строка `launchctl setenv WEZTERM_CONFIG_FILE …` внутри профиля шелла (сценарий «что блок не отменяет» в WT-LOAD-7 остаётся как есть). Её распознавание — отдельный вопрос верификации.
- Соседние требования `wezterm-config-loading` с открытыми вопросами: `XDG_CONFIG_HOME` шелла против launchd (WT-LOAD-4), ложный провал `ls-fonts` на посторонних строках `ERROR` (WT-LOAD-11). Также `WezTerm.app` в `~/Applications` (MAC-INST-7).
- Документы вне установщика — change `sync-docs-with-baseline`.
- Перевод тестов на bats-core и CI с Mac-раннером — рекомендация research, отдельный change.

## Decisions

1. **Шрифт — проверка по каждому каталогу отдельно.** Маленькая функция проходит glob каждого каталога и проверяет `[ -e ]` у совпадений.
   - Альтернатива `ls A || ls B` работает, но держится на кодах возврата `ls` (у GNU и BSD они разные) и запускает процессы.
   - `compgen -G` — встроенная команда и в bash 3.2, но читается хуже.
   - Цикл по glob — самое прямое и одинаковое в bash 3.2 и 5.
2. **Rust установлен, если есть `cargo` в PATH или исполняемый `~/.cargo/bin/cargo`.** Во втором случае печатается подсказка в стиле `gopls`.
   - Отвергнуто: убрать `--no-modify-path` и дать rustup дописать профили. Установщик правит профили только помеченными блоками и только там, где без этого нельзя (MAC-INST-4, WT-LOAD-7).
3. **git без CLT — через `xcode-select -p`.** git считается недоступным, когда одновременно:
   - `command -v git` = `/usr/bin/git`;
   - команда `xcode-select` есть;
   - `xcode-select -p` завершается ошибкой.

   `xcode-select -p` ничего не запускает и диалога не показывает. Отвергнуто:
   - `git --version` — на заглушке вызывает тот самый системный диалог установки CLT;
   - `xcrun --find git` — зависит от того же каталога разработчика и шумит.

   В песочнице (WSL) `xcode-select` нет, поэтому `/usr/bin/git` считается настоящим, и сценарий S7 не меняется. Заглушка без CLT моделируется заглушкой `xcode-select` с ненулевым кодом (S19). Проверка одна на весь скрипт: её зовёт бутстрап, в том числе для файла вне чекаута (Decision 11). Установке конфига из чекаута git больше не нужен.
4. **Профили: смотреть только хвост после последнего `# <<< forge-nvim <<<`.** Хвост вырезается `awk` (есть в macOS), дальше та же проверка «упоминание вне комментария». Строка `unset` самого блока лежит до маркера конца и в хвост не попадает, поэтому повторные запуски сходятся: после дописанного блока хвост пуст.
   - Отвергнуто: переписывать старый блок на месте или считать упоминания против числа блоков. Первое нарушает append-only из FIXLOG §43, второе хрупко.
5. **LaunchAgent: разбирать команду plist, а не искать текст.**
   - plist приводится к XML: `plutil -convert xml1 -o - <plist>`. Без `plutil` (песочница) файл читается как есть.
   - Из `ProgramArguments` (и `Program`) вынимаются строки `<string>…</string>` с раскодировкой XML-сущностей.
   - Перекрытием считается `launchctl setenv WEZTERM_CONFIG_FILE <значение>`: подряд идущими аргументами или внутри одной строки для шелла (`sh -c`).
   - `~` и `$HOME` раскрываются только во втором случае — так их раскрыл бы и сам шелл. Потом `resolve_path` и сравнение с файлом репо.
   - Нарушители копятся в списке (строка через перевод строки — в bash 3.2 нет ассоциативных массивов), и каждый называется отдельной строкой.
   - Отвергнуто: `PlistBuddy` и `plutil -extract` — их нет в песочнице, да и версии `plutil` отличаются; `python3 plistlib` — на чистом маке это заглушка CLT.

   Сознательный выбор — ложный пропуск лучше ложного «сломано» (код 1). Текущий сеанс всё равно проверяет WT-LOAD-10.
6. **Подсказка о перезапуске: авторитетна переменная панели.**
   - Если в панели есть `WEZTERM_CONFIG_FILE`, решает только она.
   - Если нет (её снял блок WT-LOAD-7), WezTerm считается загрузившим файл репо, когда в репо ведёт любой из кандидатов: `$WEZTERM_CONFIG_DIR/wezterm.lua`, `$WEZTERM_CONFIG_DIR/.wezterm.lua` или launchd-`WEZTERM_CONFIG_FILE`, если её каталог равен `WEZTERM_CONFIG_DIR`.
   - Остаточный ложный случай (`--config-file` или переменная шелла с файлом под другим именем) записан сценарием в WT-LOAD-12.
   - Отвергнуто: спрашивать запущенный GUI через `wezterm cli` — путь конфига он не отдаёт.
7. **Шапка скрипта (divergences 13, 14).**
   - `brew shellenv` — «в профиль логин-шелла: `~/.bash_profile` для bash, иначе `${ZDOTDIR:-~}/.zprofile`».
   - Список флагов — все переменные, которые скрипт читает, с умолчаниями, включая `FORGE_NVIM_REPO`, `FORGE_NVIM_BRANCH` и `FORGE_NVIM_USE_LOCAL_SOURCE` в смысле Decision 11.
   - Пункт 3 «Что делает» описывает режим `~/.config/nvim` как симлинк на `<чекаут>/nvim_forge`.
   - Список сверяется со скриптом тестом S29: провал, если какую-то переменную `FORGE_NVIM_*` скрипт читает, а шапка её не называет. Так divergence 14 не вернётся молча.
8. **Тесты — заглушки с явной моделью.** Урок FIXLOG §43: каждая заглушка пишет в комментарии, какое поведение настоящей программы изображает и где это сверено.
   - `brew`: `list --formula|--cask --versions` читает `FAKE_BREW_INSTALLED`, `install` пишет вызовы в журнал, `shellenv` пуст.
   - `rustup-init` и `go` пишут журнал; `go env GOPATH` отдаёт каталог в HOME.
   - `xcode-select -p` возвращает `FAKE_XCODE_SELECT_RC`.
   - `plutil -convert xml1 -o - <файл>` печатает файл как есть. Модель: настоящий `plutil` отдаёт XML с тем же содержимым. Так ветка с `plutil` исполняется и в песочнице, а двоичный формат проверяется вручную на Mac.
   - `nvim` пишет в журнал аргументы и значения `NVIM_APPNAME` и `XDG_CONFIG_HOME` и возвращает `FAKE_NVIM_RC`. Лежит в отдельном каталоге, который `run` добавляет в PATH только по запросу: сценарию «нет nvim» нужен PATH без него. В `/usr/bin` и `/bin` WSL-песочницы `nvim` нет — так было и в пробе P2.
   - Сценарии шагов зависимостей запускаются без `FORGE_NVIM_SKIP_DEPS`: отдельный хелпер рядом с `run`.
   - План номеров:
     - S17 шрифт, S18 Rust, S19 git без CLT, S20 профиль после блока, S21 варианты plist (вдобавок к S13), S22 панель с `~/.wezterm.lua`;
     - S23 первая установка в `~/.config/nvim` и повтор без бэкапа, S24 занятые пути (каталог, файл, битый симлинк, симлинк на другой чекаут, `FORGE_NVIM_NO_BACKUP=1`), S25 отказы до первого бэкапа, S26 терминал nvim_forge, S27 файл вне чекаута → бутстрап, S28 клон монорепо в `~/.config/nvim`;
     - S29 шапка называет все флаги (Decision 7).
   - S11 переписывается под симлинк. Сейчас он проверяет только строку `Installing forge-nvim` при коде 1 из-за отсутствия `nvim`.
   - Фикстура S13 сейчас — две строки `<string>` без `launchctl setenv`. После Decision 5 она перестанет считаться перекрытием, поэтому её надо переписать в настоящий plist LaunchAgent с `ProgramArguments` = `launchctl setenv WEZTERM_CONFIG_FILE /elsewhere.lua`. Иначе S13 упадёт по правильной причине.
9. **Решение владельца 2026-09-27: режим установки в `~/.config/nvim` — симлинк `<путь установки>` → `<чекаут>/nvim_forge` (Q12 = B).** Чекаут — тот, из которого запущен скрипт, или клон в `FORGE_NVIM_SRC`, как у `wezterm.lua` (WT-LOAD-4).
   - Идемпотентность по построению: состояние режима — только «путь ведёт в `<чекаут>/nvim_forge`». Сравнивать нечего, копии, которая могла бы разъехаться, нет, а `git pull` в чекауте обновляет и рабочий конфиг.
   - Занятый путь, не ведущий туда, уходит в бэкап; все проверки — до первого бэкапа (Decision 12).
   - Закрывает divergences 2, 3 и 4 (MAC-INST-10, -13, -11).
   - Отвергнуто владельцем:
     - (A) копировать `nvim_forge/` с проверками до бэкапа и обновлять копию на месте. Нужен признак «эту копию поставил скрипт из того же источника» (файл-маркер) и сравнение содержимого. Это собственное состояние установщика, которое может разъехаться с чекаутом: тот же класс, что divergence 4.
     - (C) убрать режим. **BREAKING**: уходят `FORGE_NVIM_DEPS_ONLY=0`, `FORGE_NVIM_INSTALL_DIR` и `FORGE_NVIM_USE_LOCAL_SOURCE`, а `nvim` без `./nvim_forge.sh` перестаёт видеть конфиг.
10. **Путь установки подчиняется тому же правилу, что симлинк WT-LOAD-4, и тем же функциям.**
    - Правило: `resolve_path(путь) = <чекаут>/nvim_forge` — «already linked», ничего не делать. Иначе `backup_path` (целиком, симлинк переносится сам), `mkdir -p` родителя, `ln -s` на абсолютный путь с раскрытыми симлинками.
    - Относительный симлинк и симлинк на родительский каталог распознаются через `resolve_path`, как в S9 и S14 для WezTerm.
    - Общая часть — функция «симлинк `<dst>` → `<src>` с бэкапом»: её зовут шаг установки конфига и `link_wezterm_config`. У шага WezTerm остаётся только своё: `…/wezterm` не каталог → бэкап.
    - Отвергнуто: отдельная копия той же логики для `~/.config/nvim`. Две копии одной логики — ровно причина дефектов Linux, которые чинит `add-linux-installer-parity`.
    - Функция живёт там же, где `resolve_path`: сейчас в `install-macos.sh`, после `add-linux-installer-parity` — в его общем файле функций. Кто из двух changes применяется вторым, тот и переносит.
    - Вложенность проверяется отдельно, до бэкапа. Путь установки совпадает с чекаутом или лежит над ним → бэкап унёс бы сам чекаут вместе с выполняющимся скриптом. Путь внутри чекаута (кроме самого `<чекаут>/nvim_forge`) → симлинк появился бы в дереве репо. Оба случая — отказ. Сравнение — по раскрытым путям, с разделителем на конце: `/repo-other` не лежит внутри `/repo`.
11. **Чекаут вне чекаута — тем же бутстрапом MAC-INST-3, с сохранением режима.**
    - Скрипт, запущенный как файл вне чекаута в режиме установки, до шагов зависимостей клонирует или обновляет `FORGE_NVIM_SRC` и перезапускается оттуда с `FORGE_NVIM_DEPS_ONLY=0`. Без явного флага перезапуск из чекаута выбрал бы локальный режим (MAC-INST-2), и режим, выбранный при запуске, потерялся бы.
    - Дальше путь один: режим установки всегда работает из чекаута. Шаг WezTerm находит `wezterm.lua` в нём же.
    - `FORGE_NVIM_USE_LOCAL_SOURCE=1` значит «не ходить в сеть: источник — только чекаут, из которого запущен скрипт». Вне чекаута — отказ с прежним сообщением до любых действий вместо бутстрапа. Из чекаута флаг ничего не меняет, но остаётся допустимым: старые команды из README (`FORGE_NVIM_DEPS_ONLY=0 FORGE_NVIM_USE_LOCAL_SOURCE=1`) продолжают работать.
    - Отвергнуто:
      - клонировать `FORGE_NVIM_SRC` внутри шага установки, без перезапуска. Появляется второй путь «получить чекаут», а шаг WezTerm у скрипта вне чекаута не находит `wezterm.lua` и пропускается;
      - отказывать «запусти из чекаута». Ломает сценарий MAC-INST-2 «копия скрипта в установленном конфиге» и запуск скачанного скрипта, а владелец назвал клон в `FORGE_NVIM_SRC` законным источником;
      - убрать `FORGE_NVIM_USE_LOCAL_SOURCE`. Поломка чужих команд без выигрыша.
12. **Порядок проверок: все отказы — до первого бэкапа.**
    - На старте, до шага зависимостей: `FORGE_NVIM_USE_LOCAL_SOURCE=1` вне чекаута; бутстрап (git с проверкой CLT, клон или pull, перезапуск).
    - Сразу после шага зависимостей, до шага WezTerm, — одна функция предпроверки режима:
      - в `<чекаут>/nvim_forge` есть `init.lua`;
      - путь установки и чекаут не вложены друг в друга (Decision 10);
      - `nvim` в PATH.
    - После шага WezTerm: «already linked» или бэкап, `mkdir -p`, `ln -s`, синхронизация. Отказ по `FORGE_NVIM_NO_BACKUP=1` остаётся внутри `backup_path`, как у всех путей (MAC-INST-8). Бэкапов при этом флаге не бывает вовсе.
    - Почему предпроверка до шага WezTerm: шаг WezTerm сам бэкапит (`~/.wezterm.lua`, WT-LOAD-5), а правило владельца — «все проверки до любого бэкапа». `nvim` ставит сам шаг зависимостей, поэтому раньше него проверять нельзя.
    - Отвергнуто: проверять всё внутри шага установки, после шага WezTerm. Путь установки остался бы нетронутым, но конфиг WezTerm был бы уже переподключён при заведомо проваленной установке.
13. **`XDG_CONFIG_HOME` внутри чекаута не учитывается (divergence 3).**
    - Путь установки по умолчанию — `${XDG_CONFIG_HOME:-~/.config}/nvim` по шеллу. Исключение: `XDG_CONFIG_HOME` после `resolve_path` равен корню чекаута или лежит внутри него (с разделителем на конце). Тогда берётся `~/.config/nvim`.
    - Это то же правило, что Decision 3 в `add-linux-installer-parity`; проверка «путь внутри чекаута» одна на оба случая.
    - Отвергнуто:
      - `XDG_CONFIG_HOME` из launchd, как для WezTerm. `nvim` запускается из шелла и читает шелловый `XDG_CONFIG_HOME`, launchd для него не источник;
      - всегда `~/.config`. Сломало бы тех, у кого `XDG_CONFIG_HOME` задан в профиле намеренно.
14. **Синхронизация плагинов: `Lazy! restore` в окружении установленного конфига.**
    - С симлинком каталог конфига — это `nvim_forge/` чекаута. `Lazy! sync` двигает плагины к свежим версиям и переписывает отслеживаемый `nvim_forge/lazy-lock.json` (Context). Грязный чекаут потом ломает `git pull --ff-only` бутстрапа (MAC-INST-3), как только lockfile меняется выше по течению. К тому же версии перестают совпадать с зафиксированными.
    - `Lazy! restore` приводит установленные плагины к lockfile. Недостающие `lazy.nvim` ставит при старте того же `nvim --headless`, тоже по lockfile. Поэтому lockfile переписывается тем же содержимым, и `git status` чекаута не меняется. Treesitter и Mason — как прежде, сбой — только сообщение.
    - `nvim` синхронизации запускается с `XDG_CONFIG_HOME` = родитель пути установки и `NVIM_APPNAME` = его имя. Так он читает ровно путь установки, а не конфиг и данные сборки nvim_forge, которые шелл унаследовал из её терминала (`NVIM_APPNAME=nvim_forge`, `XDG_CONFIG_HOME` = репо). Для `~/.config/nvim` это обычные `~/.config` и `nvim`.
    - Отвергнуто:
      - оставить `Lazy! sync` — причины выше;
      - убрать синхронизацию, как в локальном режиме. Это меняет состав режима, а не следует из решения B; владелец этого не решал.
    - Цена: `restore` не делает `clean`. Плагины, убранные из спеки, остаются в каталоге данных до `:Lazy clean` руками.

## Risks / Trade-offs

- [Устройство macOS без CLT выведено, а не проверено] → ручная проверка на Mac без CLT с записью в FIXLOG. Если `xcode-select -p` ведёт себя иначе, остаётся нынешнее поведение (сообщение git, код ≠ 0), то есть не хуже сегодняшнего.
- [awk-разбор plist — не полноценный XML-парсер] → plist LaunchAgent почти всегда машинные и простые, а `plutil` нормализует формат. Нераспознанная структура даёт ложный пропуск, не ложное «сломано».
- [Другие способы выставить launchd-переменную при входе — скрипт, который вызывает plist, или `launchctl config`] → не распознаются. Текущий сеанс покрыт WT-LOAD-10, следующие входы — нет. Записано как ограничение.
- [Заглушки `brew` и `nvim` моделируют CLI] → модель описана в комментарии; первый прогон на Mac сверяет шаг зависимостей и синхронизацию вживую.
- [Имена сценариев заморожены OpenSpec 1.13.2] → четыре старых имени читаются как история. Тело каждого начинается с того, что теперь происходит. Переименовать их можно правкой главной спеки после архива, это не меняет поведения.
- [bash 3.2] → никаких `mapfile`, ассоциативных массивов, `${var,,}`; прогон всего набора под 3.2.57 обязателен.
- [Конфиг живёт в чекауте: удалённый или перенесённый чекаут оставляет битый симлинк, и `nvim` стартует без конфига] → повторный запуск установщика из нового места уносит битый симлинк в бэкап и ставит новый (сценарий «на месте чужой конфиг»). Предупреждение — в nvim_forge/README.md.
- [`git pull` или смена ветки в чекауте сразу меняет рабочий конфиг] → это цель решения: один источник. Откат — git в чекауте.
- [`:Lazy update` из `nvim` теперь пишет lockfile в чекаут] → видно в `git status` и коммитится осознанно, как и в локальном режиме. Сам установщик в чекаут не пишет (Decision 14).
- [Модель `lazy.nvim` сверена по исходнику локальной копии, а не прогоном на Mac] → ручной шаг: после установки на Mac `git -C <чекаут> status --porcelain` пуст. Если `restore` всё же переписывает lockfile, спека нарушена — это баг кода, чинится до архива.
- [Один конфиг — два каталога данных: `~/.local/share/nvim` для `nvim` и `~/.local/share/nvim_forge` для `./nvim_forge.sh`] → плагины качаются дважды. Так было и с копией, не ново.
- [Предпроверка до шага WezTerm: без `nvim` режим установки не подключает и WezTerm] → повторный запуск после установки Neovim делает всё. Отказ сообщает, что поставить.

## Migration Plan

- Для пользователя ничего не нужно: повторный запуск установщика и есть применение. Следующий прогон:
  - допишет недостающий блок в профиль;
  - перестанет называть безобидные plist (код может смениться с 1 на 0);
  - перестанет ставить Rust и шрифт заново;
  - в режиме `~/.config/nvim` один раз унесёт прежнюю копию (или клон монорепо, оставленный старой версией) в бэкап и поставит симлинк. Каталог данных `~/.local/share/nvim` остаётся, плагины приводятся к lockfile.
- Формат состояния для WezTerm и профилей не меняется: блоки в профилях, бэкапы и строка `brew shellenv` те же. `~/.config/nvim` из каталога становится симлинком.
- Откат — revert скрипта. Старая версия при следующем прогоне режима унесёт симлинк в бэкап (сам чекаут не тронет) и вернётся к копии; прежняя копия лежит в `~/.config/nvim.backup-*`.
- Порядок работ — tasks.md:
  - сначала тестовые заглушки;
  - затем независимые группы: шрифт и Rust, бутстрап, профили, LaunchAgent, подсказка;
  - затем режим `~/.config/nvim`;
  - затем шапка и финальный прогон.
