# Design

## Context

Мотивация — в proposal.md, раздел Why. Здесь только то, что определяет способ исправления.

- Копирование по клавишам идёт через фабрику `copy_selection_or(fallback)` (`wezterm.lua:296-312`). Колбэк читает `window:get_selection_text_for_pane(pane)` и при непустом тексте вызывает `act.CopyTo(...)`. Для умного Ctrl+C на Windows после этого вызывается `act.ClearSelection`.
- В Lua API WezTerm 20240203 каждый вызов `window:*` — отдельное уведомление GUI-потоку (`wezterm-gui/src/scripting/guiwin.rs`). Между двумя вызовами GUI-поток может отрисовать панель и снять выделение (`check_for_dirty_lines_and_invalidate_selection`, WT-CLIP-9). `CopyTo` при выполнении читает выделение заново и пишет результат безусловно (`termwindow/mod.rs:2565`).
- Таблица `copy_mode` строится из `wezterm.gui.default_key_tables()` через `to_phys_binding`. Запись `y` приходит из неё как `mapped:y` → `Multiple{CopyTo(ClipboardAndPrimarySelection), CopyMode("Close")}`. WezTerm собирает таблицу в HashMap, поэтому при повторе пары (клавиша, модификаторы) без предупреждения побеждает последняя запись (`config/src/config.rs:1213-1247`). Регистр имени физической клавиши во встроенных таблицах от запуска к запуску разный.
- Меню приложения на macOS ищет сочетания только в `config.keys` (`inputmap.rs`, `locate_app_wide_key_assignment`). Таблицы режимов оно не смотрит. Поэтому ⌘C сегодня идёт через keyDown → `phys:C`, и это нельзя сломать.
- Тестов на `wezterm.lua` в `tests/` пока нет. В исследовании (research_findings.md, «unit tests of callback logic with a fake wezterm module») `wezterm.lua` загружался без правок под `nvim -l` с поддельным модулем `wezterm`, для видов Windows и macOS. Neovim 0.12 стоит на обеих машинах.

## Goals / Non-Goals

**Goals:**
- Один путь копирования для всех клавиш, включая `y`: выделение читается один раз, в буфер пишется прочитанный текст.
- Инвариант «нет голого `CopyTo` ни в одной привязке» проверяется механически, без GUI.
- Тест детерминирован: без сети, без реального буфера обмена, без сна и без зависимости от PATH и домашнего каталога машины.

**Non-Goals:**
- Снятие выделения при выходе из copy mode и QuickSelect. WT-SCROLL-5, WT-SCROLL-12 и сценарий WT-CLIP-2 «Фрагмент, оставшийся после QuickSelect» не меняются (см. Open Questions).
- Запись в буфер не с клавиш: отпускание мыши (WT-CLIP-7), выбор метки в QuickSelect (WT-SCROLL-12), выбор символа в режиме WINDOWS, OSC 52 (WT-CLIP-11). Они не идут через `copy_selection_or`, и сегодня пустую строку не пишут.
- Search mode (Enter, `/`, `n`/`N`). Поведение Enter меняет отдельный change `change-search-enter-accept`.
- Правило WT-CLIP-9 (выделение гаснет при перерисовке) — это поведение самого WezTerm, оно не меняется.
- Разбиение `wezterm.lua` на модули и общий реестр привязок — отдельная перестройка (research_findings.md, «Целевая структура»).

## Decisions

### D1. Писать проверенный текст через `CopyTextTo`, а не `CopyTo`

Колбэк передаёт уже прочитанный текст: `act.CopyTextTo{ text = sel, destination = "ClipboardAndPrimarySelection" }`. Назначение то же, что у прежнего `CopyTo`: на Linux запись идёт в CLIPBOARD и PRIMARY, на Windows и macOS — в один системный буфер. `CopyTextTo` есть в 20240203 (`keyassign.rs:513`).

Альтернативы:
- `CopyTo` с повторной проверкой после записи. Гонка остаётся, только сдвигается.
- Сначала снять выделение, потом копировать. Нужен тот же текст, а читать его всё равно пришлось бы заранее.

### D2. Одна фабрика на все клавиши копирования, включая `y`

`copy_selection_or(fallback)` превращается в фабрику с двумя параметрами. `after_copy` — действие после успешного копирования, `on_empty` — действие при пустом выделении; оба могут быть `nil`:

| Клавиша | after_copy | on_empty |
|---|---|---|
| Ctrl+Shift+C, Ctrl+Insert, Cmd+C | — | — |
| Ctrl+C на Windows | `ClearSelection` | `SendKey Ctrl+C` |
| `y` в copy mode | `CopyMode("Close")` | `CopyMode("Close")` |

Так в коде остаётся одна конструкция, а не две похожие. Альтернатива — отдельный колбэк для `y` — дублировала бы правило §42 во втором месте.

### D3. Запись `y` заменяется, а не дописывается

После конвертации встроенных таблиц код находит в `config.key_tables.copy_mode` запись с физической клавишей `Y` без модификаторов и заменяет её действие. Имя клавиши сравнивается без учёта регистра, пустые модификаторы, `nil` и `"NONE"` считаются одним и тем же. Если найдено не ровно одна запись, код пишет `wezterm.log_error` (видно в debug overlay), и тест тоже падает. Дописывать вторую запись нельзя: при повторе WezTerm молча оставляет последнюю, и правильный результат зависел бы от порядка вставки.

Если встроенных таблиц нет (конфиг загружен без GUI, ветка `pcall`), `copy_mode` не переопределяется, и остаётся встроенная таблица WezTerm. В GUI так не бывает (WT-SCROLL-6). В этой ветке добавляется только `wezterm.log_warn`, чтобы сбой не был молчаливым.

### D4. Проверка: поддельный `wezterm` и `nvim -l`

- `tests/wezterm/fake_wezterm.lua` — минимальная подделка. Конструкторы `act.*` возвращают данные вида `{ name = "CopyTextTo", args = … }`, `action_callback` возвращает `{ callback = fn }`, `on` записывает обработчики. `gui.default_key_tables()` возвращает небольшую таблицу `copy_mode` в формате 20240203: `mapped:y` → `Multiple{CopyTo, CopyMode Close}` и несколько соседних клавиш. `target_triple` передаётся параметром, поэтому проверяются виды Windows и macOS на любой машине. `home_dir` указывает на заведомо несуществующий путь, `os.getenv` в окружении загружаемого файла отдаёт фиксированные значения. Так результат не зависит от PATH и файла состояния владельца.
- `tests/wezterm/clipboard.test.lua` загружает `wezterm.lua` с подделкой и проверяет:
  - (а) `y` при пустом выделении выполняет только `CopyMode("Close")`;
  - (б) `y` с выделением `"abc"` выполняет `CopyTextTo{text="abc"}`, затем `Close`;
  - (в) для каждой клавиши копирования поддельное окно отдаёт `"abc"` при первом чтении и `""` при любом следующем. В буфер уходит `"abc"`, выделение читается ровно один раз;
  - (г) при пустом выделении Ctrl+Shift+C, Ctrl+Insert и Cmd+C ничего не выполняют, а Ctrl+C на Windows выполняет только `SendKey`;
  - (д) обход `config.keys` и всех `config.key_tables`, включая вложенные `Multiple`, не находит ни одного `CopyTo`.
- Запуск: `nvim -l tests/wezterm/clipboard.test.lua`. Код выхода не 0 при любом провале, в выводе — список проверок.

Почему `nvim -l`, а не прогон внутри WezTerm (Lua 5.4): Neovim есть на обеих машинах, запуск без GUI и без окна. Код в этих местах не использует ничего, в чём LuaJIT и Lua 5.4 расходятся. Настоящий разбор Lua 5.4 проверяет отдельная команда `wezterm --config-file wezterm.lua ls-fonts` (WT-LOAD).

Если к моменту реализации другой change уже принесёт общий поддельный `wezterm` в `tests/wezterm/`, тест кладётся рядом с ним, и второй подделки не появляется.

### D5. Что обновить вместе с кодом

- Комментарии `wezterm.lua:288-295` («Голый act.CopyTo здесь запрещён» — теперь и в таблицах режимов) и `737-741` («Раз CopyTo ни на одну клавишу…»).
- `docs/WEZTERM.md` §5, строка `y`: «скопировать выделение и выйти; без выделения буфер не трогается».
- Новая запись FIXLOG со строкой `Спека: WT-CLIP-1 (MODIFIED), WT-SCROLL-7 (MODIFIED)`. Прежние записи, включая §42, не переписываются.

## Risks / Trade-offs

- [Колбэк `y` читает выделение не той панели, что `CopyTo`] → в 20240203 `CopyTo` берёт `selection_text` той же панели, которую WezTerm передаёт колбэку, а Ctrl+Shift+C в copy mode уже копирует через тот же вызов (WT-CLIP-4). Проверка вручную на Windows: `v`, `w`, `y` → текст в буфере.
- [Гонку нельзя воспроизвести вживую] → детерминированный тест (в) доказывает, что текст читается один раз и пишется именно он. Что в GUI гонки больше нет, следует из того, что второго чтения в коде не осталось.
- [Mac недоступен] → сценарии `y` и Cmd+C на macOS проверяет владелец на месте (`pbcopy`/`pbpaste`), результат пишется в запись FIXLOG. До этого в FIXLOG стоит «на Mac не проверено».
- [Имя сценария WT-SCROLL-7 «y без выделения стирает буфер» описывает старое поведение] → OpenSpec 1.13.2 не даёт убрать имя сценария из MODIFIED: validate и archive требуют все прежние имена. Содержание сценария описывает новое поведение: буфер не стирается. Переименовать сценарий можно только редакторской правкой `openspec/specs/` после архивации, по решению владельца.
- [Параллельные changes правят `wezterm.lua`: `fix-windows-mode-modality`, `change-search-enter-accept`, `resolve-key-ownership-conflicts`] → правка локальная (фабрика копирования и одна запись в `copy_mode`); конфликты разрешаются при apply.
- [Встроенных таблиц нет] → `y` остаётся голым `CopyTo`, но только вне GUI. В журнале остаётся предупреждение (D3).

## Migration Plan

Переносить данные не нужно. Изменение — правка `wezterm.lua`. Работающий WezTerm подхватит её сам (WT-LOAD-14) или по Ctrl+Shift+R. Откат — `git revert` коммита. Перед коммитом запустить `nvim -l tests/wezterm/clipboard.test.lua` и `wezterm --config-file wezterm.lua ls-fonts`: пустой stderr без `ERROR`.

## Open Questions

- Снимать ли выделение явно при выходе из copy mode (Esc, `q`, Ctrl+C, Ctrl+G, `y`) и после QuickSelect, чтобы на Windows следующий Ctrl+C сразу прерывал программу? Этот change от ответа не зависит. Если владелец скажет «да», понадобится отдельный change на WT-SCROLL-5, WT-SCROLL-12 и WT-CLIP-2 (плюс абзац WT-SCROLL-7 после архивации этого change). В колбэк `y` тогда добавится `ClearSelection` в `after_copy` и `on_empty`.
