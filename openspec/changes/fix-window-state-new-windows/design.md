# Design

## Context

Мотивация — в proposal.md, раздел Why. Требования — в `specs/wezterm-window-state/spec.md` и `specs/wezterm-panes-tabs/spec.md` этого change. Здесь только то, что определяет способ исправления. Ссылки на исходник — WezTerm 20240203-110809-5046fc22.

- Размер и положение окна задаются только из Lua: `gui_window:set_inner_size(w, h)` и `set_position(x, y)`. Сейчас это делает обработчик `gui-startup` (`wezterm.lua:92-108`), который WezTerm вызывает один раз на процесс (`wezterm-gui/src/main.rs:364-373`, `442`).
- Любое GUI-окно создаётся в `TermWindow::new_window` (`termwindow/mod.rs:574`). Оно показывается (`window.show()`, `:872`) и сразу получает событие `window-config-reloaded` (`:874`). Так приходят первое окно, окна от `SpawnWindow` (Ctrl+Shift+N, Cmd+N), `wezterm cli spawn --new-window`, повторный запуск (`Publish::try_spawn`) и окно, которое WezTerm создаёт заново при возврате в воркспейс (`frontend.rs`, `reconcile_workspace`). Событие отбрасывается, если в окне ещё нет активной панели (`emit_window_event`, `:1557-1559`).
- Это же событие приходит окну при перечитывании конфига для всех окон и при каждой смене его overrides (`config_was_reloaded`, `:1644`, `:1759`). Обработчик события вызывается много раз за жизнь окна и не должен двигать окно повторно.
- Overrides нового окна — `Null` (`:683`). Из Lua `get_config_overrides()` отдаёт `nil`. Смена overrides пересчитывает конфиг окна только при `value != self.config_overrides` (`:1127-1131`). Пересчёт для любого значения, включая `Null` и `{}`, заново выполняет `wezterm.lua` (`config/src/lib.rs:654-660`, `Config::load_with_overrides`). Поэтому файл состояния прочитается заново.
- При переключении воркспейса окно, которое остаётся на экране, получает другое mux-окно (`TermWindowNotif::SwitchToMuxWindow`, `:1272-1289`). Его overrides сохраняются, события `window-config-reloaded` нет, а `window:window_id()` начинает отдавать id нового mux-окна. Лишние окна закрываются, недостающие создаются заново через `new_window`.
- Новое окно берёт глобальный конфиг последнего перечитывания (`new_window` → `configuration()`, `:575`). Отсюда старый шрифт после сохранения в этой же сессии (WT-STATE-5).
- Тестов на `wezterm.lua` в `tests/` пока нет. `add-wezterm-spec-checks` (design, решение 3) описывает общий поддельный `wezterm` под `nvim -l` и файл `tests/wezterm/window-state.test.lua`. `fix-copy-clobbers-clipboard` заводит ту же подделку. Здесь используется та же подделка, вторая не появляется.

## Goals / Non-Goals

**Goals:**
- Один путь размещения для всех окон, включая первое. Второго места, где окну задаётся размер, в конфиге нет.
- Новым считается окно, которое появилось на экране и ещё не прошло этот путь. Признак хранится в самом окне, без внешнего реестра, который растёт.
- Ctrl/Cmd+`0` пересчитывает конфиг окна при каждом нажатии, и после сброса окно ведёт себя как окно без изменений шрифта (WT-STATE-5).
- Логика проверяется детерминированно: без GUI, без реального экрана и файла состояния, без времени.
- Размещение окна оставляет след в журнале WezTerm (debug overlay): какое окно, откуда размер, итог.

**Non-Goals:**
- Единицы сохранённого размера (физические или логические пиксели) — отдельный change на WT-STATE-1, 3, 4 (proposal, «Не входит»).
- Поведение первого окна (WT-STATE-1) не меняется, меняется только путь в коде.
- Запоминать положение окон и восстанавливать его при возврате в воркспейс. WezTerm положение не хранит, конфиг тоже.
- Сохранение по Ctrl+Shift+S (WT-STATE-3) и формат файла состояния, в том числе неатомарная запись.
- Сохранять режимы WINDOWS и RESIZE при перечитывании и смене шрифта (WT-WIN-2, WT-STATE-6). Это вопрос OQ7 в `review-baseline`.
- Сочетания: Ctrl+Shift+N и Cmd+N остаются `SpawnWindow` (WT-PANE-7, WT-PANE-8). Super-сочетания шрифта на Windows решает `resolve-key-ownership-conflicts`.
- Воркспейсы как таковые (WT-PANE-10), в том числе невидимое окно при повторном запуске из другого воркспейса.

## Decisions

### D1. Где и какого размера новые окна

Решение владельца 2026-09-27: вариант (a). Каждое новое окно — от Ctrl+Shift+N, Cmd+N, `wezterm cli spawn --new-window` и повторного запуска — ставится как первое: по центру активного экрана, сохранённого размера, если он есть, иначе 0,62×0,72 экрана.

Отвергнуты:
- (b) Размер как у первого окна, положение выбирает ОС (каскад). Большое сохранённое окно может выйти за край экрана.
- (c) Сохранённый размер, если он есть, иначе стандартные 80×24 знакомест; положение выбирает ОС. Это два правила вместо одного, и окно без сохранённого размера остаётся маленьким, вопреки §32 («крупным в долю экрана»).

Цена варианта (a): новые окна ложатся ровно поверх прежних. Это записано в WT-STATE-2.

### D2. Кому достаётся сохранённый шрифт

Решение владельца 2026-09-27: вариант (a). Ctrl+Shift+S уже открытые окна не меняет: конфиг не перечитывается, режимы не выключаются, WT-STATE-3 не меняется. Новое окно при появлении пересчитывает свой конфиг и берёт шрифт из файла. Ctrl/Cmd+`0` пересчитывает конфиг окна при каждом нажатии (WT-STATE-7).

Отвергнут вариант (b): после записи файла вызывать `wezterm.reload_configuration()`. Кода меньше, и повторный Ctrl+`0` чинится заодно. Но во всех окнах гаснут режимы WINDOWS и RESIZE, шрифт в других окнах «прыгает», и меняется WT-STATE-3 («Уже открытые окна сохранение не меняет», сценарий «Режим WINDOWS не выключается»).

### D3. Один путь размещения: обработчик `window-config-reloaded`

Обработчик `window-config-reloaded` вызывает функцию «принять окно». Она выполняется для каждого окна, в том числе для первого. Обработчик `gui-startup` удаляется: без него WezTerm сам открывает первое окно с программой из командной строки (`spawn_tab_in_domain_if_mux_is_empty`, `main.rs`). Сценарии WT-STATE-1 «Запуск с программой вместо шелла» и «Положение из командной строки» проверяются вручную.

«Принять окно» делает три шага:
1. Читает файл состояния: размер и шрифт из одного и того же разбора, что и сейчас (`read_saved_size`).
2. Считает размер и положение. Это чистые функции от сохранённого состояния и сведений об экране. Размер — сохранённый или доля экрана. Положение — центр активного экрана. Если сведений об экране нет — 1500×950 без положения. Результат задаётся через `set_inner_size` и `set_position`.
3. Ставит окну overrides `{}` (D4, D5).

Каждый шаг пишет `wezterm.log_info` с id окна, источником размера (`saved`, `fraction`, `fallback`) и итогом, а при ошибке — `wezterm.log_warn` с текстом ошибки. Сейчас ошибка молча глотается `pcall`. Если ошибка случилась в шаге 2, шаг 3 всё равно выполняется, иначе окно пытались бы поставить при каждом следующем событии.

Альтернативы:
- Заменить `SpawnWindow` на `action_callback` с `mux.spawn_window` и `set_inner_size`. Покрывает только клавиши: CLI, повторный запуск и возврат в воркспейс остаются без размера. Это второй путь рядом с `gui-startup`.
- Опрос из `update-right-status` (каждые 100 мс) и реестр обработанных окон (proposed_fix divergence 65). Лишнее состояние, задержка до 100 мс, и обработчик статуса начинает отвечать за размер окна.
- Вычислять `initial_cols` и `initial_rows` из сохранённых пикселей. До появления окна Lua не знает размер знакоместа и DPI, а центрирование так не задать.

### D4. Признак «окно ещё не принято» — overrides окна равны `nil`

Новое GUI-окно всегда начинает с overrides `Null`. Шаг 3 ставит `{}`, и больше конфиг overrides в `nil` не возвращает. Поэтому «overrides = nil» верно ровно для окна, которое появилось и ещё не принято. Это верно для любого источника окна и не зависит от перечитывания Lua: признак живёт в окне, а не в состоянии Lua. Инвариант «ни один путь не ставит overrides `nil`» проверяет тест (D7).

Следствия:
- Окно, которое при переключении воркспейса остаётся на экране, сохраняет overrides и не двигается.
- Окно, которое WezTerm создаёт заново при возврате в воркспейс, — новое окно ОС с overrides `Null`. Оно ставится как новое: центр и сохранённый размер. Это записано в WT-STATE-2 (сценарий «Возврат в воркспейс») и соответствует D1: прежнее положение WezTerm всё равно не хранит.

Альтернативы:
- Реестр принятых окон в `wezterm.GLOBAL` по `window:window_id()` с чисткой по `wezterm.mux.all_windows()`. `window_id()` — id mux-окна, и он меняется при переключении воркспейса (`SwitchToMuxWindow`). Окно, оставшееся на экране, при следующем событии (например, смене шрифта) выглядело бы новым и прыгало бы в центр. Кроме того, это второе состояние, которое надо ограничивать чисткой.
- Свой ключ-маркер в overrides. Overrides применяются как поля конфига (`config[key] = value`, `config.rs:1099-1129`), и строгий `config_builder` отвергает неизвестное поле.

### D5. Шрифт нового окна — пересчёт его конфига, а не явный `font_size`

Шаг 3 (`{}` вместо `Null`) меняет overrides. WezTerm заново вычисляет `wezterm.lua` для этого окна, и `config.font_size` читается из файла на момент открытия (WT-STATE-5). В overrides шрифта нет, поэтому при следующем перечитывании для всех окон окно снова берёт шрифт из файла, как любое окно без собственных изменений.

Альтернатива — `set_config_overrides{ font_size = <из файла> }` при появлении окна. Тогда новое окно вело бы себя как окно, где шрифт менялся клавишами: при перечитывании оно держало бы старое значение. Это нарушает WT-STATE-5, сценарий «Перечитывание не трогает шрифт, изменённый клавишами» (часть про окно B).

### D6. Ctrl/Cmd+`0` — два шага overrides

Сброс берёт текущие overrides окна (при `nil` — `{}`, прочие поля сохраняются) и ставит их дважды:
1. с `font_size = <шрифт из файла или 12>`;
2. без `font_size`.

Второе значение всегда отличается от первого. Значит, WezTerm при каждом нажатии пересчитывает конфиг окна хотя бы раз, и последнее вычисление читает файл заново. Итоговые overrides — те же `{}`, что сейчас после сброса. Поэтому окно после сброса следует за файлом при перечитывании (WT-STATE-7, сценарий «Сброшенное окно следует за файлом»). Промежуточное значение и есть целевой шрифт, так что между шагами шрифт не мигает. Вызовы `window:*` доходят до GUI-потока по очереди, порядок сохраняется. Режимы WINDOWS и RESIZE выключаются при каждом нажатии (`config_was_reloaded` → `clear_stack`), как и описано в WT-STATE-7.

Альтернативы:
- Только явный `font_size = <из файла>` (proposed_fix divergence 64). После сброса окно перестаёт следовать за файлом при перечитывании. Это нарушило бы WT-STATE-5 и сценарий «Сброшенное окно следует за файлом».
- Переключать overrides между `nil` и `{}`. `nil` — признак непринятого окна (D4): окно встало бы в центр при следующем событии.
- `wezterm.reload_configuration()` — затрагивает все окна, это отвергнутый вариант (b) из D2.

### D7. Проверка: чистые функции и поддельное окно

- Расчёт размера и положения — чистые функции от `(сохранённое состояние, экран)`. Внешний мир трогают только тонкие обработчики: чтение файла, `wezterm.gui.screens()`, вызовы окна.
- `tests/wezterm/window-state.test.lua` под `nvim -l` с общей подделкой (`add-wezterm-spec-checks`, решение 3). Подделке нужно:
  - `gui.screens()` с заданным активным экраном или с ошибкой;
  - поддельное окно, которое отдаёт заданные overrides и записывает вызовы `set_inner_size`, `set_position` и `set_config_overrides`;
  - файл состояния как таблица в памяти.
- Проверки:
  - (а) окно с overrides `nil` и сохранённым 1454×1335 на экране 2560×1440 → размер 1454×1335, положение `(553, 52)`, затем overrides `{}`;
  - (б) без файла → 1587×1036 по центру;
  - (в) `screens()` бросает ошибку → 1500×950, `set_position` не вызван, overrides `{}` поставлены;
  - (г) окно с overrides `{}` или `{font_size=…}` → ни одного вызова размера, положения и overrides;
  - (д) сброс из `{}`, из `nil` и из `{font_size=16.94}` → последние два вызова: `{font_size=<из файла>}`, затем значение без `font_size`; без файла — 12;
  - (е) ни «принять окно», ни колбэки шрифта (×1,1, ÷1,1, сброс) ни разу не передают `set_config_overrides(nil)`;
  - (ж) обработчика `gui-startup` нет, обработчик `window-config-reloaded` есть.
- Что тест не доказывает — что WezTerm присылает событие каждому новому окну и что размер действительно применяется. Это ручная проверка на Windows и на Mac по сценариям WT-STATE-2 и WT-PANE-7.

### D8. Что обновить вместе с кодом

- Шапка `wezterm.lua:29-33`: обещание «ВСЕ новые окна» становится верным. Добавить, что новые окна ставятся в центр и что уже открытые окна сохранение не меняет.
- Комментарий `wezterm.lua:38-39` («Доли экрана ТОЛЬКО для первого запуска») — доля действует для каждого окна, пока размер не сохранён.
- Комментарий у `change_font_size` (`wezterm.lua:323-328`): сброс при каждом нажатии пересчитывает конфиг окна (D6).
- `docs/WEZTERM.md` §8: строки `Ctrl+Shift+S` и `Ctrl/Cmd+0`. Если `sync-docs-with-baseline` уже переписал файл — его раздел «Окно и шрифт».
- Новая запись FIXLOG со строками `Спека: WT-STATE-2 (MODIFIED)`, `Спека: WT-STATE-4 (MODIFIED)`, `Спека: WT-STATE-5 (MODIFIED)`, `Спека: WT-STATE-7 (MODIFIED)`, `Спека: WT-PANE-7 (MODIFIED)`. §32 не переписывается.

## Risks / Trade-offs

- [Новое окно на мгновение видно стандартного размера и со старым шрифтом] → Событие приходит после `show()`, и раньше повлиять на окно из Lua нельзя. Для первого окна так же и сейчас: `gui_window()` в `gui-startup` находит окно только после `show()`. Принято, записано в WT-STATE-2 и WT-STATE-5.
- [Событие при создании окна не пришло: в окне ещё нет активной панели] → Окно встало бы на место только при первом пересчёте конфига в нём, например при смене шрифта. Ручная проверка покрывает все четыре источника окон. Если такое увидено, тот же вызов «принять окно» добавляется в `update-right-status`: признак D4 делает его идемпотентным, и спека и задачи от этого не меняются.
- [После применения конфиг перечитается сам (WT-LOAD-14), а окна, где шрифт не меняли клавишами, имеют overrides `nil`] → Все такие окна один раз встанут в центр с сохранённым размером. См. Migration Plan.
- [Сохранённый размер больше экрана] → Как для первого окна (WT-STATE-1): размер не уменьшается, окно выходит за край. Решается вместе с единицами размера, в отдельном change.
- [Ctrl+`0` вычисляет конфиг окна дважды] → `wezterm.lua` выполняется за миллисекунды, нажатие редкое.
- [Имя сценария WT-STATE-7 «Повторный сброс не видит новое сохранение» описывает старое поведение] → OpenSpec 1.13.2 требует в MODIFIED все прежние имена сценариев (`specs-apply.js`, проверка `missing`). Текст сценария описывает новое поведение. Переименовать сценарий можно только редакторской правкой `openspec/specs/` после архивации, по решению владельца. Так же сделано в `fix-copy-clobbers-clipboard`.
- [Mac проверить отсюда нельзя] → Сценарии WT-STATE-2, WT-STATE-7 и WT-PANE-7 на macOS (Cmd+N, Cmd+`0`) владелец проходит на месте. Результат — в записи FIXLOG, до этого там «на Mac не проверено».
- [Параллельные changes правят `wezterm.lua`] → Правка локальная: секция размера окна, `change_font_size`, одно событие. `restructure-wezterm-config` идёт после этого change. Комментарии рядом правит `sync-docs-with-baseline`, правки делаются поверх его результата.

## Migration Plan

Данные переносить не нужно, формат файла состояния не меняется. После коммита WezTerm перезапускается целиком (все окна закрыты). Если вместо этого конфиг перечитается сам, окна без изменений шрифта один раз встанут в центр с сохранённым размером (Risks). Откат — `git revert` коммита и перезапуск. Перед коммитом: `nvim -l tests/wezterm/window-state.test.lua` зелёный, `wezterm --config-file wezterm.lua ls-fonts` — stderr без `ERROR`.
