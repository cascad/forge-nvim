# Design

## Context

Мотивация — в proposal.md (Why). Здесь только состояние и ограничения, которые определяют устройство.

**Класс задачи.** Три известных класса:
- оркестрация тестов: один вход, изоляция, таймауты, отчёт;
- golden-master (снимок, с которым сравнивается вывод);
- трассировка «требование ↔ проверка».

Готовые решения и что из них берётся:
- `prove`/TAP: процесс на файл, построчный протокол, вердикт по коду возврата. Берётся как образец.
- mini.test, busted: фреймворки для Lua в Neovim. Отклонены, см. решение 2.
- bats-core: shell-тесты. Отложен, скрипт установщика уже работает.
- Approval/Jest-снимки: golden-файлы с явным принятием изменения. Берётся как образец.
- OpenFastTrace: трассировка, нужна JVM. Отклонён.
- `converge` из Spec Kit: сверку делает LLM, в гейт не годится.

Своего кода — раннер, построчный помощник, нормализация снимка и trace. У двух последних нет готового инструмента без JVM, для первых двух причина в решении 2.

**Что есть в репо.** `wezterm.lua` — один файл на 786 строк, WT-LOAD-1. Внешний мир он читает в нескольких местах:
- `require("wezterm")`: `target_triple`, `home_dir`, `gui.default_key_tables()`, `gui.screens()`, `mux`;
- `os.getenv` (PATH, USERPROFILE);
- `io.open`: файл состояния окна, файл выгрузки истории, поиск `pwsh.exe` по PATH.

Времени и случайности в нём нет. Проверки есть только у установщика macOS: `tests/install-macos.scenarios.sh`, построчный вывод `ok`/`FAIL`, итог по коду возврата, окружение bash + git + python3 (WSL, Linux, macOS). В Git Bash на этой машине python3 не запускается.

**Что проверено прототипами** (scratchpad, см. proposal):
- сломанный конфиг: `show-keys` и `ls-fonts` выходят с кодом 0; `show-keys` при этом печатает встроенные привязки, а `ls-fonts` — `ERROR` в stderr;
- обёртка с `pcall(dofile)` и `os.exit(3)` даёт настоящий код возврата;
- подмена `wezterm.target_triple` в обёртке даёт вид macOS и Linux на Windows;
- регистр `phys:` в `show-keys --lua` случаен, порядок записей стабилен: он задаётся кодом клавиши, а не порядком в исходнике;
- `EmitEvent 'user-defined-N'` нумеруется в порядке создания колбэков;
- подделка `wezterm` под `nvim -l` с `setfenv`: 44 проверки за 44 мс, три мутанта пойманы;
- `keymaps.lua` nvim_forge грузится в `nvim --clean` без плагинов;
- `keys` из спек lazy.nvim читаются через `dofile`: 126 клавиш.

**Окружение этой машины:** WezTerm 20240203-110809-5046fc22, Neovim 0.12.2 (LuaJIT), WSL с bash 5.2, git и python3.

**Ограничения:**
- `openspec/specs/**` этот change не правит;
- чек-листы `tests/manual/wezterm-{windows,macos}.md` и строки `Проверка: вручную (…)` в спеках заводит `review-baseline` (его design, решения 3 и 6);
- `fix-copy-clobbers-clipboard` планирует ту же подделку `tests/wezterm/fake_wezterm.lua` и `tests/wezterm/clipboard.test.lua`;
- `change-search-enter-accept` и `fix-windows-mode-modality` планируют `tests/wezterm-keys.scenarios.sh`.

## Goals / Non-Goals

**Goals:**
- Одна команда на обеих машинах проверяет всё, что проверяется без GUI, и печатает статус каждого ID из `openspec/specs/`.
- Проверки детерминированы: подделка получает тройку, окружение и файлы параметрами. Юнит-уровень не трогает диск, сеть и часы.
- Ни одна ошибка не выдаёт себя за успех. Падение, зависание, пустой вывод, отсутствие бинарника — это FAIL или SKIP, но не PASS.
- Любое изменение набора привязок и настроек видно как diff снимка. На этом держится `restructure-wezterm-config`.
- Связь ID ↔ проверка проверяется механически в обе стороны. Висячая ссылка — FAIL.

**Non-Goals:**
- CI (GitHub Actions). Раннер устроен так, что CI — это тот же вызов, но сам workflow — отдельный change.
- Спеки и тесты nvim_forge, в том числе полный конфиг с плагинами (уровень 2). Здесь nvim участвует только как вторая сторона контракта WT-KEYS-4/6/7.
- Кодировщик клавиш, IME, реальный буфер обмена, размер окна, отрисовка. Это ручные проверки, их чек-листы ведёт `review-baseline`.
- Строки `Проверка:` в `openspec/specs/`. Спеки здесь не правятся, см. Open Questions.
- Правка `wezterm.lua`, в том числе теги `-- spec:`. Их расставляет `restructure-wezterm-config`, trace их только проверяет.
- Перенос `tests/install-macos.scenarios.sh` на bats-core и правка скрипта. Хук `core.hooksPath` из установщиков: установщиками владеют `fix-macos-installer` и `add-linux-installer-parity`.
- Самопроверка конфига во время работы (log_error, бейдж «CFG!»). Бейдж — это поведение WT-UI-12, отдельный change.
- LLM-сверка спек с кодом в роли гейта.

## Decisions

**1. Один вход — `nvim -l tests/run.lua`. Раннер только оркеструет.**
- Раннер ищет файлы проверок по реестру, запускает каждый отдельным процессом через `vim.system` с таймаутом (по умолчанию 60 с, для установщика 180 с) и разбирает строки.
- Потом сводит результат по ID, пишет `.tests/report.json` и лог каждого файла в `.tests/logs/`.
- Аргументы: наборы `unit | wezterm | install | trace` (по умолчанию все), `--id ID`, `--update-golden`, `--strict`.
- Все источники энтропии раннера собраны в начале `run.lua`: ОС хоста, пути к `wezterm`, `wsl`, `bash`, версии, время для отчёта. Файлам проверок они передаются переменными окружения: `FORGE_REPO`, `FORGE_TEST_ID`, `FORGE_UPDATE_GOLDEN`, `FORGE_SANDBOX`.
- Почему nvim: он есть на обеих машинах, в нём LuaJIT, которым грузится `wezterm.lua`, и `vim.system` с таймаутом.
- Альтернатива: make или just. Отклонено: их нет ни на одной машине.
- Альтернатива: bash. Отклонено: на Windows нет надёжного POSIX, в Git Bash не работает python3.
- Альтернатива: раннер внутри WezTerm. Отклонено: там не поставить таймаут и не запустить подпроцесс надёжно, падение выглядит как код 0.

**2. Протокол: процесс на файл, строки `ok` / `FAIL` / `SKIP`, итог по коду возврата.**
- Формат строк тот же, что у `tests/install-macos.scenarios.sh` и у планов соседних changes: `  ok   <имя>`, `  FAIL <имя>  -- <подробность>`. Добавляется `  SKIP <имя>  -- <причина>`.
- Имя проверки начинается с ID требования.
- Правила вердикта файла:
  - код возврата не 0 — FAIL, даже если все строки `ok`;
  - таймаут — FAIL;
  - без фильтра `--id` код 0 и ни одной строки — FAIL «проверки не выполнялись». Это ловушка, которую нашёл research: WezTerm при падении вне `pcall` выходит с кодом 0 без вывода;
  - SKIP никогда не засчитывается как PASS.
- Помощник `tests/lib/check.lua` для Lua-файлов:
  - `check(имя, fn)` выполняет случай в `pcall`: ошибка становится FAIL этого случая с текстом, следующий случай выполняется;
  - `skip(имя, причина)`;
  - `finish()` выставляет код возврата;
  - фильтр `FORGE_TEST_ID` пропускает случаи, чьё имя не начинается с нужного ID.
- Фильтр `--id X` совпадает с ID, равным X, или начинающимся с `X-`. `--id WT-CLIP` берёт всю capability, `--id WT-CLIP-1` не захватывает WT-CLIP-10.
- Альтернатива: mini.test (вендорить, закрепить по коммиту). Отклонено:
  - проверки живут в трёх средах: LuaJIT в nvim, Lua 5.4 в WezTerm и bash 3.2/5, а mini.test покрыл бы только первую; для двух других всё равно нужен протокол;
  - изоляцию падений и зависаний, ради которой research предлагал mini.test, даёт граница процесса;
  - работа mini.test под `nvim -l` не проверена, а вендоринг — около 2 тыс. строк.
- Альтернатива: TAP как есть. Отклонено: существующий скрипт и соседние changes уже пишут `ok`/`FAIL`. Протокол — подмножество идей TAP, при нужде переводится одной функцией.

**3. Поддельный `wezterm` и загрузка конфига без GUI.**
- `tests/wezterm/fake_wezterm.lua` отдаёт `load_config{ triple, env, files }`. Функция делает `loadfile("wezterm.lua")` и через `setfenv` подставляет чанку окружение:
  - `require("wezterm")` → подделка;
  - `os` с поддельным `getenv` (значения из `env`, остальное — настоящий `os`);
  - `io` с `open` поверх таблицы файлов в памяти, записи перехватываются.
- `load_config` возвращает `config`, обработчики событий и журнал записей в файлы.
- Подделка:
  - конструкторы `act.*` возвращают данные `{ name, args }`;
  - `action_callback` возвращает `{ name = "Callback", fn }`;
  - `on` записывает обработчик;
  - `gui.default_key_tables()` отдаёт фикстуру;
  - `gui.screens()` и `mux` — записывающие заглушки;
  - поддельные окно и панель для колбэков записывают `perform_action`, отдают выделение и `active_key_table`.
- У каждого поддельного поведения в комментарии сказано, какое настоящее поведение 20240203 оно имитирует и где это проверено. Урок research: подделка установщика однажды закрепила неверное убеждение про код возврата `show-keys`.
- Фикстура `tests/wezterm/fixtures/default_key_tables.lua` снимается с настоящего бинарника:
  - обёртка из решения 7 запускается в процессе wezterm-gui (`show-keys`) и сериализует `wezterm.gui.default_key_tables()` в Lua-литерал;
  - в шапке фикстуры записано происхождение: версия WezTerm, тройка хоста, команда;
  - обновляется только через `--update-golden`.
- Юнит-уровень не касается диска: файлы — таблица в памяти, HOME — заведомо несуществующий путь.
- `loadfile` под LuaJIT заодно следит за подмножеством языка: синтаксис только Lua 5.4 (`//`, `<const>`, `goto` в неподходящем месте) падает здесь же.
- Альтернатива: юнит-проверки внутри WezTerm (Lua 5.4). Отклонено как основной путь: нужен `pcall` на всё и явный `os.exit`, нет поддельного окна, нет таймаута. Настоящий Lua 5.4 покрывает проверка загрузки из решения 7.
- Если `fix-copy-clobbers-clipboard` применён раньше, его подделка дополняется до этого описания, а не заводится вторая. Контракт его теста (`act.*` как данные, `action_callback`, `on`) — подмножество этого.

**4. Проверки по ID — файл на capability, характеризация базовой линии.**
- Файлы `tests/wezterm/{keyboard-protocol,key-ownership,clipboard,windows-mode,panes-tabs,scrollback,window-state,ui}.test.lua`. Каждая проверка — один сценарий требования с исходом, который виден в `config`, в таблицах клавиш, в действиях колбэка на поддельном окне или в записях в поддельные файлы. Обе тройки windows и macos гоняются в одном файле, где сценарий касается платформы — ещё и linux.
- Требование бывает одновременно AUTO и MANUAL. Пример WT-KBD-2: значение `enable_kitty_keyboard` проверяется автоматически, а то, что nvim получает `<C-.>`, — вручную. В отчёте видны обе части.
- Критерий MANUAL: исход зависит от кодировщика клавиш WezTerm, ConPTY, IME, буфера обмена ОС, оконной системы или отрисовки.
- Фаза 1: проверки описывают код как есть, включая известные баги. Например, WT-WIN-10 (`x` не выходит из режима) проверяется так, как написано в спеке. Change, который исправит поведение, правит проверку в том же коммите.
- Если проверка, написанная по сценарию, падает на текущем коде, это расхождение базовой линии. Проверку под код не подгоняют, а действуют по правилу фазы из `config.yaml`:
  - в фазе 1 правится спека, отдельным коммитом, с проверкой открытых delta по тому же ID (`review-baseline`, решение 7);
  - в фазе 2 это баг кода и отдельный change.
- Проверки пишутся по действующей спеке: `openspec/specs/` плюс delta тех changes, чьи задачи уже применены к коду, но ещё не заархивированы.

**5. Повторы (клавиша, модификаторы) — по исходнику, через подделку.**
- WezTerm при повторе молча оставляет последнюю запись, поэтому снимок `show-keys` повтор не покажет. Проверка идёт по `config.keys` и по каждой `config.key_tables.*` сразу после загрузки через подделку, для каждой тройки.
- Нормализация:
  - буква после `phys:` — в верхний регистр;
  - модификаторы — отсортированное множество, `nil`, `""` и `NONE` — одно и то же.
- Действия сравниваются структурно, колбэки — по идентичности.
- По WT-KEYS-8:
  - в `config.keys` и в таблицах windows, resize_pane и search_mode повторов нет вовсе;
  - в copy_mode разрешены только повторы с тем же действием, и их число сверяется с текстом требования.
- Альтернатива: проверка внутри настоящего WezTerm (прототип `dupcheck.lua`). Отклонено как второй путь к тому же: фикстура из решения 3 снята с того же бинарника, а одна реализация проще.

**6. Межслойная проверка WezTerm ↔ nvim_forge (WT-KEYS-4, WT-KEYS-6, WT-KEYS-7).**
- Сторона WezTerm — `config.keys` из подделки для каждой тройки. Таблицы режимов не входят: они активны только в режиме.
- Сторона nvim собирается помощником `tests/lib/nvim_keymaps.lua`:
  - запускается `nvim --clean --headless -i NONE` с XDG-каталогами в `.tests/sandbox/nvim`, с `nvim_forge` в runtimepath и лидером, как в `init.lua`;
  - вызываются `config.ru_keys.setup()`, `config.options`, `config.keymaps`, плагины не грузятся;
  - в JSON выводятся `nvim_get_keymap` по режимам и `keys` из `lua/plugins/*.lua`, прочитанные `dofile`.
- Обе стороны приводятся к одной записи nvim (`<C-S-f>`, `<D-A-l>`):
  - таблица имён: `phys:` по раскладке US-ANSI, CTRL→C, SHIFT→S, ALT→A, SUPER→D;
  - нормализация через `vim.fn.keytrans(vim.keycode(lhs))`;
  - правила собраны в `tests/lib/keynames.lua` и имеют самопроверку.
- Что проверяется:
  - пересечение совпадает с исключениями WT-KEYS-7: `<C-v>` на всех платформах и `<C-c>` на Windows, записаны в тесте со ссылкой на ID;
  - из `<C-S-…>` в nvim только F, P, E, D и F5, из `<D-…>` только `<D-A-l>`;
  - `<F13>` привязан в режимах n, i и x, а Ctrl+[ в WezTerm — `SendKey F13` (WT-KEYS-6).
- Ограничение: буферные привязки, привязки из `LspAttach` и из `config`-функций плагинов (например, `lsp.lua`) без плагинов не видны. Это записано в тесте и в `tests/README.md`.
- Альтернатива: полный конфиг с плагинами. Отклонено: сеть при старте (mason, treesitter), в research зависло, трогает живой `nvim_forge-data`.

**7. Настоящий бинарник: проверка загрузки (WT-LOAD-11).**
- Обёртка `tests/wezterm/guard.lua` работает внутри WezTerm, Lua 5.4:
  - берёт `FORGE_CONFIG` и `FORGE_TARGET` из окружения;
  - подменяет `wezterm.target_triple`, делает `pcall(dofile, FORGE_CONFIG)`;
  - при ошибке пишет `FORGE_CONFIG_ERROR: …` и выходит с кодом 3, при успехе пишет маркер `FORGE_CONFIG_OK <тройка>`;
  - всё тело обёрнуто в `pcall` и заканчивается явным `os.exit`.
- `tests/wezterm/config-loading.test.lua` проверяет:
  - (а) дословный контракт WT-LOAD-11 на файле репо для ОС хоста: `wezterm --config-file <репо>/wezterm.lua ls-fonts`, stdout не пуст, в stderr нет `ERROR`;
  - (б) обёртку для трёх троек: код 0 и маркер.
- HOME, USERPROFILE и XDG указывают в `.tests/sandbox/wezterm`, чтобы файл состояния владельца не влиял.
- Нет бинарника — SKIP с причиной.
- `ls-fonts`, а не `show-keys`: `show-keys` печатает встроенные привязки и молчит об ошибке (CLAUDE.md, «Проверки»).

**8. Снимки: `show-keys` по ОС и вся конфигурация из подделки.**
- `tests/wezterm/snapshot.test.lua` выполняет `wezterm --config-file tests/wezterm/guard.lua show-keys --lua` для каждой тройки. Нормализация:
  - буква после `phys:` — в верхний регистр;
  - `EmitEvent 'user-defined-N'` → `Callback`.
- Какой колбэк висит на какой клавише, снимок не хранит. Это закрепляют проверки решения 4.
- Порядок записей задаёт WezTerm (по коду клавиши), поэтому перестановка в исходнике снимок не меняет.
- Результат сравнивается с `tests/wezterm/golden/keys.{windows,macos,linux}.lua`.
- Второй снимок — `tests/wezterm/golden/config.{windows,macos,linux}.lua`. Это весь `config` из подделки плюс отсортированный список событий. Сериализация детерминирована: ключи отсортированы, функции заменены меткой. Он ловит изменения настроек, которых нет в `show-keys`: шрифт, цвета, протокол клавиатуры, `default_prog`.
- В шапке каждого эталона — происхождение: версия WezTerm, тройка, команда.
- `tests/wezterm/VERSION` = `20240203-110809-5046fc22`. Если `wezterm --version` другой, снимок `show-keys` получает SKIP с обеими версиями, а проверка загрузки и снимок конфигурации идут как обычно.
- `--update-golden` перезаписывает эталоны и фикстуру. Diff эталона входит в коммит вместе с изменением поведения.
- Снимок — детектор изменений, а не спека. Требования описывают правила, таблицы клавиш в спеку не копируются.

**9. Установщик macOS и другие shell-наборы — через реестр.**
- Для каждого shell-набора в реестре `run.lua` записаны окружение и способ запуска.
- `tests/install-macos.scenarios.sh`:
  - Windows — `wsl bash`, путь репо переводится через `wslpath`, для ветки bash 3.2 — `FORGE_BASH32=<путь в WSL>`, если задан;
  - macOS — `/bin/bash` (3.2) и `bash` из Homebrew, если есть;
  - Linux — `bash`;
  - нет среды — SKIP с причиной.
- Скрипт не меняется. Его ID не пишутся в имена проверок, а берутся из строк `Проверка: tests/install-macos.scenarios.sh (…)` в спеках. Статус этих ID — вердикт всего набора.
- `tests/wezterm-keys.scenarios.sh` из соседних changes, если он есть к моменту применения, регистрируется с окружением «bash + wezterm» (на Windows годится Git Bash).
- Trace падает, если в `tests/` есть `*.sh` или `*.test.lua` вне реестра.

**10. Trace — статические проверки и отчёт покрытия.**
- ID распознаются так: токен `<ОБЛАСТЬ>-<ПРЕФИКС>-<n>`, где область — первая часть ID из спек (сегодня `WT`, `MAC`).
- Известные ID:
  - заголовки `### Requirement:` в `openspec/specs/`;
  - ADDED-требования открытых changes (тест может появиться вместе с ещё не заархивированным требованием);
  - для строк FIXLOG ещё и требования из `openspec/changes/archive/` (снятые ID остаются резолвимыми).
- `tests/trace.test.lua` падает, если:
  - в файлах проверок, в чек-листах `tests/manual/*.md`, в тегах `-- spec: …` в `wezterm.lua` или в строках `Спека:` FIXLOG есть неизвестный ID;
  - путь `tests/…` в строке `Проверка:` спеки не существует или файл не в реестре;
  - пункт `вручную (tests/manual/<файл>, <пункт>)` не найден в чек-листе.
- Отчёт раннера даёт каждому ID из спек статус:
  - PASS — все его проверки `ok`;
  - FAIL;
  - SKIP;
  - MANUAL — с последней строкой `Проверено:` пункта, а если её нет — «не проверялось»;
  - UNCOVERED.
- В фазе 1 UNCOVERED не валит прогон, `--strict` включает это требование.
- Отдельным списком отчёт печатает ID, у которых есть автоматические проверки, но нет строки `Проверка:` в спеке.
- Формат чек-листов берётся у `review-baseline` (его design, решение 3): у пункта есть код (W1…, M1…) и ID требований, результат дописывается строкой `Проверено: <дата>, <ОС>, WezTerm <версия>, раскладка <…> — совпало | расходится: …`, последняя строка — текущий статус. Разбор сделан по этому контракту. Если файлов ещё нет, в отчёте нет MANUAL, и это сказано явно.

**11. Хук pre-commit — необязательный и явный.**
- `.githooks/pre-commit` — POSIX sh, работает в Git Bash и на macOS. Запускает `nvim -l tests/run.lua`, при FAIL коммит не проходит.
- Нет `nvim` в PATH — хук падает с подсказкой, а не пропускает молча.
- Включается на каждой машине один раз: `git config core.hooksPath .githooks`. Выключается: `git config --unset core.hooksPath`.
- Обход через `--no-verify` допустим: хук страхует от забывчивости.

**12. Наблюдаемость и ручной ремонт.**
- Человек видит:
  - в терминале — строки каждого файла и сводку по ID;
  - в `.tests/logs/<файл>.log` — полный вывод;
  - в `.tests/report.json` — происхождение (HEAD и признак грязного дерева, ОС, версии nvim и WezTerm) и статусы.
- Всё в `.tests/` производное: удаляется и пересобирается одной командой, в git не попадает.
- Ремонт одного места:
  - `nvim -l tests/run.lua --id WT-CLIP-2` — одно требование;
  - `nvim -l tests/wezterm/clipboard.test.lua` — один файл напрямую;
  - `--update-golden` — принять осознанное изменение, diff виден в git.

## Risks / Trade-offs

- [Подделка расходится с настоящим WezTerm] → Встроенные таблицы берутся из фикстуры, снятой с бинарника. Разбор и загрузку проверяет настоящий бинарник (решения 7 и 8). У каждого поддельного поведения записан источник.
- [LuaJIT против Lua 5.4: колбэки исполняются только под LuaJIT] → Верхний уровень конфига исполняет и настоящий Lua 5.4 (решение 7). Конфиг держится в общем подмножестве языка. Известные различия, например `string.format('%d', 1.5)`, перечислены в `tests/README.md`.
- [Виды macOS и Linux сняты с Windows-бинарника, а встроенные таблицы режимов могут зависеть от ОС сборки] → Владелец запускает `nvim -l tests/run.lua` на Mac, результат записывается в `tests/manual/wezterm-macos.md` (пункт-паспорт M0 у `review-baseline`). Если виды разойдутся — Open Questions.
- [Характеризация закрепляет известные баги] → Так и задумано в фазе 1. Change, меняющий поведение, меняет проверку в том же коммите (CLAUDE.md, правило 5).
- [Соседние changes раньше заведут подделку, `clipboard.test.lua` или shell-набор своей формы] → Первая задача apply сверяет, что уже есть в `tests/`, и сводит всё к одной подделке и одному реестру, а не заводит вторую копию.
- [Межслойная проверка не видит динамические привязки nvim] → Ограничение записано. Оставшаяся часть WT-KEYS-7 проверяется вручную.
- [`--update-golden` используют, чтобы «позеленить»] → Diff эталона всегда в том же коммите, что и изменение, и виден на ревью. `restructure-wezterm-config` запрещает его вовсе.
- [WSL нет или он медленный] → Набор установщика получает SKIP с причиной, в отчёте он не PASS. На macOS набор идёт нативно.
- [Хук обходят] → Принято. Хук — напоминание, а не защита от умысла.

## Migration Plan

- Переносить данные не нужно, добавляются файлы в `tests/` и `.githooks/`, в `.gitignore` строка `.tests/`.
- Порядок: каркас раннера → подделка и фикстура → проверки по capability → бинарник и снимки → установщик → trace → хук. На каждом шаге команда уже работает с теми наборами, что есть.
- Откат: удалить добавленные файлы. Хук выключается `git config --unset core.hooksPath`.
- На Mac после применения владелец один раз запускает ту же команду. Если версия WezTerm там другая, снимок `show-keys` получает SKIP, остальное идёт.
