# Spec Delta

## ADDED Requirements

### Requirement: WT-KBD-9 Объявление nvim_forge и подменные клавиши
nvim_forge SHALL объявлять себя терминалу пользовательской переменной панели `FORGE_NVIM` (последовательность OSC 1337 SetUserVar). Значение переменной — версия таблицы подмен. nvim_forge SHALL ставить её при запуске с интерфейсом в терминале и при возврате из приостановки и SHALL снимать (пустое значение) при выходе и перед приостановкой.

Терминал на Windows SHALL считать панель объявленной, только когда значение `FORGE_NVIM` совпадает с версией таблицы подмен в конфиге. При другом значении, пустом значении или без переменной подмены нет (WT-KEYS-10).

Каждая подменная клавиша SHALL доходить до nvim через ConPTY ровно одной клавишей. Эта клавиша одинакова на русской и английской раскладке и у каждого сочетания своя. Подменная клавиша SHALL NOT совпадать ни с одной клавишей, которую nvim на Windows получает от физического нажатия, в том числе от F-клавиш с модификаторами: они приходят как `<F13>`–`<F63>` (WT-KBD-6).

Для панели без объявления терминал SHALL повторять исходное нажатие так, чтобы программа получила то же, что без подмены: тот же код клавиши, скан-код, символ и модификаторы. Это касается и программы с VT-вводом через ConPTY, и программы, которая читает записи консоли (например, PSReadLine). Отличий два: правый Ctrl приходит как левый, а отпускание клавиши — сразу за нажатием. Колбэк привязки не знает, какой Ctrl нажат и когда клавишу отпустят.

nvim_forge объявляет себя на любой платформе, но вне Windows терминал объявление не использует. Объявление можно выключить на стороне nvim_forge — тогда nvim_forge получает эти сочетания так же, как nvim без объявления (WT-KBD-6).
Платформы: все
История: FIXLOG «WezTerm + nvim_forge: сочетания nvim_forge на Windows через подмену клавиш»
Проверка: tests/wezterm/conpty/chords.test.py (проба через conpty.dll: объявление, подменные клавиши, повтор нажатия) | вручную (windows; результат — в tests/manual/wezterm-windows.md)

#### Scenario: Объявление при запуске и снятие при выходе
- **GIVEN** Windows, в панели шелл, объявления нет
- **WHEN** пользователь запускает nvim_forge, а потом выходит из него (`:qa`)
- **THEN** пока nvim_forge работает, `FORGE_NVIM` у панели равна версии таблицы подмен
- **AND** после выхода значение пустое, и шелл получает сочетания WT-KEYS-10 без подмены

#### Scenario: Подменные клавиши различимы
- **GIVEN** Windows, в панели nvim, который объявил себя так же, как nvim_forge, но своих привязок не имеет (например, `nvim --clean` с одной командой объявления)
- **WHEN** пользователь на русской и на английской раскладке нажимает каждое сочетание WT-KEYS-10 и печатает полученную клавишу (`:lua print(vim.fn.keytrans(vim.fn.getcharstr()))`)
- **THEN** на каждое нажатие nvim получает ровно одну клавишу
- **AND** у разных сочетаний клавиши разные, на двух раскладках — одинаковые
- **AND** ни одна из них не совпадает с тем, что nvim получает от F1–F12 с Shift, Ctrl, Alt и их сочетаниями, и от сочетаний из WT-KBD-6

#### Scenario: Другая версия таблицы
- **GIVEN** Windows, программа в панели объявила `FORGE_NVIM` со значением, которое не совпадает с версией таблицы в конфиге (например, nvim_forge со старой таблицей на удалённой машине по ssh)
- **WHEN** пользователь нажимает Ctrl+Shift+F
- **THEN** подмены нет, программа получает исходное нажатие (WT-KBD-6)

#### Scenario: Повтор исходного нажатия для программы без объявления
- **GIVEN** Windows, две панели без объявления: в одной pwsh с PSReadLine, в другой программа с VT-вводом (Claude Code или `nvim --clean`)
- **WHEN** пользователь на обеих раскладках нажимает левым Ctrl каждое сочетание WT-KEYS-10
- **THEN** программа с VT-вводом получает те же байты, что без подмены
- **AND** PSReadLine получает ту же запись нажатия (код клавиши, скан-код, символ, модификаторы), а запись отпускания — сразу за ней
- **AND** проба через conpty.dll сверяет это по каждому сочетанию

#### Scenario: Правый Ctrl в повторе
- **GIVEN** Windows, в панели без объявления программа, которая читает записи консоли и различает правый и левый Ctrl
- **WHEN** пользователь нажимает сочетание WT-KEYS-10 правым Ctrl
- **THEN** программа получает запись с признаком левого Ctrl: это известное отличие повтора от прямого нажатия

#### Scenario: Объявление выключено
- **GIVEN** Windows, в nvim_forge выключено объявление (настройка nvim_forge)
- **WHEN** пользователь нажимает Ctrl+Shift+F
- **THEN** WezTerm ничего не подменяет, nvim_forge получает `<C-f>`, как в WT-KBD-6

#### Scenario: Объявление на macOS ни на что не влияет
- **GIVEN** macOS, kitty включён, nvim_forge объявил себя
- **WHEN** пользователь нажимает Ctrl+Shift+F
- **THEN** nvim получает `<C-S-f>` по kitty (WT-KBD-2), WezTerm ничего не подменяет

## MODIFIED Requirements

### Requirement: WT-KBD-6 Что получает nvim на Windows
На Windows nvim SHALL получать клавиши в том виде, в каком их переводит ConPTY, без kitty; это ограничение, а не цель. nvim спрашивает о kitty (`CSI ?u`), ответа не получает (WT-KBD-1) и включает modifyOtherKeys (`CSI >4;2m`). Запрос проходит через ConPTY в WezTerm, но набираемые клавиши это не меняет: они идут записями win32-input-mode, и в последовательности для nvim их переводит ConPTY (modifyOtherKeys влияет только на клавиши, которые WezTerm шлёт сам, WT-KBD-7). Сочетания, которых нет в классической кодировке, до nvim отдельными клавишами не доходят: nvim видит их как другие клавиши и выполняет привязки на этих клавишах, а часть сочетаний не получает вовсе. Исключение — nvim_forge, объявивший себя (WT-KBD-9): сочетания из таблицы WT-KEYS-10 WezTerm ему подменяет, и nvim_forge их различает. Всё, что ниже сказано про эти сочетания, относится к nvim без объявления (например, `nvim --clean`) и к nvim_forge, чьё объявление терминал не принял: другая версия таблицы или объявление выключено.
Платформы: windows
История: FIXLOG §41, «nvim_forge: мёртвые привязки Ctrl+V удалены, вставку делает WezTerm», «WezTerm + nvim_forge: сочетания nvim_forge на Windows через подмену клавиш»

#### Scenario: Ctrl+Shift+буква неотличима от Ctrl+буквы
- **GIVEN** Windows, в панели nvim без объявления (например, `nvim --clean`), любая раскладка
- **WHEN** пользователь нажимает Ctrl+Shift+F, Ctrl+Shift+P, Ctrl+Shift+E или Ctrl+Shift+D
- **THEN** nvim получает `<C-f>`, `<C-p>`, `<C-e>` и `<C-d>` — ровно то же, что от Ctrl+буквы
- **AND** в nvim_forge, объявившем себя, эти сочетания выполняют свои действия (панель поиска, палитра, проводник, отладка — WT-KEYS-10), а не действия Ctrl+буквы (поиск по буферу, поиск файла, фокус проводника, прокрутка на полэкрана)

#### Scenario: Enter и точка с модификаторами
- **GIVEN** Windows, в панели nvim без объявления
- **WHEN** пользователь нажимает Shift+Enter, Ctrl+Enter и Ctrl+.
- **THEN** nvim получает `<CR>`, `<NL>` и `<C-n>`
- **AND** `<NL>` для nvim — та же клавиша, что `<C-j>`
- **AND** в nvim_forge, объявившем себя, Ctrl+Enter и Ctrl+. подменяются (WT-KEYS-10), и нижняя панель по Ctrl+Enter не переключается; Shift+Enter и там приходит как `<CR>`, привязки `<S-CR>` у nvim_forge нет

#### Scenario: Ctrl+Space не доходит
- **GIVEN** Windows, nvim без объявления в режиме вставки
- **WHEN** пользователь нажимает Ctrl+Space
- **THEN** nvim не получает ничего
- **AND** в nvim_forge, объявившем себя, Ctrl+Space подменяется и вызывает автодополнение (WT-KEYS-10)

#### Scenario: Ctrl+знак препинания на русской раскладке
- **GIVEN** Windows, активна русская раскладка, nvim_forge объявил себя, нормальный режим
- **WHEN** пользователь нажимает Ctrl + физическую `;`, затем Ctrl + физическую `/`
- **THEN** на Ctrl+; nvim получает `<C-v>` и включает блочное визуальное выделение — встроенное значение `<C-v>`: Ctrl+; не подменяется, а своих привязок `<C-v>` у nvim_forge нет (WT-KEYS-7)
- **AND** Ctrl+/ подменяется (WT-KEYS-10) и переключает комментарий
- **AND** nvim без объявления получает на эти два сочетания `<C-v>` и `<C-n>`

#### Scenario: F-клавиши с модификаторами приходят под другими номерами
- **GIVEN** Windows, в панели nvim без объявления, `TERM=xterm-256color` (умолчание WezTerm)
- **WHEN** пользователь нажимает Shift+F5, Ctrl+F5 и Ctrl+Shift+F5
- **THEN** nvim получает `<F17>`, `<F29>` и `<F41>`, а не `<S-F5>`, `<C-F5>` и `<C-S-F5>`
- **AND** в nvim_forge, объявившем себя, Ctrl+Shift+F5 подменяется и перезапускает сессию DAP (WT-KEYS-10), а Shift+F5 и Ctrl+F5 приходят как `<F17>` и `<F29>`, как и без объявления

#### Scenario: Что доходит различимо
- **GIVEN** Windows, nvim в панели
- **WHEN** пользователь нажимает Tab, Shift+Tab, Ctrl+PageUp, Ctrl+PageDown, Alt+букву, Ctrl+букву или Shift+кириллическую букву
- **THEN** nvim получает `<Tab>`, `<S-Tab>`, `<C-PageUp>`, `<C-PageDown>`, `<M-буква>` (буква текущей раскладки, WT-KBD-4), `<C-буква>` (латинская буква этой клавиши и на русской раскладке) и заглавную кириллическую букву текстом
- **AND** F13, который WezTerm шлёт вместо Ctrl+[ (WT-KEYS-6), приходит как `<F13>`

### Requirement: WT-KBD-7 Клавиши, которые WezTerm отправляет сам
Клавиши, которые WezTerm отправляет программе от себя, терминал SHALL кодировать xterm-кодировкой независимо от kitty и win32-input-mode. Таких клавиш две, если не считать подмен для nvim_forge на Windows: F13 вместо Ctrl+[ (WT-KEYS-6) и Ctrl+C без выделения на Windows (WT-CLIP-2). Как кодируются подменные клавиши и повтор исходного нажатия для панели без объявления, задаёт WT-KBD-9. F13 всегда уходит как `CSI 25~`. Ctrl+C уходит байтом 0x03, а если программа включила modifyOtherKeys в режиме 2 (`CSI >4;2m`; на Windows так делают nvim и Claude Code, запрос проходит через ConPTY), — как `CSI 27;5;99~`. modifyOtherKeys WezTerm принимает всегда, от конфига это не зависит. На Windows ConPTY переводит обе формы для программы: nvim получает `<C-c>` и `<F13>`.
Платформы: все
История: FIXLOG §17, §31, «WezTerm + nvim_forge: сочетания nvim_forge на Windows через подмену клавиш»

#### Scenario: Ctrl+C без выделения в nvim на Windows
- **GIVEN** Windows, nvim в панели (включил modifyOtherKeys), выделения WezTerm нет
- **WHEN** пользователь нажимает Ctrl+C
- **THEN** WezTerm шлёт `CSI 27;5;99~`, и nvim получает `<C-c>`

#### Scenario: Ctrl+C без выделения в шелле на Windows
- **GIVEN** Windows, в панели шелл без modifyOtherKeys, выделения нет
- **WHEN** пользователь нажимает Ctrl+C
- **THEN** WezTerm шлёт 0x03, и шелл получает прерывание

#### Scenario: F13 на Windows
- **GIVEN** Windows, nvim в панели
- **WHEN** пользователь нажимает Ctrl+[
- **THEN** WezTerm шлёт `CSI 25~`, и nvim получает `<F13>`

#### Scenario: F13 в kitty-программе на macOS
- **GIVEN** macOS, nvim с включённым kitty
- **WHEN** пользователь нажимает Ctrl+[
- **THEN** WezTerm шлёт `CSI 25~`, а не kitty-последовательность, и nvim получает `<F13>`
