# Design

## Context

Мотивация — в proposal.md (Why). Здесь состояние файла и ограничения.

**Класс задачи:** рефакторинг под защитой характеризационных тестов (golden master). Образцы:
- «Strangler»-подход — перестройка шагами, каждый с зелёными тестами;
- approval-тесты как гейт «вывод не изменился».

Полное переписывание отклонено всеми четырьмя исследованиями (research: wezterm-audit, critic). Прошлые баги (§41, §42, маска IME) сидели в семантике протоколов, а не в устройстве кода, и выстраданные решения теряются при переписывании.

**Состояние `wezterm.lua`** (рабочее дерево 2026-09-27):
- 786 строк, из них 318 строк комментариев;
- `config.keys` пишут литерал в строке 341, `table.insert` в строках 369 и 383–392 и помощник `map()` (стр. 427), который вызывается блоками до конца файла;
- `config.key_tables` собираются в строках 514–702, среди них `table.insert` в `windows`;
- `is_windows` проверяется в строках 24, 116, 118, 128, 163, 181, 368, 391, 736;
- внешний мир читается в строках 35 и 606 (`home_dir`/`USERPROFILE`), 44, 79 и 613 (`io.open`), 115–119 (PATH).

**Ограничения:**
- WT-LOAD-1: конфиг — ОДИН файл `wezterm.lua` в корне репо, подключается ссылкой или переменной (WT-LOAD-3/4/13). Всё, что меняет путь или число файлов, меняет спеку.
- `wezterm.config_builder()` в 20240203 строгий: неизвестные поля конфига — ошибка. Значит, «выставить внутренности для тестов» через поле конфига нельзя. Тесты достают колбэки через привязки и события, как это уже делает подделка из `add-wezterm-spec-checks`.
- Проверки из `add-wezterm-spec-checks`:
  - проверки по ID через подделку для троек windows и macos;
  - снимки `show-keys --lua` и всей конфигурации для трёх троек (`tests/wezterm/golden/`);
  - trace тегов `-- spec:`.

  Снимок `show-keys` упорядочен по коду клавиши, а колбэки в нём заменены на `Callback`. Поэтому перестановка записей в исходнике и перенумерация колбэков снимок не меняют, а любое смысловое изменение меняет.
- Задачи открытых changes ссылаются на нынешние имена: `copy_selection_or`, `to_phys_binding`, `map(`, `exe_in_path`, `change_font_size`, `save_window_size`, `scrollback_to_nvim`.

## Goals / Non-Goals

**Goals:**
- Ответ на вопрос «что перехватывает терминал» даёт одна секция файла, «чем ОС отличаются» — пометки в записях этой секции и одна секция фактов о платформе.
- Каждый колбэк — именованная функция, которая зависит только от своих аргументов, фактов о платформе и явно переданных путей.
- Код требования находится поиском `grep 'spec: <ID>' wezterm.lua`, и trace держит теги в согласии со спеками.
- После каждого шага эталоны побайтно прежние. Регресс виден механически, а не на ревью глазами.

**Non-Goals:**
- Разбиение на модули и смена способа подключения (WT-LOAD-1/3/4/13, установщики). Это отдельный change с delta, см. Open Questions.
- Исправления поведения. Их делают changes `fix-windows-mode-modality`, `change-search-enter-accept`, `fix-copy-clobbers-clipboard`, `resolve-key-ownership-conflicts`, `fix-window-state-new-windows`, `fix-ui-robustness`.
- Исправление неверных комментариев, то есть 14 divergences `sync-docs-with-baseline`. Здесь комментарии только сокращаются до ссылок, и только после его применения.
- Самопроверка во время работы: `validate()` с `log_error`, бейдж «CFG!», `log_warn` в молчаливых `pcall`. Бейдж — это поведение WT-UI-12, нужен отдельный change.
- Генерация таблиц `docs/WEZTERM.md` из таблицы привязок.
- Новые тесты сверх проверки тегов. Покрытие по ID — забота `add-wezterm-spec-checks`.

## Decisions

**1. Гейт каждого шага — «эталоны не изменились».** Шаг — отдельный коммит. После него обязательно:
- `nvim -l tests/run.lua` выходит с кодом 0: проверки по ID, снимки `keys.*` и `config.*` для трёх троек, trace;
- `git status --porcelain tests/` пуст;
- `--update-golden` не применяется ни разу.

Любой diff эталона значит, что шаг изменил поведение. Такой шаг откатывается и делится мельче, эталон не принимается. В сообщении коммита — «поведение не меняется, эталоны без изменений» и что перенесено.
- Альтернатива: проверять только проверки по ID. Отклонено: они покрывают сценарии спек, а снимок конфигурации ловит любое поле, в том числе то, о котором спека молчит.

**2. Один файл, секции в порядке зависимостей.** Порядок секций:
1. шапка: как подключён конфиг, оглавление секций, где спеки и проверки;
2. факты о платформе;
3. файл состояния: чтение и запись;
4. настройки, сгруппированные по capability (протокол клавиатуры, вид, шелл);
5. действия и колбэки;
6. привязки `config.keys`;
7. таблицы режимов (`windows`, `resize_pane`; перевод `copy_mode` и `search_mode` плюс замены);
8. сборка;
9. события.

Каждая секция читается сама по себе: она использует только то, что определено выше.
- Альтернатива: каталог `wezterm/` с модулями `forgeterm/{platform,window_state,keymap,actions,status}` (research: wezterm-audit). В этом change отклонено по трём причинам:
  - по WT-LOAD-1 это изменение спеки, а change без delta его не несёт;
  - нужна смена подключения на трёх ОС (Open Questions);
  - тестам разбиение не нужно: подделка грузит файл целиком.

  Секции нарезаны по тем же границам, что и модули из research. Если разбиение понадобится, секция станет модулем без переделки.

**3. Факты о платформе — одна таблица, читается один раз.**
- Секция строит `platform`:
  - ОС (`windows | macos | linux` из `target_triple`);
  - домашний каталог (`home_dir`, иначе `USERPROFILE`);
  - разделители путей;
  - найденный шелл (поиск по PATH, `exe_in_path`).
- Только здесь читаются `target_triple`, `home_dir`, `os.getenv` и PATH. Остальной код берёт `platform.*`.
- Энтропия файла сведена в одно место, подделка подменяет её тем же способом, что и сейчас (тройка и окружение), поэтому тесты не меняются.
- Условия переносятся дословно: «не Windows» остаётся «не Windows» (macOS и Linux), а не превращается в «macOS». Снимок linux это проверяет.

**4. Таблица привязок — записи, один сборщик.**
- Все сочетания вне режимов добавляются в одной секции вызовами `map(key, mods, action, opts)`, по записи на строку, с тегом в конце. Имя `map` сохраняется, на него ссылаются задачи соседних changes.
- `map` дописывает запись в локальный список, а не в `config.keys`.
- `opts.os` повторяет нынешнее условие платформы (`"windows"` или `"not_windows"`).
- Семейства (вкладки 1…9, шрифт с Ctrl и Super, с Shift и без) строятся циклами, которые тоже вызывают `map`.
- После секции одна строка: `config.keys = build_keys(bindings, platform)`. Сборщик отфильтровывает записи по ОС и отдаёт WezTerm только `key`, `mods` и `action`.
- Таблицы `windows` и `resize_pane` собираются так же, помощником для таблиц режимов.
- Альтернатива: поле `spec = "WT-…"` в записи. Отклонено:
  - поле пришлось бы вырезать в сборщике: примет ли WezTerm лишнее поле в записи привязки, не проверялось;
  - тестам оно всё равно недоступно: конфиг не может отдать наружу внутренности;
  - тег-комментарий виден grep'у, и его проверяет trace.
- Альтернатива: одна литеральная таблица `{ … }` без `map`. Отклонено: семейства пришлось бы склеивать после литерала, и появился бы второй способ добавить привязку.

**5. `copy_mode` и `search_mode` — встроенные таблицы плюс явные замены.**
- Перевод `to_phys_binding` над `wezterm.gui.default_key_tables()` остаётся, имя сохраняется.
- Дописки `/`, `n`, `N` и будущие замены соседних changes (`y`, Enter) оформляются записями «заменить пару», а не «дописать». Так решили и `change-search-enter-accept`, и `fix-copy-clobbers-clipboard`: при повторе WezTerm молча оставляет последнюю запись.
- Запасная ветка `pcall` (встроенных таблиц нет) сохраняется как есть.
- Альтернатива: написать таблицы руками. Отклонено: расхождение со встроенными при обновлении WezTerm, соседние changes отклонили это по той же причине.

**6. Колбэки — именованные функции с явными входами.**
- Встроенные в выражения колбэки выносятся в именованные локальные функции в секции действий: копирование, размер шрифта, сохранение размера, `gui-startup`, готовый лэйаут, запросы переименования и воркспейса, выгрузка истории, бейдж.
- Входы функции:
  - аргументы WezTerm (`window`, `pane`, `line`);
  - `platform`;
  - явные пути (файл состояния, файл выгрузки).
- Уже существующие имена (`copy_selection_or`, `change_font_size`, `save_window_size`, `ready_layout`, `scrollback_to_nvim`, `read_saved_size`, `center_on_active_screen`) не меняются.
- Крюков для тестов в конфиге нет: строгий `config_builder` не даёт для них места. Тесты достают колбэк через привязку или событие.

**7. Теги `-- spec:` и комментарии.**
- Формат тега: `-- spec: WT-CLIP-2` или `-- spec: WT-CLIP-2, WT-CLIP-5`, в конце строки записи или над группой настроек.
- Каждая строка с вызовом `map(`, помощника таблицы режима или записи-замены несёт тег.
- `tests/trace.test.lua` получает проверку: строка с таким вызовом без тега — FAIL с номером строки. Неизвестный ID и так FAIL (`add-wezterm-spec-checks`, решение 10).
- Комментарий-обоснование или история, содержание которых уже есть в требовании или в записи FIXLOG, заменяется тегом и строкой `История: FIXLOG §N`.
- Знание, которого нет ни в спеке, ни в FIXLOG, остаётся комментарием у кода. Новые записи FIXLOG ради переноса не заводятся: FIXLOG — журнал инцидентов.

**8. Порядок относительно других changes.**
- Change, чьи задачи по `wezterm.lua` начаты, но не закончены (в `tasks.md` есть и `[x]`, и `[ ]`), доводится до конца до начала перестройки.
- Change, не начатый вовсе, может применяться и после неё. Его задачи описывают поведение и ID, имена функций сохранены (решения 4–6), а код требования находится по тегу.
- Рекомендуемый порядок — после изменений поведения. Это последний этап из research (critic, Ф3): перестройка файла, который уже не меняется.
- Шаг с комментариями (решение 7, вторая часть) идёт только после применения `sync-docs-with-baseline`, иначе оба правят одни и те же строки. Остальные шаги от него не зависят.
- Альтернатива: перестройка до исправлений, чтобы исправления шли уже по таблице. Отклонено как правило по умолчанию: сейчас у семи changes задачи написаны под нынешнее устройство. Но и не запрещено, при этом условии.

**9. Подмножество языка.** Код остаётся в пересечении LuaJIT (подделка под `nvim -l`) и Lua 5.4 (WezTerm): без `//`, битовых операторов, `<const>` и `<close>`, без `%d` с дробным числом. Подделка ловит синтаксис Lua 5.4, настоящий бинарник — остальное на верхнем уровне (проверка загрузки в `add-wezterm-spec-checks`).

## Risks / Trade-offs

- [Снимок не показывает, какой колбэк висит на какой клавише, там только `Callback`] → Это закрепляют проверки по ID (копирование, шрифт, лэйаут, выгрузка). Снимок конфигурации показывает наличие и место колбэка.
- [Запасная ветка без встроенных таблиц не входит в обычный прогон] → В шаге 3 разовая проверка: подделка с бросающим `gui.default_key_tables` грузит конфиг без ошибки. Команда и результат записываются в заметки apply.
- [Смена условия платформы при переносе (Linux)] → Эталоны linux входят в гейт.
- [Соседний change применяется после перестройки и не находит код по старым строкам] → Имена сохранены, теги есть, задачи соседей ссылаются на ID. Номера строк в их design устареют, это принято.
- [Порядок полей или событий влияет на результат (поздняя запись перекрывает раннюю)] → Снимок конфигурации сравнивает итоговые поля и список событий.
- [Нативный вид macOS не проверяется на Windows] → После применения владелец запускает `nvim -l tests/run.lua` на Mac и перечитывает конфиг там (задача 7.2).
- [Файл остаётся длинным] → Длина не цель. Цель — чтобы секции читались по отдельности. Разбиение — по условиям из Open Questions.

## Migration Plan

- Путь и число файлов не меняются, установщики и переменные окружения не трогаются. Работающий WezTerm подхватит правку при перечитывании (WT-LOAD-14) или по Ctrl+Shift+R.
- Порядок шагов: платформа → колбэки → привязки → таблицы режимов → теги → комментарии. Каждый шаг — коммит, гейт из решения 1.
- Откат: `git revert` коммита шага. Эталоны при этом не трогаются, они не менялись.
- Mac: `git pull`, перечитывание конфига и `nvim -l tests/run.lua` — задача 7.2.

## Open Questions

- **Разбиение на модули** — отдельный change, если появится конкретный повод. Поводы:
  - у секции появился второй потребитель;
  - кода без комментариев стало больше ~600 строк;
  - нужна проверка внутренностей, недоступных через привязки и события.

  Ответ не меняет задачи этого change: секции нарезаны по границам будущих модулей. Ограничения, проверенные research по исходнику 20240203 и прототипом:
  - в `package.path` нет каталога самого конфига. Там только `~/.config/wezterm`, `~/.wezterm`, каталог exe (Windows), `XDG_CONFIG_DIRS` (unix), каталог плагинов и `.\?.lua` от текущего каталога;
  - `wezterm.config_dir` — это родитель файла в том виде, как его открыли, без раскрытия симлинка. Поэтому входной файл первой строкой добавляет `wezterm.config_dir` в начало `package.path`;
  - на macOS и Linux симлинком становится КАТАЛОГ `~/.config/wezterm` → `<репо>/wezterm`, существующий каталог уходит в бэкап;
  - на Windows `WEZTERM_CONFIG_FILE` = `<репо>\wezterm\wezterm.lua`;
  - установщик проверяет загрузку по пути, который WezTerm реально откроет;
  - обёртка `tests/wezterm/guard.lua` добавляет в `package.path` каталог `FORGE_CONFIG`;
  - модули лежат в пространстве `forgeterm/`, чтобы не столкнуться с `~/.config/wezterm`;
  - подгруженные через `require` файлы WezTerm сам добавляет в список автоперечитывания.

  Такой change несёт MODIFIED WT-LOAD-1, WT-LOAD-3, WT-LOAD-4, WT-LOAD-13 и задачи в установщиках, согласованные с `fix-macos-installer` и `add-linux-installer-parity`.
- **Самопроверка конфига во время работы:**
  - `log_warn` в молчаливых `pcall`: битый файл состояния, `gui-startup`, встроенные таблицы;
  - `validate()` с `log_error`;
  - бейдж «CFG!».

  Отдельный change, бейдж — delta к WT-UI-12. От ответа задачи этого change не зависят.
- **Таблицы клавиш `docs/WEZTERM.md`** — генерировать из таблицы привязок или из снимка, или сверять с ними. Решается после `sync-docs-with-baseline`.
