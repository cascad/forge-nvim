# forge-nvim — правила работы в репо

Отвечай по-русски. Комментарии в коде, FIXLOG и спеки — по-русски.

Владелец 2026-10-31 явно разрешил глобально запускать OpenSpec через
`npx.cmd --yes @fission-ai/openspec@1.13.2` с необходимыми подкомандами.
Не запрашивать повторное согласие на эту команду в рамках работы.
Технические ограничения среды и обязательные escalation-запросы сохраняются.

Владелец также явно разрешил необходимые запуски Neovim, тестов, Docker и
явную подготовку тестовых зависимостей. Повторного разговорного согласования
не нужно. Диалог среды разрешений не равен вопросу о намерении владельца:
не обещать, что запись правила отменит все будущие системные запросы.

Уточнение 2026-11-01 после инцидента Docker: разрешение на container-тесты
не означает автоматическое управление Docker Desktop/WSL. Агент не запускает,
не перезапускает и не останавливает Desktop/WSL, не ремонтирует IPC и не меняет
внешние настройки ради очередного теста без отдельного явного поручения.
Если engine недоступен — продолжать независимые Windows-проверки и сообщить
ограничение Ubuntu. Уже запущенный разрешённый engine можно использовать для
тестов; test runner не должен сам поднимать Desktop.
Текущее явное поручение владельца «настроить заново / на чистый» разрешает
разовую настройку чистого Docker; это не разрешение на будущие автозапуски.
Старый диск F:/wsl/DockerDesktopWSL/disk/docker_data.vhdx сохраняется: выбор
чистого окружения не является разрешением удалять старые данные других проектов.

2026-11-01 владелец поручил самостоятельно коммитить завершённые и
проверенные шаги, затем продолжать docs/IDE_ROADMAP.md без отдельного
«давай дальше». Вместе с исправлением сохранять E2E, FIXLOG/HISTORY,
команды и точные ограничения проверок. Новые найденные проблемы заносить
в очередь со стабильными ID; не выдавать зелёный повтор за причину/фикс.
После сообщения о переключении permissions в Full access сначала выполнять
обычный запуск (use_default), не переносить require_escalated автоматически
из прежних вызовов. Эскалация — только при фактической необходимости среды.

Уточнение владельца 2026-11-10: использовать готовые LSP/backend; не строить
собственный language server, SQL binder/index или существенный private fork
ради полноты матрицы. Ограничение инструмента остаётся явным, фича не закрывается
текстовым fallback. Собственный SQL references prototype отменён. Перед
рефакторингом обязателен большой обзор фич, плагинов, обёрток и backports
(IDE-080, docs/FEATURE_REVIEW.md): ценность, пересечения, стоимость и варианты
убрать/заменить/упростить. Runtime не переписывается до такого обзора. Ранее
принятые узкие backports тоже входят в review с причиной, regression и условием
удаления; их не удаляют автоматически вместе с прототипом.

Уточнение владельца 2026-11-12 имеет приоритет над прежним автономным режимом:
бесконечный goal остановлен. Работаем по одному конкретному пункту очереди,
с обозначенным результатом; один прогон нужных тестов за итерацию, затем
отчёт и commit при успехе. Уточнение владельца в продолжении 2026-11-12:
завершённые шаги коммитить самостоятельно и переходить к следующему пункту
плана. Остановиться, когда план закончен, остаются только натурные проверки
владельца или нет продвижения; явно сообщить причину. При FAIL сохранить
результат и сообщить, что осталось; не повторять прогоны до зелёного.
Новый бесконечный goal не создавать. E2E обязательны для фич/фиксов.
Перед отдельным развитием тестовой инфраструктуры нужен понятный владельцу
план прогресса. Черновик E2E-каталога отложен, текущий приоритет — продукт.

## Где что лежит (один источник на каждый вопрос)

| Вопрос | Источник |
|---|---|
| Как фича работает | `openspec/specs/<capability>/spec.md` |
| Что решено поменять / какие баги известны | `openspec/changes/<id>/` — proposal + delta к спеке |
| Что ломалось, почему, как чинили | `nvim_forge/FIXLOG.md` — журнал, только дописывается |
| Единая хронология, включая прежнюю папку | `docs/HISTORY.md`; источники импорта — `docs/history/` |
| Новые жалобы и хотелки | `PROBLEMS.md` — инбокс |
| Как пользоваться (для человека) | `docs/*.md`, README — производные |

Формат спек, роли артефактов и текущая фаза — `openspec/config.yaml`.
Спеками покрыты WezTerm (`wezterm.lua`) и установщик macOS
(`openspec list --specs`); базовая линия nvim_forge ещё не снята.
Первые требования IDE-BOOT-1/2 находятся в change make-editor-startup-passive.

## Кто прав при расхождении (жизненный цикл)

- **Сейчас — фаза 1, «базовая линия».** `openspec/specs/` сняты с кода и
  описывают его КАК ЕСТЬ. Источник правды — код; README и docs — тоже
  производные от кода. Спека не совпала с кодом → чинится спека.
- **Фаза 2, «источник правды»** — после того как владелец проверит
  базовую линию (change `review-baseline`; строка «ТЕКУЩАЯ ФАЗА» в
  `openspec/config.yaml`). Тогда спека —
  намерение владельца, код, расходящийся с ней, — баг, а README и docs
  производны от спеки.
- В обеих фазах всё, что решено поменять, и найденные баги — это
  `openspec/changes/<id>/` с delta (MODIFIED/ADDED/REMOVED). Пока change
  не применён (`/opsx:apply`) и не заархивирован (`/opsx:archive`),
  specs/ не меняются.

## Правила

1. **Поведение меняется только через change** (`/opsx:propose`) и с
   явного согласия владельца. В фазе 2 не правь `openspec/specs/`, чтобы
   код или тест «прошли».
2. **Баг.** Найди требование (ID вида `WT-CLIP-1`) и открытые changes по
   нему → сверь с кодом (код требования: `grep -n 'spec: <ID>' wezterm.lua`);
   его проверки: `nvim -l tests/run.lua --id <ID>`:
   - (фаза 2) код нарушает спеку → чини код; в FIXLOG `Спека: <ID> (FIX)`;
   - спека молчит → сначала сценарий в change (ADDED/MODIFIED), потом код.
3. **Прежде чем «чинить» странность** — проверь `openspec/changes/`:
   возможно, это уже известный баг или принятое решение.
4. **PROBLEMS → FIXLOG.** Разобранный пункт из `PROBLEMS.md` чинится, в
   `nvim_forge/FIXLOG.md` добавляется нумерованная запись
   `Проблема → Причина → Изменение → Проверка/e2e → Вывод → Файлы`
   (+ `Спека:` если задето
   поведение), а сам пункт уезжает в карту разобранного внизу
   `PROBLEMS.md` со ссылкой на §.
   Каждое исправление получает такую историю, включая неудачные попытки,
   если они объясняют итог. Причина и гипотеза различаются; непроверенные
   платформы не объявляются проверенными. Шаблон —
   `docs/history/ENTRY_TEMPLATE.md`; хронологию `docs/HISTORY.md` обновлять
   вместе с записью. Старые записи не переписывать: уточнение — новым §.
5. **Доказательства — в репо.** Проверка, которая что-то доказала,
   кладётся в `tests/` в том же коммите. Иначе в FIXLOG пиши
   «Проверено вручную: как, где».
6. **Меняешь поведение — обнови всё, что его описывает** в том же
   изменении: спеку (через change), docs, FIXLOG.
7. **Универсальность (решение владельца 2026-10-31).** Windows, macOS и
   Ubuntu — активные целевые среды; Mint временно отложен. Общие сценарии IDE и хоткеи
   едины; системные пути, shell, процесс/PTY, clipboard и установка вынесены
   на границы. Целевая структура — `docs/PORTABLE_ARCHITECTURE.md`.
8. **E2E (решение владельца 2026-10-31).** Каждая фича получает e2e,
   каждый исправленный баг — постоянный регрессионный e2e с исходным
   воспроизведением. Unit/проверка настроек не заменяют пользовательский
   сценарий. В change нужны тест и результаты на применимых целевых ОС;
   нет VM/GUI — явно непроверено, не PASS. Владелец обеспечивает и запускает
   VM/машину; Windows проверяем нативно, Ubuntu headless — в Docker на Windows,
   macOS — отдельно на Mac. Команды — `scripts/test.ps1` / `scripts/test.sh`
   и `docker compose -f tests/containers/compose.yaml run --build --rm ubuntu full`.
   Границы проверок,
   покрытие и ещё не реализованные части — `tests/e2e/README.md`.
   На этом Windows-хосте тяжёлые Windows и Ubuntu-Docker регрессы выполнять
   поочерёдно: совместный прогон 2026-11-02 замедлил Ubuntu full с 303 до
   612 секунд и содержал IDE-042 (60s timeout). Причина самого timeout не
   установлена; порядок запуска — ограничение нагрузки, не runtime fix.
   Лёгкие независимые чтения/проверки можно группировать; на разных машинах
   это ограничение не требуется.
9. **Временные данные (решение владельца 2026-11-01).** Windows-тесты не
   заполняют системный C:. Runtime редактора создаётся в `.tests/tmp` на диске
   checkout (здесь F:); `scripts/test.ps1` задаёт там TEMP/TMP/TMPDIR для своего
   процесса и восстанавливает окружение после запуска. При прямом запуске
   тестов агент задаёт те же переменные перед `nvim`; другие команды агента,
   создающие temp (Python, npx и т.п.), тоже используют F:; для npx агент задаёт
   `npm_config_cache=F:/forge-nvim-tmp/npm-cache` в окружении команды. Профили очищаются после
   сохранения артефактов и при ошибке подготовки. На macOS/Linux по умолчанию
   используется native temp; `FORGE_TEST_TMPDIR` задаёт абсолютный override.
   Windows Go cache переиспользуется в `.tests/tmp/go-build-cache`; старые
   данные C: перенесены с журналом в `F:/forge-nvim-tmp/`, вне checkout.

## OpenSpec: штатные команды (Claude Code)

- `/opsx:explore` — обдумать идею или проблему, ничего не меняя.
- `/opsx:propose` — change целиком за один шаг (proposal, delta, design,
  tasks). `/opsx:new` + `/opsx:continue` — то же по одному артефакту.
- `/opsx:update` — поправить артефакты change после нового решения.
- `/opsx:apply` — выполнить задачи change (здесь меняется код).
- `/opsx:verify` — сверить реализацию с change и спекой перед архивом.
- `/opsx:sync` / `/opsx:archive` — влить delta в `openspec/specs/`.
- CLI: `openspec list` (changes), `openspec list --specs`,
  `openspec show <id>`, `openspec status --change <id>`,
  `openspec validate --all --strict`.

## Проверки

- **Одна команда: `nvim -l tests/run.lua`** — всё, что проверяется без GUI
  (наборы `unit`, `e2e`, `wezterm`, `install`, `trace`), и статус каждого ID из
  `openspec/specs/`: PASS / FAIL / SKIP / MANUAL / UNCOVERED. Одно
  требование — `--id WT-CLIP-2`, вся capability — `--id WT-CLIP`;
  осознанное изменение эталонов — `--update-golden` (diff — в тот же коммит).
  Отчёт — `.tests/report.json`, логи — `.tests/logs/`. Протокол, реестр и
  как добавить проверку — `tests/README.md`. Установщик macOS идёт в том же
  прогоне (на Windows — в WSL; ветка bash 3.2 — `FORGE_BASH32=<путь в WSL>`,
  в Git Bash — вместе с `MSYS2_ENV_CONV_EXCL=FORGE_BASH32`).
- Проба клавиатуры через conpty.dll (Windows): `nvim -l tests/run.lua conpty`
  — около 1,5 минут, поэтому в обычный прогон и хук не входит; идёт и с
  `--id WT-KBD-9` / `--id WT-KEYS-10`.
- Один файл проверок — напрямую, например копирование и `y` в copy mode:
  `nvim -l tests/wezterm/clipboard.test.lua` (печатает список проверок,
  код ≠ 0 при любом провале).
- Хук pre-commit (необязательный, `.githooks/pre-commit` — тот же
  `nvim -l tests/run.lua`): включить — `git config core.hooksPath .githooks`,
  выключить — `git config --unset core.hooksPath`. Включает владелец на
  своей машине; агент `core.hooksPath` не выставляет.
- `openspec validate --all --strict` — формат спек и changes (OpenSpec
  1.13.2; без глобальной установки —
  `npx -y @fission-ai/openspec@1.13.2 validate --all --strict`).
- `tests/install-macos.scenarios.sh [repo] [bash]` — установщик macOS в
  песочнице (bash 5 и bash 3.2; нужны bash, git, python3 — WSL/Linux/macOS).
- `tests/install-linux.scenarios.sh [repo] [bash]` — шаг WezTerm
  установщика Linux в песочнице (WT-LOAD-13; те же bash, общий
  `nvim_forge/scripts/lib/wezterm-link.sh`). Оба набора идут и в
  `nvim -l tests/run.lua` (набор `install`).
- WezTerm-конфиг грузится: `wezterm --config-file wezterm.lua ls-fonts`
  (при ошибке — пустой stdout и `ERROR` в stderr; `show-keys` ошибок НЕ
  показывает).
- nvim_forge headless: `NVIM_APPNAME=nvim_forge XDG_CONFIG_HOME=<repo> nvim --headless …`.
- Ручные чек-листы по платформам — `tests/manual/wezterm-windows.md`,
  `tests/manual/wezterm-macos.md`: то, что без GUI не проверить. Результат
  дописывается строкой `Проверено: <дата>, <ОС>, WezTerm <версия>, раскладка <…> —
  совпало | расходится: …`, прежние строки не правятся. Пункт без такой строки
  даёт в сводке `nvim -l tests/run.lua` статус MANUAL.
