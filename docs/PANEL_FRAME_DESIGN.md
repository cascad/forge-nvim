# Постоянные рамки панелей: варианты после прототипа

2026-11-11, IDE-076. Следующий шаг после7ef5d7a; это разбор архитектуры,
не внедрение новой раскладки. [Реальные изображения и метрики](PANEL_FRAME_REVIEW.md).

Пожелание владельца — **полная рамка и цвет**, включая понятный фокус.
Текущий zoom prototype показывает этот стиль, но не реализует постоянную
рамку обычного split. Новая реализация должна сохранять единый Space w,
функции backend, площадь и переносимость; цвет сам по себе не основание
добавлять ещё один постоянный слой состояния.

## Три реальных варианта

| Подход | Цельная рамка | Влияние на архитектуру | Оценка |
|---|---|---|---|
| Подкрасить текущие winbar/разделители Edgy | Нет | Существующие split/focus/collapse; ограниченные style options | Может улучшить аккуратность, но не закрывает IDE-076 |
| Наложить декоративное окно или копию panel buffer поверх каждого split | Да, как визуальный образец | Две window identities на панель; синхронизация resize/focus/mouse/close/session, исходный slot остаётся под overlay | Прототип допустим; такой постоянный слой не рекомендуется |
| Перевести рабочие панели на единую раскладку floating windows | Да, native border | Один владелец tool-layout вместо Edgy для этих панелей; backend остаётся источником данных/действий | Подходящий кандидат при обязательной полной рамке, но требует отдельного рабочего пилота |

Во втором варианте проблема не в количестве установленных пакетов:
два окна одного backend уже пришлось согласовывать в zoom. Прототип выявил
IDE-101. Делать такой overlay постоянным для каждой панели расширило бы
ту же задачу на всю раскладку. Это архитектурный риск, а не измеренное
утверждение о тормозах.

В третьем варианте можно исследовать **уже закреплённый Nui** как библиотеку
раскладки. Добавлять его поверх Edgy как второго хозяина того же tool-окна
не следует. Библиотека не заменяет адаптацию существующих backend и controls;
нет доказательства, что миграция окажется маленькой. До пилота Edgy остаётся
рабочим владельцем текущей раскладки, default не меняется.

## Предлагаемый следующий эксперимент

Сначала одна реальная панель Locals в отдельном тестовом layout. Не копия
buffer поверх живого source split: один видимый interactive window и один
владелец геометрии. Использовать native border и существующие DAP данные/
действия, не переписывать адаптер и не создавать общий новый framework.

Пилот должен ответить на конкретные вопросы:

1. Может ли backend обновлять тот же buffer/выбор/variables после step и
   нового breakpoint, если размещением управляет другой owner?
2. Работают ли Space w h/j/k/l/0/d/c/q/z/?, restore и возврат из помощи,
   без конкурирующего Edgy refresh и без второго source окна?
3. Кто сохраняет место для кода, resize и минимальные размеры? Два border
   столбца/строки входят в outer geometry; для каждого layout нужны свои
   фактические метрики, особенно для четырёх коротких DAP-секций.
4. Остаются ли working area, tabs/session, hide/reopen, job/channel/stdout и
   cleanup правильными после закрытия окна backend? Что происходит, если
   пользователь открыл native backend другим shortcut?
5. Какова измеренная цена открытия/idle/redraw относительно сохранённого
   baseline, без произвольных обещаний «быстрее» и без polling на каждый key?

Если для одной панели нужны постоянный shadow split, дублирующий window
registry или fork backend, это повод пересмотреть решение до переноса на
остальные панели. Красивый кадр не является основанием для такого переноса.

## Условия переноса в default

Нужен отдельный change с проверяемым контрактом владения окнами и планом
отката. Пилот не разрешает попутную перепись всех panels/session/root rules.
После выбора реализации — реальные E2E для Files/Outline/Tests/Search/Tasks/
Terminal/Trouble/Git и paused Debug, в том числе literal terminal input и
native действия выбранного элемента из zoom. Регресс каждого найденного
сбоя сохраняется; существующие44 checks не доказывают новый layout заранее.

Windows и Ubuntu проверяются поочерёдно; Mac запускается отдельно.
Physical GUI должен проверить шрифт/Nerd icons/DPI, мышь и фактическую
доставку клавиш WezTerm. Обсуждение этого дизайна не означает удаления Edgy
или завершения IDE-076; выбор постоянной реализации остаётся открытым.
